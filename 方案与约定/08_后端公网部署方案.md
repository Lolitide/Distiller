# 08 · 后端公网部署方案（替代内网穿透）

> 背景：目前用 Tailscale Funnel / cpolar 把本机 `8731`（只放行 `/api/relay/*`）映射到公网做测试。
> 上架审核与正式运营不能再依赖「一台开着的电脑 + 穿透」。
> 本文给出候选方案、推荐路径、迁移步骤与上线前清单。
>
> **调研日期：2026-10-25。价格与政策会变，下单前请以官网为准（文中已区分「已核实」与「量级参考」）。**

---

## 0. 一句话结论

1. **比选服务器更紧急的是「APP 备案」**——未完成备案的 APP，应用分发平台**不得提供分发服务**（工信部下发的省级通管局文件已明确）。这是上架的硬前置，必须**今天就开始办**，它才是关键路径。
2. **APP 备案必须由「接入商」提交**（已确认：华为**不**提供分发平台代备案）——所以你必须有一个**境内云服务商**身份（华为云/阿里云/腾讯云任一）。这一条把"怎么部署"和"能不能备案"绑在了一起：**先定接入商，再定部署**。
3. **推荐形态（2026-10-28 BYOB 之后）**：**境内常开 VPS/容器 + 域名**。BYOB 需要给每个用户托管一个 `botpy_main.py` 长连接子进程，**AGC 云函数这类短生命周期运行时不能承载**；AGC 可以只做 HTTP API 层，但会把架构拆成两套，当前不建议。**先定接入商（华为云/阿里云/腾讯云），再买一台 2C2G 起的境内轻量服务器。**
4. **机器人进程只需要出网**（连 QQ 网关、调推送），不需要公网入站——这是它天然适合放小主机的原因。

| 密钥 | 整个 `qqbot-backend/` 已被 `.gitignore` 排除，未进 git | ✅ 但迁移时仍要 `scp` 且 `chmod 600` |

## 3. 方案 A：AGC 云函数 + 云数据库（**仅 API 层，不适合 BYOB Bot**）

> **2026-10-28 结论**：BYOB 的每个租户 Bot 都是一条常驻 WebSocket + 一个 Python 子进程，**AGC 云函数无法承载**。如果坚持 AGC，必须另找一台常开主机跑 bot runner，架构被拆成两套；当前不推荐。下面内容保留作为「只把 App API 放 AGC」的参考。

你们 `07_前后端对接方案.md` 里已经论证过这条路（「路径 B：不依赖公网入口」）。它的价值仍然成立，但**只在"App 网络请求落在华为域名"这一层**，不等于"不用备案"：

```
QQ 群 ──WebSocket──► bot 进程（任意常开小主机，只需出网）
                        │  HTTPS 出站 + 共享密钥
                        ▼
              AGC 云函数（HTTP 触发器）──► AGC 云数据库 BotTask
                                              ▲
                                     华为自有域名 + HTTPS
                                              │
                                    手机 App 拉取（SDK）
```

**它的真实优势**：

- App 的网络请求落在**华为自己的域名**上，你不用运维自有域名的证书，审核方不会因为「服务器不可达/明文 HTTP/证书过期」打回；
- bot 主机**不开放任何入站端口**，不需要公网 IP、不需要买带宽。

**它不能替你解决的事**（务必看清）：

- **APP 备案仍然必须做**，且必须由**接入商**提交（AGC 场景下是华为云）；
- 「后台域名」这一栏在 AGC 场景怎么填，**仍需向华为云备案客服确认**。


**必须先验证的 3 个前提**（不要凭假设开工）：

1. AGC 云函数是否支持 **HTTP 触发器**（供外部的 bot 进程调用）；
2. 云数据库的**免费额度/读写上限**是否够（按你们 30 分钟窗口 + 每日消息量估算）；
3. **APP 备案表单里如何填写「服务器/域名」**——走 AGC 时是否可以不填自有域名。这一条必须问华为备案指引/工单，**它决定 A 和 B 的取舍**。

**改造量**：后端加一个「写云」出口（把候选写进 AGC）；前端 `service/cloud/` 从调 `/api/relay/*` 改为读云数据库。按你们 `07` 文档的评估是「中等」。

## 4. 推荐方案 B：自建公网后端（保留现有架构）

### 4.1 选型建议

- **机器**：国内轻量应用服务器 **2 核 2G 起**（跑 bot + HTTP + 规则解析够用；**不要指望在同机上跑 9B 模型**）；
- **系统**：Ubuntu 24.04 LTS（Python 3.12 可直接用）；
- **域名**：便宜的 `.top/.xyz/.cn` 均可，关键是**能备案**（`.cn` 需实名）；
- **HTTPS**：用 **Caddy** 自动签 Let's Encrypt，零手工证书；
- **备案**：先做**域名 ICP 备案**（需要域名、服务器、身份证、真实性核验，通常 1–4 周），再做 **APP 备案**。

### 4.2 迁移步骤（可直接照做）

**① 服务器初始化**

```bash
sudo apt update && sudo apt install -y python3 python3-venv python3-pip caddy git rsync
sudo useradd -m -s /bin/bash zhiliao
sudo -iu zhiliao
# 把 qqbot-backend 上传到 /home/zhiliao/app
cd ~/app && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
```

> 先把 `requirements.txt` 里的版本在 **Python 3.12** 上装一遍；`qq-botpy-v2==1.0.2` 等若报错再微调版本。

**② 环境变量（写 `/home/zhiliao/app/.env.prod`，`chmod 600`）**

```ini
QQBOT_APP_ID=...
QQBOT_SECRET=...
QQBOT_CONSOLE_HOST=127.0.0.1      # 控制台只绑本机
QQBOT_CONSOLE_PORT=8730
QQBOT_CONSOLE_USER=admin
QQBOT_CONSOLE_PASSWORD=<强口令>
QQBOT_PUBLIC_HOST=127.0.0.1       # 公开口也只听本机，由 Caddy 反代
QQBOT_PUBLIC_PORT=8731
QQBOT_RELAY_KEY=<新随机值，勿沿用本机 .relay_key>
QQBOT_DEV_INGEST=0                # 生产必须关闭
QQBOT_AUTOSTART_BOT=1             # 旧自营 bot（可选；BYOB 租户由 tenant_manager 拉起）
QQBOT_SECRET_KEY=<base64(32B)>    # BYOB 租户 AppSecret 加密主密钥；丢失=全部租户需重新绑定
QQBOT_MAX_TENANTS=20              # 按机型调，2C2G 建议 8–12
QQBOT_PUSH_SA=/home/zhiliao/app/service_account.json
```

**③ systemd 托管（重启自愈 + 开机自启）**

```ini
# /etc/systemd/system/zhiliao.service
[Unit]
Description=Zhiliao backend (relay + bot)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=zhiliao
WorkingDirectory=/home/zhiliao/app
EnvironmentFile=/home/zhiliao/app/.env.prod
ExecStart=/home/zhiliao/app/.venv/bin/python -X utf8 server.py
Restart=always
RestartSec=5
# 只允许写自己的工作目录
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now zhiliao
sudo systemctl status zhiliao --no-pager
```

**④ Caddy 反代 + 自动 HTTPS（只暴露公开口）**

```caddyfile
# /etc/caddy/Caddyfile
api.example.com {
    encode gzip
    # 只反代公开口；控制台 8730 不做任何反代
    reverse_proxy 127.0.0.1:8731
    header {
        Strict-Transport-Security "max-age=31536000"
        X-Content-Type-Options nosniff
        -Server
    }
}
```

```bash
sudo systemctl reload caddy
```

**⑤ 防火墙（关掉一切不需要的入站）**

```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp     # 或改成你的 SSH 端口
sudo ufw allow 80,443/tcp # Caddy 用
sudo ufw enable
```

**⑥ App 侧**：把 `Config.baseUrl` 改成 `https://api.example.com`，删除「允许用户改服务器地址」或仅在 debug 包保留。

### 4.3 数据迁移

```bash
# 本机 → 服务器（含路由表、词表、群名缓存、运维库）
scp qqbot-backend/{relay_store.json,group_lexicon.json,group_names.json,bot.db} zhiliao@<host>:~/app/
scp qqbot-backend/.env.prod qqbot-backend/service_account.json zhiliao@<host>:~/app/
# 已存在 BYOB 租户时才搬（必须同时搬 QQBOT_SECRET_KEY，否则密文解不开）
scp qqbot-backend/tenants.json zhiliao@<host>:~/app/
ssh zhiliao@<host> 'chmod 600 ~/app/.env.prod ~/app/service_account.json ~/app/tenants.json'
```

**不要**搬 `.relay_key`，在服务器上重新生成并轮换（见 §6）。**`QQBOT_SECRET_KEY` 必须与 `tenants.json` 配套迁移；丢失后所有租户只能重新绑定。**

## 5. LLM 怎么处理（这是最容易踩坑的一环）

`qwen3.5:9b` 约 7GB，2C2G 云主机**跑不起来**，CPU 推理也会慢到不可用。三条路：

| 方案 | 做法 | 成本 | 风险/合规 |
| --- | --- | --- | --- |
| **① 规则降级（推荐做默认）** | 不装 Ollama，`llm_parse.available()` 返回 False，走 `pipeline_proto` 规则链路 | 0 | 抽取质量下降，但**零幻觉、零外部依赖**，且你们已有 `test_parse_degraded.py` 覆盖 |
| **② 调国内大模型 API** | 把 `llm_parse` 的 `_post` 指向 DeepSeek/Qwen 等 API | 低（按 token，量小约几元/月） | ⚠️ **群消息正文会离开你的服务器**，与「正文不落盘」的自我承诺不冲突，但**必须在隐私政策里写明**；接口提供方需是已备案的生成式 AI 服务 |
| **③ 审核期临时开本机 Ollama** | 演示时把 `OLLAMA_BASE` 指向一台有 GPU/大内存的机器 | 高 | 不稳定，审核期不建议 |

**建议**：生产默认走 ①（稳、免费、可解释），答辩演示时用 ③ 或本机环境展示 AI 能力；如果确实要 ②，先改隐私政策再上线。

## 6. 公网暴露前必须做的安全加固（按优先级）

| 优先级 | 项 | 具体做法 |
| --- | --- | --- |
| P0 | 控制台绝不能公网可达 | `QQBOT_CONSOLE_HOST=127.0.0.1`；Caddy 只反代 8731；确认外部访问 `https://域名/api/status` 返回 404 |
| P0 | 生产关闭联调注入口 | `QQBOT_DEV_INGEST=0`；公开口已挡 `/dev/ingest`，但双保险 |
| P0 | 轮换密钥 | 服务器上重新生成 `QQBOT_RELAY_KEY`，不沿用本机 `.relay_key`；`QQBOT_CONSOLE_PASSWORD` 用强口令 |
| P0 | 密钥文件权限 | `.env.prod`、`service_account.json`、`tenants.json` → `chmod 600`，属主 `zhiliao`；`QQBOT_SECRET_KEY` 只放 `.env.prod`，离线另存一份 |
| P0 | 租户子进程风暴 | `/api/relay/tenant/register` 按设备/IP 限流；同设备并发锁；失败立即 kill；`QQBOT_MAX_TENANTS` 按机型设小 |
| P1 | **补限流**（HTTP 层当前完全没有） | `/device/register` 按 IP 限速（如 1 次/分钟、单 IP 设备上限 3）；`/messages`、`/parse` 按设备令牌限速；超限返回 429。注意 `register_device()` 每注册一次都会**全量重写 `relay_store.json`**，不设限就等于开放磁盘写放大 |
| P1 | 屏蔽管理接口 | 公开口对 `/admin/*` 直接 404（现在是靠 `x-relay-key` 校验，建议再挡一层） |
| P1 | 设备/数据容量上限 | `relay_store.json` 加设备总数上限与过期回收，防刷爆磁盘 |
| P2 | 日志脱敏 | 确认日志里不落消息正文、不落完整 openid（你们的 `_preview_len` 机制已在做，复核一遍） |
| P2 | 备份 | `relay_store.json` / `group_lexicon.json` / `tenants.json` 每日备份；**`QQBOT_SECRET_KEY` 单独离线保存**，不与 `tenants.json` 放同一备份包 |
| P2 | 监控保活 | 定时探活 `/api/relay/health`，异常告警（邮件/webhook）；systemd `Restart=always` 已兜进程崩溃 |

> 其中「限流」是**必须补**的：`register_device` 无上限，公网暴露后任何人都能把 `relay_store.json` 写爆。

## 7. 审核期专项清单（比服务器更容易被忽略）

1. **APP 备案**（硬前置）：未备案不能上架。需要主体信息 + APP 信息 + 服务器/域名信息；**先确认 A/B 方案下表单怎么填**，再决定买什么。
2. **备案号展示**：按要求在 App 显著位置（设置页/关于页）标注备案编号。
3. **隐私政策补条款**：写清「消息由我们的服务器/华为云服务处理」「若使用第三方大模型 API，文本会发送给该服务商」「BYOB 下用户自建 Bot 的 AppID/AppSecret 由服务端加密托管、仅用于建立该 Bot 的连接」「自动群采集默认关闭，只处理用户主动转发的单条内容」等（取决于 §5 选择）。
4. **审核员怎么进得来**：绑定流程已改为 **BYOB（用户创建自己的 QQ Bot，填 AppID/AppSecret）**，不再要求审核员给官方 Bot 发配对码；但审核员仍未必愿意创建 Bot。**必须准备**：
   - **主推荐路径：粘贴/分享消息 → 待确认**，审核说明写明「无需 QQ Bot 即可完整体验」；或
   - 演示账号 + 预置数据；或
   - 审核说明里写清 BYOB 步骤，并提供一个可用的测试 Bot（如愿意）。
   - 否则大概率以「无法验证核心功能」驳回。
5. **服务可用性**：审核期间服务器必须 7×24 在线；建议审核前一周开始跑监控，确认没有崩溃重启。
6. **后台通知**：你们文档里已记录「App 在后台收不到通知是平台边界」，审核说明里应提前写明，避免被判为功能缺陷。

## 9. 风险与取舍

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 备案没下来就提交审核 | 直接无法上架 | **今天启动备案**；先用方案 C（境外）跑通审核演示，备案下来再切 B |
| 2C2G 跑不动 LLM | 解析质量下降 | 默认规则降级；演示用本机；或接 API（先改隐私政策） |
| 公网被刷 | 磁盘/内存打满、服务不可用 | 补限流 + 设备上限 + systemd 重启 + 监控 |
| 境外机器国内访问抖动 | 审核时超时 | 审核期若走 C，加客户端重试与超时提示；必要时用国内备案后切回 |
| 审核员无法完成绑定 | 功能无法验证被驳回 | 提供演示账号/预置授权 + 图文步骤 |
| 迁移后数据不一致 | 用户订阅丢失 | 迁移前备份，迁移后核对 `/api/relay/my/data` 与 `/admin/bindings` |
