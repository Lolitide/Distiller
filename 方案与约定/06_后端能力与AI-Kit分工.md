# 06 · 后端能力 + AI/Kit 分工（对照 `05_API接口文档.md`）

> 读法：本文回答三个问题——**后端现在到底能做什么**、**哪些活是 Kit 干的**、**哪些活是 AI 干的**。
> 与 `05_API接口文档.md` 的差异逐条对照在 §2。
> 最后核验：2026-10-15（后端 `qqbot-backend/`；端侧契约以交付前端 `cicad_fe` 为准）。

---

## 1. 三层分工（先看这张）

| 层 | 跑在哪 | 具体技术 | 负责什么 | 出不出网 |
| --- | --- | --- | --- | --- |
| **规则层** | 后端 Python | `pipeline_proto.py` / `candidate_engine.py` | 噪声过滤、时间**归一化**、去重、聚类、优先级、幂等 ID、游标 | 不出网 |
| **AI 层** | 后端本机 | Ollama `qwen3.5:9b`（`llm_parse.py`） | **语义判断**：分类、标题、摘要、时间/地点的**原话**、需带物品 | 不出网（本机） |
| **Kit 层** | **端侧** | `@kit.NaturalLanguageKit`（`ParseService.ets`） | 实体抽取（时间/地点/人名/电话/URL/邮箱）、分词词性 | 不出端侧 |

一句话：**Kit 抽"实体串"，AI 判"这是什么意思"，规则保证"不猜、不错、可复现"。**

三者是**互补而非替代**：
- Kit **不会**告诉你"这是待办还是通知"——它只给实体和词性。
- AI **不负责**把"后天"算成 `2026-10-15`——归一化是规则算的，AI 只给原话 `后天`。
- 规则 **不做**语义判断——不用规则去猜"开打"是不是比赛。

## 3. 一个候选（Candidate）的每个字段，是谁产出的

以 `GET /candidates` 返回的一条为例：

| 字段 | 产出者 | 说明 |
| --- | --- | --- |
| `candidate_id` | **规则** | `c_` + 群号与簇首条文本的 hash → 幂等、可 upsert |
| `rev_seq` | **规则** | 全局单调；内容变了才 +1（内容没变不重发） |
| `thread_id` | **规则** | 群号前 6 位 + 锚点 hash |
| `kind` | **AI**（失败回退**规则**） | 待办/通知/活动/出行计划/闲聊/忽略 |
| `priority` | **规则** | 由 `kind` + `time_normalized` 与当前时间差算出（≤24h→urgent，≤3d→high，闲聊→later） |
| `title` | **AI**（回退规则） | ≤24 字 |
| `summary` | **AI**（回退规则拼接） | ≤120 字；**若 AI 编造过结构化槽位，就不信它润色的摘要**，改用原话拼接 |
| `time_text` | **AI** + **规则** | AI 给原话；跨消息拼合（`明天` + `下午两点` → `明天下午两点`）由规则做 |
| `time_normalized` | **规则（绝不靠 AI）** | 由 `time_text`/整簇文本用 `parse_time` 算；中文数字（`两点`）走 `cn2an` |
| `time_unresolved` | **规则** | `下周`/`月底` 这类推不出确切日期 → true（**不猜**） |
| `place` | **AI** + **规则** | AI 给原话；**跨消息拼合**由规则做（`培训…` + `主楼A103`） |
| `who` / `deadline` | **AI** | 必须是原文子串 |
| `items[]` | **AI** | 需带物品/注意事项，逐字取自原文 |
| `steps[]` | **规则** | 簇内各条的动作去重 |
| `tags[]` | **AI 优先** + 规则 | 具体标签（竞赛/报名…） |
| `confidence` | **规则** | 由 kind/槽位/动作综合算出 |
| `engine` | **规则** | `llm` / `rules`，标明这条是谁算的 |
| `source{}` | **规则** | 群号、发送者、`msg_ids`、条数、首末时间 |

> **安全闸（规则）**：AI 给的所有"原话类"字段都要过**原文子串校验**——不是原文里逐字出现的，一律清空。
> 所以**编造内容永远不会到用户面前**。实测幻觉率 1.3%（9b），全部被拦下。

## 4. Kit 干什么、不干什么

> 交付前端的端侧 AI 全在它自己的 `service/ai/`（见 §4.1），按它的 `docs/开发指南.md` §9.4 硬规矩
> **必须动态 `import()`**，目前是骨架、尚未接入。§4.2 / §4.3 是我们在联调期间**实测出来的坑与结论**
> （实现代码不属交付物），交付前端写 `service/ai/` 时照这两节避坑。

### 4.1 端侧 Kit 用什么（交付前端 `service/ai/` 的规划）

| 子服务 | Kit | 用途 |
| :-- | :-- | :-- |
| `TextExtractService` | Natural Language Kit（`textProcessing.getEntity` / `getWordSegment`） | 实体抽取（DATETIME / LOCATION / NAME / PHONE_NO / URL / EMAIL）+ 分词 |
| `OcrService` | Core Vision Kit（`textRecognition.recognizeText`）+ Scan Kit（`detectBarcode`） | 截图文字 / 二维码 |
| `SpeechService` | Core Speech Kit | 语音转文字（识别完即丢音频，只留文字） |

**三条平台事实（照 `cicad_fe/docs/开发指南.md` §2.2 / §9.4）**：
- 这三项**都不支持模拟器**，且模拟器上**静态 import 会直接闪退** → 一律动态 `import()`；
- NL Kit 单次输入 **≤1000 字符** → 要切片合并，并给每次调用包超时；
- 统一返回「成功 / 失败 + 错误码」，**异常不许抛到页面层**。

### 4.2 Kit 结果没被用起来 → **已改成按需（2026-10-14）**

**问题**（改造前）：
- 列表页每条消息下方的 `时间 / 地点 / 截止 / 需带` **不是 Kit 给的**，读的是 `item.event`（= 后端 `parse`）。
- Kit 的产出 `msg.entities` 唯一真渲染点是**详情页**的实体列表；`HomePage.entityListFor()` 与
  `ParseRules.buildKeyFields()` **都是死代码**（定义了、全文无调用）。
- 但 `parsePending()` 在**每条新消息**上都跑一遍 Kit（逐片 `getEntity` + `getWordSegment`，带切片/超时/批量提交）
  —— **用错场景**：为详情页一个低频小列表，付了全量开销。

**改造后（按需）**：
| 调用方 | 是否跑 NL Kit |
| --- | --- |
| `parsePending()`（批处理，每条新消息） | ❌ 不跑；只做图片识别 + 端侧规则事件 |
| `MessageDetailPage.ensureEntities()`（进详情页，按 `msg_id` 去重） | ✅ 跑**这一条** |
| 详情页「重新解析」按钮 | ✅ 强制跑 |

实现：`ParseService.parseOne(msg, withNlp)` 加开关；`parsePending → false`、`reparse/ensureNlp → true`；
`nlpDone: Set<msg_id>` 保证同一进程内不重复跑。

**仍未处理的**：`HomePage.entityListFor()` 与 `ParseRules.buildKeyFields()` 两处死代码仍在（删不删看你）。

### 4.3 端侧与后端**不一致**的已知点（同源 bug，端侧未修）

| 问题 | 后端 | 端侧 `nlp/` |
| --- | --- | --- |
| `时` 当时间分隔符（`一时`→01:00） | 已修（只认 `点 / : / ：`） | ✅ 本来就没有（`TimeParser.ets:88`） |
| **不支持中文数字时间**（`下午两点`/`十一点`） | ✅ 支持（`cn2an`） | ❌ **不支持**（正则只认 `\d{1,2}`） |
| **通用标签 `"通知"` 导致无关通知被并簇** | 已修（聚类忽略通用标签） | ❌ **存在**（`EventBuilder.ets:41` + `EventCluster.ets:180`） |
| **`10.31` 点分日期不认** | 已修 | ❌ **存在**（`TimeParser.ets:149/157`） |
| **地点缺跨消息拼合** | 已修（`_place_of`） | ❌ **存在**（`EventCluster.ets:222` 只取 `best`） |

> 两端不一致 = 同一句话在**端侧**和在后端里结果不同。**§4.3 的四条端侧问题已在 2026-10-14 一并修掉**

## 6. 隐私红线（三层都要守）

| 数据 | 状态 |
| --- | --- |
| 群消息正文 | **只在后端内存 30 分钟窗口**，不落盘 |
| 候选（candidates） | 不落盘（内存流） |
| `/parse` 的手动输入/截图/文件 | **只处理、不存储**：不进窗口、不进候选流、不落盘；`test_parse_api.py` 第三节专测 |
| `/attachment` 的附件字节 | **只在内存过路**：90 秒短缓存（16 条/64MB 封顶）后即丢，不进窗口、不落盘；窗口过期附件找不回 |
| **端侧**的附件副本（`filesDir/attachments/`） | 群里的图片/文件在**轮询到的 30 分钟窗口内**被 App 取回并落到**本机沙箱**（`AttachmentStore`），所以窗口过期后仍能查看/保存；默认 200MB 上限、按最旧优先淘汰，随「清空本机消息」一起删。**不占服务器存储** |
| **端侧**的用户画像（`profile_json`） | 词条**只落端侧** preferences，随「清空本机数据 / 清空画像」一起删；出端侧的素材只有「词 + 次数 + 类别」，**不含正文**；后端 `/profile` 与之同款「只处理不存储」（见上表） |
| **按群领域词表** `group_lexicon.json` | **唯一允许落盘的非路由数据**，且只含「词 + 次数 + 类别」，**绝不含正文**（写完自检：最长条目是词，不是句子） |
| 端侧 Kit 解析 | 全程**不出端侧**（无网络请求） |
| 一键删除 `DELETE /my/data` | 清绑定/订阅/配对码；该群已无别的订阅者时，**连带清掉它的词表** |

| 项 | 说明 |

| 端侧 Kit 结果没接进列表 | 见 §4.2 |
| `10.31` 以外的日期写法 | `版本1.2` 这类会被误当日期，暂未处理 |
| 单线程解析队列 | 9b 约 3s/条，群里短时涌入 50 条会排队约 150s（窗口 30 分钟内不丢，只是迟） |
| 词表残余噪声 | `不同/或者` 之类靠人工删（`drop()`）；`drop_words` 回传通道后端已有，前端删词 UI 待做 |
| QQ 附件直链（已取证 ✅） | **2026-10-15 真机验证通过**：群里发截图 → 后端可取回原图；发 docx → 「保存到手机」成功落盘。
  说明 QQ 的图片 CDN 与文件直链（`ftn.qq.com`）**服务端都可 GET**，`/health` 的 `capabilities` 已加 `attachment`。
  前端侧接法（附件卡片 / 点击预览 / 保存到手机）见 `07_前后端对接方案.md` §4 |
| 群文件不参与 AI 上下文 | 候选/LLM 只读消息 **`content`**（`candidate_engine.py` 里 `payload.get("content")`），而文件消息的 content 为空
  → 群文件对候选/摘要**没有任何贡献**。**手动添加的文件则相反：会参与**——
  `/parse` 用 `office_extract` 抽出文本后送模型。要不要让群文件也进 AI（服务端主动下载 + 抽取文本）需单独定，  涉及隐私与算力 |
| **附件落盘只能"趁窗口还在"** | App 只在前台轮询（`EntryAbility.onBackground` 会停轮询），所以**后台期间到达**的消息，重开 App 时可能已超 30 分钟 → 附件取不回。已落盘的不会丢；没来得及落盘的**找不回**，UI 文案已改成「本机没存过，且已超 30 分钟窗口」 |
| **画像只吃本机消息** | 端侧只保留最近 500 条消息，画像素材就来自这批（且只取 `is_self === true`）。消息被滚动淘汰后，对应的词条计数不再增长（但已生成的词条仍在画像里） |
