# 信息总结方案（端侧可运行）—— 调研 + 验证 + 落地

> 适用项目：「知了」大学信息源（HarmonyOS 校园信息整理与提醒）
> 解决的问题：**能抽取的字段太少、拼不成一句话**
> 本文所有结论都在你项目的**真实群消息（106 条）**上跑过验证，不是纸面方案。

---

## 0. 结论先行：你卡住的不是模型，是方法

三个诊断，按重要性排序：

### ① 缺少「分级过滤」—— 66% 的消息本来就不该被理解

在你真实的 106 条消息里跑一遍分级，结果是：

| 分级 | 条数 | 占比 |
| --- | --- | --- |
| **忽略**（纯数字、表情、`ok`/`bb` 这类） | 70 | 66% |
| **闲聊**（疑问句、水群、"难道…"） | 33 | 31% |
| **待办** | 2 | 1% |
| **通知** | 1 | 1% |
| **出行计划** | 2 | 1% |

也就是说：**只有 4 条消息值得整理**，另外 102 条进任何"总结"流程都是浪费和噪声。
如果你把所有消息都塞给模型总结，模型面对 96% 的噪声，当然只能吐出"少量、杂、拼不成句"的结果——**这不是模型能力问题，是输入没过滤**。

### ② 用「实体抽取（NER）」去做「信息整理」，方向就错了

固定 NER 只能给你 `时间 / 地点 / 人名 / 机构` 这几类，所以你会感觉"抽取的种类很少"。
但用户想要的不是实体，而是**可执行的事件对象**：要做什么、什么时候、在哪、谁负责、截止什么时候。

这两件事的区别：

```
NER 思路（你现在的）          事件对象思路（建议改成）
─────────────────────        ─────────────────────
实体：时间=后天               事件类型：出行计划
实体：地点=火车站             动作：先去坐车，再去北京旅游
实体：机构=北京               时间：2026-10-14（后天）
→ 拼句子：??                 地点：火车站
                              → 模板成句：计划先去坐车，再去北京旅游；
                                          途经/目的地：火车站；时间：2026-10-14（后天）
```

**事件类型是封闭枚举（4~6 种），每种类型有自己固定的槽位表**——这样"种类少"就不再是缺点，而是可控的接口。

### ③ 「拼成一句话」不该由模型生成，而应该由模板拼

这是最关键的一条。我调研到的 Huawei 官方示例（会议助手）作者写得很直白：

> **"语义层真正要做的不是'总结'，而是把会议内容拆成业务对象"**
> AI 只生成候选结果，用户确认后才进入任务系统

**对提醒类应用来说，让模型自由生成一句话是有害的**：

- 模型可能把"下周三"生成成"本周三"，用户因此错过截止时间；
- 模型可能凭空补一个地点；
- 生成结果不可校验、不可回归测试。

正确做法：**输出 = 模板 × 槽位**。措辞来自原话，语序来自模板。
代价是字段少时句子短，收益是**永不出错、可单测、可离线**。

实测对比（同一条真实消息）：

| 方案 | 输出 |
| --- | --- |
| 模型自由生成 | "记得明天上午去教学楼上课哦" ← 时间被改写、加了语气词、无法验证 |
| 模板 × 槽位（本方案） | `上课；时间：2026-10-12 09:00（今天上午9点）；地点：教学楼` ← 可核对、可点回原话 |

## 1. 调研：端侧可用的总结能力有哪些

### A. 系统原生能力（**优先尝试**，零模型体积、零功耗）

| 能力 | 能做什么 | 与本项目的匹配度 |
| --- | --- | --- |
| **Data Augmentation Kit**（HarmonyOS 7 / API 26） | 端侧知识加工：**邮件智能分类、摘要、待办意图抽取** | ⭐⭐⭐ 官方就是拿"分类 + 摘要 + 待办意图"当示例场景 |
| **Natural Language Kit** | 文本语义理解、分词、**实体抽取** | ⭐⭐ 适合做槽位里的"时间/地点"补充 |
| **Core Vision Kit** | 文字识别（OCR） | ⭐⭐ 对应你们报告里的「截图分享」通道 |
| **Core Speech Kit** | 语音识别（端侧、离线） | ⭐ 对应报告里的「语音输入」通道 |
| **Intents Kit（意图框架）** | 把结构化结果交给系统（日历/待办） | ⭐⭐ 对应报告的「提醒」模块，可让系统的日历提醒替你做兜底 |

**行动建议**：先去 AGC/开发者后台确认 **Data Augmentation Kit 是否已对你的应用开放**。如果开放，摘要+待办抽取这块**直接用它，不要自己训模型**（你们只有一个月）。它即使不可用，下面的方案也完全不依赖它。

### B. 端侧自跑小模型（**成本最高，建议放到最后**）

调研到的技术路径是通的：

- **MindSpore Lite** 是鸿蒙官方端侧推理引擎，支持 NPU 优先、CPU/GPU 兜底；
- 流程：`.onnx/.mindir` → 量化（**INT8 体积缩 4 倍、速度 2~3 倍、精度损失通常 1~2%**）→ 转 `.ms` → ArkTS 用 `mindsporeLite` 加载推理；
- 有社区实践把 **Qwen-1.5B 量化后跑在 NPU 上**（论坛帖，非官方文档，**需自行实测功耗与内存**）。

**但对你这个项目，我不建议现在做**，原因：
1. 你要解决的问题 90% 靠"分级 + 封闭 schema + 模板"就能解决，不需要模型；
2. 端侧 1.5B 模型的集成、内存占用（数百 MB）、功耗、机型差异，一个月内做不完；
3. 提醒类应用对准确性要求极高，小模型生成的内容**仍然需要校验**，那还不如直接不生成。

### C. 折中方案：小模型只做"受约束的结构抽取"，且必须校验

如果你确实想用模型（比如为了展示 AI 能力），**唯一可接受的用法**是：

- 模型只输出 **JSON**，字段来自**封闭枚举**，禁止自由文本；
- **prompt 里强制要求：每个字段值必须是原文里出现过的一段子串，填不出来就输出空字符串，禁止编造**；
- 拿到结果后做**校验**：字段是否在枚举内、时间格式是否合法、值是否真的是原文子串；
- **校验不通过就整体丢弃，回退到规则方案**。

这样模型只可能"漏"，不可能"编"。这就是下面 T3 层的设计。

## 2. 方案：三层渐进架构（每层都能单独跑、单独验收）

```
群消息
  │
  ├─ T0 归一化 ── 表情/AT/链接还原（否则前端看到 <faceType=6,...> 这种乱码）
  │
  ├─ T1 分级过滤 ── 噪声/闲聊/待办/通知/出行计划（66% 在这里被丢掉）
  │     └ 规则实现，纯本地，毫秒级
  │
  ├─ T2 槽位抽取 + 模板成句 ── 封闭事件类型 × 固定槽位 × 模板拼接
  │     └ 规则实现，零幻觉，可单测
  │
  └─ T3 事件聚合（可选增强）── 把连续相关消息并成一个"事件"，给出标题
        └ 关键词/TF 实现；若 Data Augmentation Kit 或端侧模型可用，用它替换
```

**关键：T1/T2 完全不需要 AI**，而且已经能产出可用的卡片。T3 才是"锦上添花"。

### T0 归一化（必做，否则界面是乱码）

QQ 把表情下发成这种形式，直接展示用户看到的就是乱码：

```
<faceType=4,faceId="",ext="eyJ0ZXh0IjoiW+WTh+Whnl0ifQ==">
```

`ext` 是 base64 的 `{"text":"[哇塞]"}`。**必须解码成 `[哇塞]`**。
同理 `<@8C9570...>` 要转成 `@某人`，URL 转成 `[链接]`。

### T1 分级过滤（收益最大的一步）

规则很简单但极有效：

```
纯数字/单字符/纯标点           -> 忽略
只剩表情、@、链接              -> 忽略
纯字母缩写（ok/hh/vu/bb）      -> 忽略
疑问句（吗/呢/几点/什么时候）   -> 闲聊（不问用户任何东西）
出现闲聊词（那我/干脆/哈哈/感觉/是不是）且无强任务词 -> 闲聊
有"记得/别忘/需要/请/务必/截止/ddl"  -> 待办
有"通知/报名/截止/比赛/大赛/招聘"    -> 通知
有"坐火车/旅游/出发" + 时间          -> 出行计划
```

**产品原则：宁可漏判成闲聊，也不要误判成待办。**（一条假提醒比漏掉更伤信任）

### T2 槽位抽取 + 模板成句

**封闭事件类型**（4 类就够，别贪多）：

| 类型 | 槽位 | 模板 |
| --- | --- | --- |
| 待办 | 动作、时间、地点、对象、截止 | `{动作}；时间：{}；地点：{}` |
| 通知 | 事件名、截止、标签 | `通知：{事件名}；截止：{}` |
| 出行计划 | 动作、时间、途经/目的地 | `计划{动作}；途经/目的地：{}；时间：{}` |
| 闲聊 | — | 不生成任何句子 |

**时间解析（最容易出错的地方）**：

- 能确定的才归一化：`今天/明天/后天/下周三/10月20日/9点/下午3点` → `2026-10-14 09:00`
- **推不出确切日期就留空并标记 `unresolved`**：`下周`、`月底`、`最近` → 显示 `下周（待确认具体日期）`
- 界面上**永远同时显示原话**：`2026-10-14（后天）`
- 相对时间的基准是**消息自己的时间戳**，不是当前时间（否则补看历史消息会算错）

**成句时要注意的坑**（我在实测里踩到的）：
- 地点正则会贪婪匹配，`记得来教学楼` 会被抽成地点 → 要剪掉前面的趋向动词（`来/去/在/往`），只留 `教学楼`；
- 动作描述里要**先抠掉时间串和地点**再拼句，否则出现 `来教学楼上课；地点：教学楼` 这种重复；
- 通知类文案的客套尾巴（`有兴趣的同学可以参加`）要剪掉。

### T3 事件聚合

规则：**共享标签或关键词 + 间隔 < 30 分钟 → 同一簇**，每簇取置信度最高的一条当代表。

⚠️ **不要用"同一发送者"当聚合条件**：实测会把同一个人连发的无关消息拼成 `我是消息 + 消息` 这种垃圾簇。

## 3. 界面上不要输出"一段摘要"

这是方案的一部分，不是 UI 细节：

> 你们的报告写的是「信息按用户的待办组织」「首页按接下来要做什么组织，不做信息流」。
> 那么展示形式就不该是一段话，而应该是**结构化事件卡片**。

推荐卡片（一条真实验证输出）：

```
┌────────────────────────────────────────────┐
│ ⏰ 待办 · 课程              ● 高置信 0.95   │
│ 上课                                       │
│ 📅 2026-10-13（明天）   📍 超市             │
│ ─────────────────────────────────────────  │
│ 「明天去超市买点吃的」            ▸ 查看原话 │
│ 硫酸Cu · 10-12 19:54          [转成待办]    │
└────────────────────────────────────────────┘
```

要点：
- **标题短、字段结构化**（时间/地点/截止各自成行，用户一眼能扫）；
- **必须能回到原话**（卡片底部显示原文 + 来源人和时间）——这既是可信度，也是你们报告里"原文对照"的设计；
- **置信度低时显式标注**「字段不完整，建议人工确认」，不要假装确定。

## 5. ArkTS 落地：文件与职责

```
entry/src/main/ets/nlp/
├── MessageNormalizer.ets   // T0：表情解码、@ 还原、去链接
├── MessageClassifier.ets   // T1：噪声/闲聊/待办/通知/出行计划
├── TimeParser.ets          // T2：中文时间表达 -> 归一化 + 原话保留
├── SlotExtractor.ets       // T2：动作/地点/人物/截止（找不到就留空）
├── EventRenderer.ets       // T2：模板成句（禁止模型自由生成）
├── EventCluster.ets        // T3：关键词聚合 + 标题
└── EventValidator.ets      // T3 用：校验模型输出（枚举/时间格式/原文子串）
```

### 关键实现要点（照抄即可）

**T3 的模型校验器（如果你用了小模型，这是安全闸）**：

```ts
// EventValidator.ets 的核心逻辑
export function validateLlmEvent(raw: string, sourceText: string): CampusEvent | null {
  let obj: CampusEvent;
  try {
    obj = JSON.parse(raw) as CampusEvent;
  } catch (e) {
    return null;                                  // 不是 JSON -> 丢弃，回退规则
  }
  // 1) 类型必须在闭集里
  if (!['待办', '通知', '出行计划', '闲聊'].includes(obj.kind)) {
    return null;
  }
  // 2) 每个非空字段的值必须是原文子串（防编造，最简单也最有效的护栏）
  const fields: string[] = [obj.action, obj.place, obj.who, obj.time_text];
  for (const v of fields) {
    if (v && v.length > 0 && sourceText.indexOf(v) < 0) {
      return null;
    }
  }
  // 3) 归一化时间必须能通过格式与合理性检查
  if (obj.time_normalized && !/^\d{4}-\d{2}-\d{2}( \d{2}:\d{2})?$/.test(obj.time_normalized)) {
    return null;
  }
  return obj;   // 通过校验才允许进入候选列表
}
```

**为什么"值必须是原文子串"这条最有用**：它一行代码就把"模型编造时间/地点"这类最危险的错误全部挡住，而且不依赖任何模型能力。

**给模型的 prompt 模板（如果你要用模型）**：

```
你是信息抽取器，只做抽取，不做总结，不做改写。
从下面这条 QQ 群消息里抽取字段，输出 JSON。

硬性要求：
1. kind 只能是：待办 / 通知 / 出行计划 / 闲聊
2. 每个字段的值必须是我给你的原文里**逐字出现**的一段，不许改写、不许补全
3. 任何字段如果原文里没有，**必须输出空字符串**，禁止猜测
4. time_text 填原文的时间表达（如"明天上午9点"），time_normalized 留空，由程序计算

输出格式（只输出 JSON，不要解释）：
{"kind":"待办","action":"","time_text":"","place":"","who":"","deadline":""}

原文：{message}
```

⚠️ 注意：**归一化时间交给程序算，不要让模型算**。模型算日期是幻觉重灾区。

## 6. 建议的推进顺序（对齐你们剩余时间）

| 步骤 | 做什么 | 验收标准 | 工作量 |
| --- | --- | --- | --- |
| **1** | 把 T0+T1 搬成 ArkTS（归一化 + 分级） | 真实群里 66% 消息被标为"忽略"，界面不再出现乱码 | 0.5 天 |
| **2** | 把 T2 搬成 ArkTS（槽位 + 模板 + 时间解析） | 上面那 4 条真实消息能生成和 Python 原版一致的句子 | 1 天 |
| **3** | 事件卡片 UI（结构化字段 + 查看原话 + 转成待办） | 每张卡都能点回原话 | 0.5 天 |
| **4** | 查询 Data Augmentation Kit 是否可用；可用则替换 T3 的标题/聚合 | 事件标题质量提升 | 0.5 天 |
| **5**（可选） | 端侧小模型 + `EventValidator` 校验 | 校验不通过时能正确回退到规则 | 2 天+ |

**第 3 步做完就可以写进答辩材料了**：因为此时你已经能做到"群里一条通知，App 里出现一张带时间、地点、截止、原文出处的卡片"，这正是报告里"避免信息差"的落点。

## 7. 风险与取舍（写进报告的"创新点"和"风险"都合适）

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 模板句子太"干" | `上课；时间：…；地点：…` 不如自然语言顺口 | 这是**刻意的取舍**：提醒类应用准确 > 文采。后续可用模型润色，但**润色结果不得进入时间字段** |
| 规则覆盖不到新表达 | 新词、方言、缩写抽不到 | 槽位留空 + 原文可查，用户手动补；收集漏判样本迭代关键词表 |
| 模型幻觉 | 编造时间/地点 | **值必须是原文子串**的校验 + 校验不过回退规则 |
| 相对时间算错 | "下周三"基准搞错 | 基准用**消息时间戳**，并单测覆盖；推不出就标记 `unresolved` |
| 过度自动创建待办 | 水群被误判 | T1 保守分级 + 置信度阈值 + 用户确认（与报告"AI 只给建议，用户点确认才落库"一致） |
