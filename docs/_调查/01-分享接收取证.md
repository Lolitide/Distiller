### 1.3 `type` 字段：`share` 合法性核对（★重点核对项）

**核对结论：`share` 是合法取值，三方应用可用。**

**证据一 —— 配置文件文档的 type 取值表**（DOC:`开发指南/开发基础知识/应用配置文件/module_json5配置文件/module-configuration-file`，表内原文）：

> \| share \| 提供内容分享处理功能的[ShareExtensionAbility](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-app-ability-shareextensionability)。 \|

**证据二 —— 同表中存在易混淆的另一个取值**（原文）：

> \| sysPicker/share \| 系统分享的ExtensionAbility，三方应用配置不生效，当前配置仅在系统应用中有效。 \|

→ **`share` 与 `sysPicker/share` 是两个不同取值**；三方应用只能写 `"type": "share"`，写 `"sysPicker/share"` 不生效。

**证据三 —— BundleManager 枚举**（`SDK:@ohos.bundle.bundleManager.d.ts`）：

- **L411**：`SHARE = 16,`
- L404-410 JSDoc 原文：

> [ShareExtensionAbility]{@link @ohos.app.ability.ShareExtensionAbility:ShareExtensionAbility}: provides sharing service templates based on the UIExtensionAbility.
> `@syscap SystemCapability.BundleManager.BundleFramework.Core`
> `@since 10`

> **⚠ 不要混淆**：枚举里是**数字** `16`（这是 `bundleManager` 查询返回的枚举值），`module.json5` 里写的是**字符串** `"share"`（配置文件字面量）。二者语义对应，写法不同。
> 另注：`SDK:@ohos.app.ability.AbilityConstant.d.ts`:L302 有 `SHARE = 5,`，但那属于**另一个枚举**，与 `ExtensionAbilityType` 无关，不要引用。

### 1.4 ★完整可用的 `module.json5` 片段（官方原文，逐字）

来源：DOC:`开发指南/Share_Kit_分享服务/系统分享/目标应用处理分享内容/分享详情页处理分享内容/share-sec-panel` 第 4 步。

官方说明原文：

> 构建完分享能力Ability，需要在应用配置文件（src/main/module.json5）的[skills]配置中注册。配置actions为ohos.want.action.sendData，并且uris需穷举所有支持的数据类型。

```json5
"extensionAbilities": [
  {
    "name": "TestShareAbility",
    "srcEntry": "./ets/abilities/TestShareAbility.ts",
    "type": "share", // 支持分享数据处理
    "description": "xxx",
    "exported": true,
    "label": "$string:xx_label",
    "icon": "$media:icon",
    "skills": [
      {
        "actions": [
          "ohos.want.action.sendData"
        ],
        // scheme为预留字段，在此处不生效，配置file仅为示例
        // 目标应用在配置支持接收的数据类型时，需穷举支持的UTD，比如：支持全部图片类型，可声明：general.image
        // maxFileSupported 对于归属指定类型的文件，标识一次支持接收的最大数量。默认为0，代表不支持此类文件的分享。
        // 文件类型归属关系参考：@ohos.data.uniformTypeDescriptor (标准化数据定义与描述)
        "uris": [
          {
            "scheme": "file",
            "utd": "general.text",
            "maxFileSupported": 1
          },
          {
            "scheme": "file",
            "utd": "general.png",
            "maxFileSupported": 1
          },
          {
            "scheme": "file",
            "utd": "general.jpeg",
            "maxFileSupported": 1
          }
        ]
      }
    ]
  }
]
```

**字符串逐项取证：**

| 字段 | 值 | 依据 |
|---|---|---|
| `actions[0]` | `"ohos.want.action.sendData"` | DOC:share-sec-panel 原文「配置actions为ohos.want.action.sendData」；DOC:share-design-specification 同 |
| `uris[].scheme` | `"file"` | 官方片段原文；并注明「scheme为预留字段，在此处不生效，配置file仅为示例」 |
| `uris[].utd` | `"general.text"` / `"general.png"` / `"general.jpeg"` | 官方片段原文 |
| `uris[].maxFileSupported` | `1` | 官方片段原文 |
| `type` | `"share"` | §1.3 |
| `entities` | **官方三处片段（share-sec-panel / share-interface-description / share-design-specification）均未配置 `entities` 字段** | 三份 DOC 原文 |

**`utd` 串合法性交叉核对**（DOC:`开发指南/ArkData_方舟数据管理/标准化数据定义/UTD预置列表/uniform-data-type-list`）：

> \| general.image \| general.media \| - \| - \| 所有图片的基类型。 \|
> \| general.png \| general.image \| .png \| image/png \| PNG图片类型。 \|
> \| general.jpeg \| general.image \| .jpg, .jpeg,.jpe \| image/jpeg \| JPEG图片类型。 \|
> \| general.text \| general.object \| - \| - \| 所有文本的基类型。 \|
> \| general.plain-text \| general.text \| .txt,.text \| text/plain \| 未指定编码的文本类型，无修饰的文本。 \|
> \| general.hyperlink \| general.text \| - \| - \| 超链接类型。 \|
> \| openharmony.pixel-map \| general.image \| - \| - \| HarmonyOS系统定义的Pixel map数据类型。 \|

→ 官方片段用的三个 UTD 串**均在预置列表中真实存在**。

**字段语义**（DOC:`.../module-configuration-file`，extensionAbilities / skills / uris 标签表原文）：

> **name**：标识当前ExtensionAbility组件的名称，**不可缺省**
> **srcEntry**：标识当前ExtensionAbility组件所对应的代码路径，**不可缺省**，取值为长度不超过127字节的字符串
> **type**：标识当前ExtensionAbility组件的类型，**不可缺省**
> **exported**：标识当前ExtensionAbility组件是否可以被其他应用调用。缺省值为 **false**
> **utd**：标识与Want相匹配的标准化数据类型，具体请参考@ohos.data.uniformTypeDescriptor (标准化数据定义与描述)，**适用于分享等场景**。
> **maxFileSupported**：对于指定类型的文件，标识一次能接收或打开的最大数量，**适用于分享等场景**，需要与utd配合使用。（数据类型=整数，**缺省值为 0**）
> **extensionProcessMode**：…**对于UIExtensionAbility及其子类，支持以上三种进程模型。**（instance / type / bundle）

> ⚠ **`maxFileSupported` 缺省值为 0 的含义**：官方注释原文「默认为0，代表不支持此类文件的分享」。→ **不写这一行 = 该类型收不到分享**，这是最常见的「配了却不生效」根因。

> ⚠ **`exported` 缺省 false**：官方片段显式写 `"exported": true`，**必须写**，否则外部应用（分享面板）无法拉起。

## 2. 接收文本：取值路径与官方示例

### 2.1 取值链路（唯一官方路径）

```
ShareExtensionAbility.onSessionCreate(want, session)
        │
        ├─ systemShare.getSharedData(want) : Promise<SharedData>
        │        │
        │        └─ data.getRecords() : Array<SharedRecord>
        │                 │
        │                 └─ record.content  ← 文本 / 链接（含 App Linking）走这里
        │                    record.title    ← 标题（文本类缺省时=文本内容本身）
        │
        └─ session.loadContent('pages/Index')   ← 加载分享详情页 UI
```

**★ 关键否定结论**：**不存在** `want.parameters` 的分享数据 key，`UIExtensionContentSession` 上**也没有**任何取数据的方法。

- `SDK:@hms.collaboration.systemShare.d.ts` 全文（901 行）grep `parameters|want\.` **仅命中 3 处注释**（L281、L708、L875），**无任何 key 常量**。
- `SDK:@ohos.app.ability.UIExtensionContentSession.d.ts` 全部成员清单中**无 getSharedData / 数据读取方法**（详见 §5.2）。

> 引用块（DOC:share-system-share，`getSharedData` 接口说明原文）
> 通过目标应用获取的want信息，从中解析出分享数据，使用Promise异步回调。

> 引用块（DOC:share-system-share，`SharedRecord.content` 字段说明原文）
> 数据记录内容。链接（包含App Linking）、文本类型的内容通过该字段传递。
> **说明：** content和uri二者至少有一个不为空。

> 引用块（DOC:share-system-share，`SharedRecord.title` 字段说明原文）
> 如果是文本、链接等内容，建议填入title标识其标题。缺省时，若分享内容为文本类型，则文本内容作为title字段；若分享内容为文件类型，则文件名作为title字段。

### 2.2 官方示例代码原文（扩展形态）

DOC:`开发指南/Share_Kit_分享服务/系统分享/目标应用处理分享内容/分享详情页处理分享内容/share-sec-panel` 第 1、2 步原文：

export default class TestShareAbility extends ShareExtensionAbility {
  onSessionCreate(want: Want, session: UIExtensionContentSession) {
    systemShare.getSharedData(want)
      .then((data: systemShare.SharedData) => {
        data.getRecords().forEach((record: systemShare.SharedRecord) => {

      });

}

**★ 从后台转前台必须用 `onNewWant`**（DOC:`FAQ/内容分享服务_Share_Kit/如何获取到其他应用分享的内容/faqs-share-3`）：

> **问题现象**：在 `EntryAbility` 的 `onForeground` 中调 `systemShare.getSharedData` 拿不到分享内容。
>
> **解决方案原文**：onNewWant和onForeground都具备从后台转前台触发的特性。但是onForeground没有返回最新的want，而onNewWant方法能够获取新的want，这个want里有其他应用分享的内容。

FAQ 给出的正确写法原文：

```ts
onNewWant(want: Want) {
  systemShare.getSharedData(want).then((data) => {
    data.getRecords().forEach(() => {
      // ...
      this.context.eventHub.emit("ShareContent", { msg: "应用进入前台" });
    });
  })
  // ...
}
```

### 3.1 图片以什么形式传来？→ **`uri`（string）**

### 3.3 ★`uri` → `PixelMap` 的取证链路（跨文档推导，非官方 Share Kit 示例）

要喂给 OCR，必须自己把 uri 解码成 `PixelMap`。以下是**每一步都有官方依据**、但**没有一份官方文档把它们串在 Share Kit 场景下**的链路：

**Step 1 — `uri` → `fd`（官方 FAQ 明确支持）**

DOC:`FAQ/本地数据和文件/本地文件管理/文件操作API的常见参数类型转换以及场景有哪些/faqs-local-file-manager-56`

> 引用块（背景知识原文）
> `fs.openSync`：以同步方法打开文件或目录。**支持使用uri打开文件。**

该 FAQ 的「参数转换」表原文两行：

| 序号 | 参数转换 | 常见业务场景 | 转换方式 |
| :-- | :-- | :-- | :-- |
| 5 | `uri -> fd` | 应用打开文件管理器操作文本文件进行读写 | `let file = fs.openSync(uri); let fd = file.fd;` |
| 6 | `uri -> sandboxPath` | 应用打开文件管理器操作文本文件进行读写 | `let file = fs.openSync(uri); let sandboxPath = file.path;` |

同一 FAQ 的「常见FAQ」原文：

> **Q**：通过documentViewPicker.select选择文件，将用户选择的文件路径，即回调参数作为参数值，调用@ohos.file.fs的fs.statSync为什么报错，fs.openSync就没报错？
> **A**：documentViewPicker.select返回的是用户选择文件的uri数组，**fs.openSync要求传入沙箱路径或者文件uri参数所以没报错**；fs.statSync要求传入沙箱路径或者文件fd值，参数类型不匹配，所以报错了。

> ⚠ **语境提示**：该 FAQ 的场景是 **DocumentViewPicker**，不是 Share Kit 接收侧。属**跨文档推导**，非官方 Share Kit 示例。

**Step 2 — `fd` → `ImageSource` → `PixelMap`（Image Kit 官方原文）**

DOC:`开发指南/Image_Kit_图片处理服务/图片开发指导_ArkTS/图片解码/使用ImageSource完成图片解码/image-decoding`

> 引用块（创建 ImageSource，方法二原文）
> **方法二：通过文件描述符fd创建ImageSource。**
> `const imageSource: image.ImageSource = image.createImageSource(fd);`

SDK 侧签名依据（`SDK:@ohos.multimedia.image.d.ts`）：

| 行号 | 签名 |
|---|---|
| L4182 | `function createImageSource(uri: string): ImageSource;` |
| **L4220** | **`function createImageSource(fd: number): ImageSource;`** |
| L4258 | `function createImageSource(buf: ArrayBuffer): ImageSource;` |
| L11816 | `createPixelMap(options?: DecodingOptions): Promise<PixelMap>;` |

> ⚠ **重要约束**（`SDK:@ohos.multimedia.image.d.ts`:L4165-4175，`createImageSource(uri)` 的 JSDoc 原文）
> Creates an ImageSource instance based on a given URI.
> `@param { string } uri - Image path.` **Currently, only the application sandbox path is supported.**

→ 即 **`createImageSource(uri)` 只接受沙箱路径**。而分享来的 `record.uri` 是**应用文件 URI / 用户文件 URI**，**不能直接丢给 `createImageSource(uri)`**，必须先 `fs.openSync(uri)` 拿 `fd`（或先转 sandboxPath）。

**这就是为什么必须走 `uri → fd` 这一步。**

**Step 3 — 释放**（`SDK:@ohos.multimedia.image.d.ts`:L11800-11806 NOTE 原文）

> This method is not thread-safe and does not support concurrent calls on the same ImageSource instance.
> Images occupy a large amount of memory. When you finish using a PixelMap instance, call release to free the memory promptly.

**《知了》OCR 取值代码（工程推导，非官方原文）**：

```ts
import { image } from '@kit.ImageKit';
import { fileIo as fs } from '@kit.CoreFileKit';

async function uriToPixelMap(uri: string): Promise<image.PixelMap | undefined> {
  let file: fs.File | undefined;
  let imageSource: image.ImageSource | undefined;
  try {
    file = fs.openSync(uri, fs.OpenMode.READ_ONLY);      // 官方 FAQ「uri -> fd」
    imageSource = image.createImageSource(file.fd);      // Image Kit 官方「方法二」
    return await imageSource.createPixelMap();
  } catch (e) {
    return undefined;
  } finally {
    await imageSource?.release();
    if (file) { fs.closeSync(file); }                    // SDK @ohos.file.fs.d.ts:L416
  }
}
```

**URI 形态参考**（DOC:`API参考/Core_File_Kit_文件基础服务/ArkTS_API/ohos_file_fileuri_文件URI_/js-apis-file-fileuri`，`FileUri.constructor` 参数说明原文）：

> URI类型：
> - 应用沙箱URI：`file://<bundleName>/<sandboxPath>`
> - 公共目录文件类URI：`file://docs/storage/Users/currentUser/<publicPath>`
> - 公共目录媒体类URI：`file://media/<mediaType>/IMG_DATETIME_ID/<displayName>`

> ⚠ **风险提示（工程判断，非官方结论）**：QQ / 微信分享截图给《知了》时，`record.uri` 常为 `file://media/...` 形式的**公共目录媒体类 URI**。`fs.openSync` 对三类 URI 的**权限要求官方未逐一说明**。
>
> **未取证**：`fs.openSync` 对 `file://media/...` 媒体类 URI 的权限模型（是否需要 `ohos.permission.READ_IMAGEVIDEO` 等）。本地文档库中 `faqs-local-file-manager-56` 未覆盖该场景。

> 引用块（SDK:`@ohos.app.ability.UIExtensionAbility.d.ts`:L103-110，**逐字原文**）

### 6.2 为什么《知了》必须用「等待调试」

分享详情页由**系统分享面板**（而非 DevEco 的运行按钮）拉起，属于「外部事件冷启动扩展进程」，普通 Debug 运行抓不到。

**可迁移的官方依据**：DOC:`FAQ/程序框架/卡片开发_Form/如何对服务卡片进行调试/faqs-form-15`（FormExtensionAbility，同属 ExtensionAbility 进程模型）

> 引用块（问题现象原文）
> 因为卡片事件是从应用的form进程发起，正常情况下使用debug模式运行后会导致走不到断点；另外卡片交互冷启动应用的场景也无法正常使用debug模式进行断点调试。

> 引用块（背景知识原文）
> 开发者可以通过将某个应用设置为"等待调试模式"，然后当开发者需要对应用进行调试时，拉起应用即可快速进入调试。

**方式一步骤原文**：

> 1. 设备选择框选设备，单击 **Run-》Attach to Process by Name**。
> 2. 选择调试工程并将类型选为 **ArkTS**，单击 **Attach**，即可将该应用设置为"等待调试模式"。
> 3. 确认 DevEco Studio 底部出现 **Waiting for debugger** 进度条后，可以开始调试。
> 4. 在需要调试的代码行左侧边线设置断点。
> 5. 操作应用，运行到代码处会停住并高亮。

### 6.3 `Attach Debugger to Process` 官方约束

DOC:`开发指南/应用调试/代码调试/ArkTS代码调试/attach启动调试/ide-debug-arkts-attach`

> 引用块（与 Debug 的区别）
> Attach Debugger和Debug的区别在于，Attach Debugger to Process可以先运行应用/元服务，然后再启动调试，或者直接启动设备上已安装的应用/元服务进行调试；而Debug是直接运行应用/元服务后立即启动调试。

> 引用块（前提条件）
> 当前设备上被attach的应用代码和本地代码一致，且已提前进行构建生成必要的sourceMap文件。

> 引用块（使用约束）
> attach不支持的场景：
> * 本地无源码。
> * bundleName不匹配，将出现提示"The selected process does not match the bundlename of the current project!"，但不阻塞调试过程。

**操作步骤原文**：工具栏选设备 → 单击 **Attach Debugger to Process** → 选择要调试的应用进程（**若应用bundleName与当前工程不一致，则需勾选 Show all process**）→ 选择调试配置 → 选择 Debug type → OK。

**★签名约束原文**：

> 正常情况下，attach调试仅支持debug签名的应用，从DevEco Studio 6.0.2 Beta1版本开始，PC/2in1上的应用，如果使用了release签名并且配置了ohos.permission.kernel.ALLOW_DEBUG权限，也支持被attach调试。

→ **手机（phone）上无论如何都必须是 debug 签名**才能 attach。

### 6.4 推荐调试流程（《知了》专用，工程建议）

1. `devecocli build` 构建 debug 包 → `devecocli run` 安装到真机。
2. DevEco Studio → **Attach Debugger to Process** → 勾选 **Show all process** → 选中《知了》进程 → Debug type 选 **ArkTS** → OK，看到 **Waiting for debugger** 进度条。
3. 在 `ZhiliaooShareAbility.onSessionCreate` / `onDestroy` / `uriToPixelMap` 首行下断点。
4. 切到 QQ / 微信，长按消息或截图 → 分享 → 选择《知了》。
5. 断点命中后逐帧看 `want` 与 `record`。
6. 辅助日志：`devecocli log --level E --bundle-name <包名> --follow`；崩溃：`devecocli log --crash`。

## 7. 能否不写扩展、只用 `UIAbility` 接收纯文本

**结论：可以，官方明确支持，且是最省事的路径。**

### 7.1 官方直接依据

**依据一 —— 官方专篇**：DOC:`开发指南/Share_Kit_分享服务/系统分享/目标应用处理分享内容/应用内处理分享内容/share-interface-description`（见 §1.1 引用块 B）。目录名就叫「**应用内**处理分享内容」，与「分享详情页处理分享内容」并列。

**依据二 —— 设计规范文档把两者并列**：DOC:`开发指南/Share_Kit_分享服务/系统分享/目标应用处理分享内容/目标应用设计规范/share-design-specification`

> 引用块（原文）
> 当应用实现了用于接收分享内容的[UIAbility]或者[UIExtensionAbility]后，可在配置文件（src/main/module.json5）的[skills]配置中注册。并配置actions为ohos.want.action.sendData。
> 当分享内容类型为应用所支持的类型时，应用图标将出现在分享面板的分享方式区内。
> **应用可以针对不同的ability，设置不同的名称和图标。**

该文档给出的示例**同时**包含 `abilities`（UIAbility）与 `extensionAbilities`（`type: "share"`）两段，且两段的 `actions` / `uris` **完全一致**：

```json5
"abilities": [
  {
    "name": "TestUIAbility",
    "srcEntry": "./ets/entryability/TestUIAbility.ets",
    "label": "$string:EntryAbility_label", // ability名称
    "icon": "$media:layered_image", // ability图标
    "description": "$string:EntryAbility_desc",
    "startWindowIcon": "$media:startIcon",
    "startWindowBackground": "$color:start_window_background",
    "exported": true,
    "skills": [
      {
        "actions": [ "ohos.want.action.sendData" ],
        "uris": [
          { "scheme": "file", "utd": "general.text", "maxFileSupported": 1 }
        ]
      }
    ]
  }
],
"extensionAbilities": [
  {
    "name": "TestShareAbility",
    "srcEntry": "./ets/abilities/TestShareAbility.ts",
    "type": "share", // 支持分享数据处理
    "exported": true,
    "label": "$string:xx_label", // ability名称
    "icon": "$media:icon", // ability图标
    "description": "$string:TestShareAbility_desc",
    "skills": [
      {
        "actions": [ "ohos.want.action.sendData" ],
        "uris": [
          { "scheme": "file", "utd": "general.text", "maxFileSupported": 1 }
        ]
      }
    ]
  }
]
```

**依据三 —— 两种形态共用同一套取值 API**：`systemShare.getSharedData(want)` 在两篇指南的示例里**写法完全相同**（对比 §2.2 与 §2.3）。

### 7.2 取舍对照表（官方依据 + 工程判断）

| 维度 | UIAbility（应用内处理） | ShareExtensionAbility（分享详情页） | 依据 |
|---|---|---|---|
| skills 配置 | `actions: ["ohos.want.action.sendData"]` + `uris[].utd` | **完全相同的配置**，只是放在 `extensionAbilities` 里 | DOC:share-design-specification |

### 7.3 对《知了》的建议（工程判断，非官方原文）

- **纯文本接收（QQ 消息、链接）**：**用 UIAbility 即可**，官方通道完备（`onCreate` + `onNewWant` + `getSharedData`），无需扩展，可复用现有 MVVM 分层与路由，改造成本最低。
- **需要「留在分享面板里快速确认」的体验**：才上 `ShareExtensionAbility`。
- 两者**可以并存**（`share-design-specification` 示例即同时给出），但会造成分享面板出现**两个《知了》入口** —— 该文档原文承认「应用可以针对不同的ability，设置不同的名称和图标」，即官方允许此形态。
- ⚠ 若用 UIAbility 接收，**必须**同时在 `onNewWant` 里处理（`faqs-share-3` 明文：`onForeground` 拿不到新 want）。

## 10. 《知了》主链路落地建议（工程判断，非官方结论）

```
QQ / 微信 → 分享面板 → 【路径 A：UIAbility】 → onNewWant(want)
                      → 【路径 B：ShareExtensionAbility】 → onSessionCreate(want, session)
                                ↓
                    systemShare.getSharedData(want)
                                ↓
                        data.getRecords()
                                ↓
        ┌───────────────────────┴───────────────────────┐
   record.content 非空                              record.uri 非空
        │                                               │
   纯文本/链接 → 直接进解析确认页            fs.openSync(uri).fd
        │                                               │
        │                                  image.createImageSource(fd)
        │                                               │
        │                                  imageSource.createPixelMap()
        │                                               │
        │                                    → OCR → 进解析确认页
        └───────────────────┬───────────────────────────┘
                            ↓
                    onDestroy 落库必须 async/await
```

**最小改造清单**
1. `entry/src/main/module.json5`：按 §1.6 加 `extensionAbilities`（若走路径 B）或按 §7 给已有 `EntryAbility` 加 `skills`（若走路径 A）。
2. 新增 `ZhiliaooShareAbility.ets`，`onSessionCreate` 里 `getSharedData` → 分流 content / uri。
3. 新增 `ShareParser`（Model 层）：`SharedRecord[]` → 领域对象。
4. 新增 `uriToPixelMap()`（§3.3），接 OCR。
5. `onDestroy` 严格写成 `async onDestroy(): Promise<void>` + `await`。
6. 真机验证：QQ / 微信各分享一次文本、一次截图、一次链接、一次多图，覆盖 §8 的 U3/U4/U10 三个未取证风险点。
