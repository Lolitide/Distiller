### 2.3 时间实体的 `jsonObject` 结构

来源：`API参考/Natural_Language_Kit_自然语言理解服务/ArkTS_API/jsonObject_实体的其他字段/natural-language-json-object-api`

结构：`{ "time": [ { ...字段... } ] }`，键为 `time`，值为数组。

| 字段 | 类型 | 说明（原文要点） |
| :-- | :-- | :-- |
| `repeat` | string | 周期。**替代了 `rrule`** |
| `rrule` | string | 周期标识，原文「不一定准确，具体以 repeat 为准（参考数据，不建议使用）」 |
| `start` | string | 开始时间。示例：`2021-08-28T08:00:00`（日期+精确时间）/ `2021-08-28TM`（日期+模糊时间）/ `2021-08-28`（日期）/ `T08:00:00`（周期时间，无明确日期，如「每天8点」）/ `TM`（周期时间，如「每天早上」） |
| `suggestStart` | string | 具体开始时间。原文「大多数情况和 start 一样，表面上是单个时间，但实际是时间段的时候有区别」。示例：「1月」→ `start 2021-01`、`end 2021-01`、`suggestStart 2021-01-01`、`suggestEnd 2021-01-31` |

| `maxSection` / `minSection` | string | 最大/最小时间粒度。`P` 精确时间、`M` 早晨、`F` 上午、`N` 中午、`A` 下午、`L` 傍晚、`E` 晚上、`W` 凌晨 |
| `isContainFuzzyTime` | boolean | 是否包含模糊时间，默认 false |
| `containFuzzySection` | string | 模糊时间粒度，不包含时默认 `D` |
| `inferType` | string | 时间推理类型枚举 |
| `rangeDecoration` | string | 范围描述 |
| `rangeText` | string | 带范围描述的文本，如「每周四晚上10点」 |

### 2.4 地点实体的 `jsonObject`

键为 `location`，值为数组。顶层含 `type`（首层核心地点的实际类型，必选）、`coreLocation`（必选）、`adornLocation`（修饰核心地点的成分，如「小肥羊旁边的」）、`isAbstract`（0 非抽象 / 1 与意图相关的抽象地点）。`coreLocation` 内含 `oriText`（必选）、`value`（原文去除修饰词后的地点）、`province` / `city` / `county` / `district` / `subDistrict` / `town` / `village` / `subVillage` / `region` / `road` / `default` / `location`。来源同 §2.3。

### 6.1 `Event` 的字段（日历路径写日程时要用的全部内容）

来源 `@ohos.calendarManager.d.ts:586-715`（`interface Event`）+ `:881`（`enum EventType`）+ `:907-1023`（`interface RecurrenceRule`）+ `:805`（`interface Location`）。

### 7.1 接收侧实现（官方原文）

```typescript
import { Want, ShareExtensionAbility, UIExtensionContentSession } from '@kit.AbilityKit';
import { systemShare } from '@kit.ShareKit';
import { BusinessError } from '@kit.BasicServicesKit';

export default class TestShareAbility extends ShareExtensionAbility {
  onSessionCreate(want: Want, session: UIExtensionContentSession) {
    systemShare.getSharedData(want)
      .then((data: systemShare.SharedData) => {
        data.getRecords().forEach((record: systemShare.SharedRecord) => {
          // 处理分享数据
        });
        session.loadContent('pages/Index');
      })
      .catch((error: BusinessError) => {
        console.error(`Failed to getSharedData. Code: ${error.code}, message: ${error.message}`);
        session.terminateSelf();
      });
  }
}
```

要点：

- **纯文本记录走 `record.content`**；图片等文件记录走 `record.uri`。
- `getSharedData()` **必须在 `onSessionCreate` 里同步发起**（`want` 只在那一帧有效）；因为 `onDestroy()` 里的异步写库可能失败（`UIExtensionAbility.d.ts:115`），**落盘要在 `onSessionCreate` 阶段完成**。
- 失败处理用 `session.terminateSelf()` 退出，不要留一个空白的分享详情页。

## 8. 通知：Notification Kit

### 8.1 请求通知授权（`开发指南/Notification_Kit_用户通知服务/请求通知授权/notification-enable`）

**原文要点**：「应用需要获取用户授权才能发送通知。在通知发布前调用 `requestEnableNotification()` 接口，弹窗让用户选择是否允许发送通知。**当用户拒绝授权后，将无法通过该接口再次拉起弹窗。** 如果应用需要向用户再次申请通知授权，则可以使用 `openNotificationSettingsWithResult` 接口拉起通知管理半模态弹窗。」

| 接口 | 描述 | 来源 |
| :-- | :-- | :-- |
| `isNotificationEnabled(): Promise<boolean>` | 查询通知是否授权 | 文档表 1；`@ohos.notificationManager.d.ts:371`；同步版 `isNotificationEnabledSync(): boolean` 在 `:383` |
| `requestEnableNotification(context: UIAbilityContext): Promise<void>` | 请求发送通知的许可，**第一次调用会弹窗** | 文档表 1；`@ohos.notificationManager.d.ts:633`；**无参重载 `:602`/`:548` 已废弃** |
| `openNotificationSettingsWithResult(context: UIAbilityContext): Promise<NotificationSetting>` | 拉起通知管理半模态弹窗，**用户设置完成后返回设置结果**（含通知授权、锁屏、横幅、角标、铃声、振动开关） | 文档表 1 |

**关键错误码**：`requestEnableNotification` 返回 **`1600004` 即用户拒绝授权**（文档原文「若返回的错误码为1600004，即为拒绝授权」）。

**官方调用模式（文档原文）**：先 `isNotificationEnabled()` 判断，**只有未授权时才调 `requestEnableNotification()`**；catch 里按 `1600004` 区分「用户拒绝」与「其它失败」；用户拒绝过的场景改用 `openNotificationSettingsWithResult()` 再申请。

> [!important] 对「知了」的直接后果
> 提醒是这个应用的全部价值，而**用户点一次「不允许」就永久堵死了自动弹窗**。因此第 2 周做 W2-T06 时必须：
> 1. **不要在冷启动就弹窗**——先在首次启动引导页里说明「知了要在截止时间前提醒你，需要通知权限」，用户点了「开启提醒」再调 `requestEnableNotification`；
> 2. catch 到 `1600004` 时，提示语必须是**可执行的下一步**（照报告 §6 的要求）：「已关闭通知，知了无法提醒你。点这里去设置里打开」，点击调 `openNotificationSettingsWithResult(context)`；
> 3. 拒绝后**重试路径靠 `openNotificationSettingsWithResult`**，不是反复调 `requestEnableNotification`。

### 11.1 云调试的两条硬约束与一条省时技巧（本地 FAQ 已读到正文）

来源：`FAQ/应用调试/云调试应用安装失败常见问题排查与解决方案/faqs-app-debugging-80`（七个问题 + 方案，本机 `devecocli docs read` 可直接读全文）；辅助来源 `FAQ/应用调试/云调试应用期间出现黑屏如何处理/faqs-app-debugging-79`。

| 项 | 原文要点 | 对「知了」的直接含义 |
| :-- | :-- | :-- |
| **硬约束 1：设备 API 必须够高** | 问题二现象「应用安装报『应用不匹配当前系统版本，请选择其他系统版本设备』」；方案原文「查看工程目录 `build-profile.json5` 文件的 `compatibleSdkVersion` 字段，**标识应用/元服务运行所需兼容的最低 SDK 版本**」；问题六方案「『该应用类型不适用于所选设备』……也可能是**因为应用的版本过高**，导致云调试的真机设备不能安装……**修改该字段版本让其小于或等于云调试真机版本**」 | 我们的 `compatibleSdkVersion` 是 `6.0.2(22)`（§1 工程脚手架事实），**云调试时只能筛 API ≥ 22 的设备**，否则装不上 |
| **硬约束 2：包格式** | 问题三方案原文「**HarmonyOS NEXT 的设备只能上传 HAP 和 APP 包**」；问题四现象「云调试安装 release 包提示安装失败，报 `error: failed to install bundle. code:9568297 error: failed to install because of an older sdk version in the device`」 | 我们 `devecocli build` 产出 HAP，格式没问题；但**必须是签名后的包**（默认产物 `entry-default-unsigned.hap` 装不进去，见 §1.1 的签名 WARN）→ 走云调试就得把 W4-T03 的签名提前 |
| **省时技巧** | 问题五现象「云调试上传软件包耗时过长，**浪费免费体验时长**」；方案「在**云调试-我的信息-应用**中，**提前上传**需要调试的应用。选择调试设备，应用中显示已上传的应用，点击安装即可」 | 进设备会话前先把包传到「我的信息 → 应用」，别把上传时间花在计费/免费时长里 |
| **其它已确证细节** | 问题一：`BusinessError 17700101: Bundle manager service is excepted.`（查文件完整性与文件名特殊符号）；问题七：**云调试已支持多 hap 包安装**（多 product 的 app 包不能直接装）；问题五截图路径为「云调试-我的信息-应用」 | 只有 entry 一个模块时不会碰到问题七 |
| **画面是截屏流** | `faqs-app-debugging-79` 原文出现「**云真机**」一词；问题一现象「云真机设备勾选隐私政策后，进入登录页面时，云真机一直黑屏」；原因「由于**应用自身登录页设置了防截屏**，此时云真机会显示黑屏」；两条出路：重新打包关闭防截屏开关，或点「**获取控件树**」按钮启动辅助控件绘制功能 | 我们不做登录，但**第 4 周若给分享进来的图片加防截屏/隐私保护，云调试上会黑屏**，届时用「获取控件树」绕过 |
| **自建远程真机（不是我们的选项）** | `faqs-app-debugging-66` 给出的工具 `https://gitcode.com/OpenHarmonyToolkitsPlaza/HOScrcpy`（HarmonyOS NEXT 下基于视频流的投屏，「帧率基本持平真机帧率」） | 四周课程项目不值得自建，仅记录为**华为提供云调试**这一事实的第二处官方旁证 |

> [!important] 一条排期结论

### 12.2 官方定位、计费与模拟器支持

来源：`开发指南/Cloud_Foundation_Kit_云开发服务/Cloud_Foundation_Kit简介/cloudfoundation-introduction`。

- **官方定位原文**：「应用运行所需的服务器和环境均可由云端平台提供，开发者只需关注业务的业务逻辑，而无需关心基础设施」。
- **优势原文**：低运维成本 / 弹性伸缩、**按量计费** / **「支持数据全密态加密，支持 APP、用户和服务三重认证，提供基于角色的权限管理机制」** / 端云一体化开发（DevEco 内统一技术栈编码、调试、编译、部署）。
- **计费原文**：「云函数、云数据库、云存储服务提供了**免费额度**以供试用」——**具体额度数字属于 AGC 侧文档，不在本地库**。
- **支持设备**：云函数 / 云数据库 / 云存储 = Phone、Tablet、PC/2in1、Wearable、TV；预加载 = 前三者。
- **模拟器**：「从 6.0.0(20) Beta5 版本开始，本 Kit 支持模拟器」，且**「仅云函数、云数据库、云存储服务支持模拟器」**（详见 `cloudfoundation-emulator`）。→ 本机两个模拟器（6.1.1(24) / 7.0.0 Beta2）**都满足**。
- **签名**：「关联注册应用进行自动签名」（DevEco 6.0.0 Beta5 及以上）与「手动签名」两种。

### 12.3 四种触发器与「端上拉云」的官方做法

来源：`FAQ/云开发服务_Cloud_Foundation_Kit/云函数各触发器的场景使用/faqs-cloudfoundation-7`、`.../云数据库端云同步方案/faqs-cloudfoundation-12`。

| 触发器 | 官方原文要点 |
| :-- | :-- |
| **HTTP 触发器** | 「为云函数完成 HTTP 触发器配置后会生成触发 URL，在向该 URL 发起 HTTP 请求时将触发云函数」；官方给的场景是**端侧直接调用**（应用通过 `cloudfunction.call` 调用）与 Server SDK |
| 云数据库触发器 | 「当云数据库发生插入、更新、删除、清空数据等变更操作时触发云函数」 |
| 认证服务触发器 | 认证相关事件触发 |
| 云存储触发器 | 存储对象变更触发 |

**端上拉云不需要「实时监听」**：官方方案原文是「Cloud Foundation Kit 的云数据库如果要实现**监听云侧数据变化**，需要结合云函数的云数据库触发器一起使用」——步骤为①建对象类型与存储区、引入对象类型文件、初始化数据库访问 ②建函数时触发器类型选「云数据库触发器」，事件类型选 `onWrite` ③函数内处理触发器 event。**我们要做的是「用户主动拉取」，用 `cloudDatabase` 直接查询即可，比监听简单一档。**

### 12.4 未取证（且没有替代方案）：HTTP 触发器能否被第三方平台从公网 POST

> [!warning] 这是本链路唯一的空白，必须用实验补，不能用文档补
> 官方文档只描述了两种 HTTP 触发器用法：**端侧 `cloudfunction.call`** 与 **Server SDK**。**没有任何一处声明它是通用的公网 Webhook 接收端点。** 因此「QQ 侧的 WebHook 能不能直接 POST 到 AGC 云函数」**在本次取证范围内没有任何官方依据**。
>
> 处理方式（已写进指南 §6.2 与 W1-T11）：**主路径改成不依赖公网入口的 WebSocket**，把这个未知项降级为「半天 spike，通了就多一条备选，不通就直接放弃」。
