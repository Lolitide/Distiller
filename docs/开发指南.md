## 0. 一句话结论

**这个项目能不能做出来，第 1 周就定了；而不取决于写代码的速度。**

第 1 周必须回答三个问题，任何一个为「否」都要立刻改设计，不能拖到第 3 周：

1. **代理提醒在这台手机上能不能用？** —— 管控机制真实存在，且我们**还没申请**。申请审批要 **8 个工作日**（约 1.5 周），走日历兜底要额外开发量。**这是全项目唯一的硬阻塞项**（依据：`开发指南/Background_Tasks_Kit_后台任务开发服务/代理提醒_ArkTS/agent-powered-reminder` 约束与限制章节原文）。**所以 W1-T06 必须在第 1 周的前两天就提交，并写成有日期的记录。**
2. **只有一台真机，AI 能力怎么验？** —— 图片文字识别**不支持模拟器**，实体抽取**不支持模拟器**；模拟器上静态 import 还会让应用起不来。团队现有的真机只有**杜俊廷那一台 HarmonyOS 6.0.2(22)**（本机 `devecocli device list` 仍返回 `No active devices`，因为手机没连在这台开发机上，这是正常的）。一台设备意味着**所有依赖真机的验证必须串行、集中一次做完**（见 §3.1 与 §7.2），需要第二路验证时用 **AGC 云调试**（官方确实提供，见 §7.2 与 `docs/99-附录-取证台账.md` §11.1）。
3. **无障碍读屏这条通道值不值得做？** —— **不值得，而且做不了**。官方文档明文「系统不再开放相关能力」，API 12 起相关接口全部废弃；华为消费者侧口径是「升级后第三方读屏软件不支持屏幕朗读」；应用审核指南 2.10 还把「开启辅助功能」列为禁止诱导项。**这条 P2 通道直接砍掉**（依据见 `_调查/02-无障碍读屏取证.md`）。
4. **机器人转发的数据要经过云服务器中转，这件事怎么落地？** —— 华为**不提供**现成的「QQ 机器人接入」服务，但提供了**云函数 + 云数据库（Cloud Foundation Kit）**，正好够做中继，不必自己租服务器。真正的未知只有一条：**AGC 云函数的 HTTP 触发器能不能被 QQ 侧从公网直接调用**。这一条要在第 1 周用 curl 花半天验掉（见 §6 与 W1-T11）。

### 2.3 三个已知的坑（踩过一次就别再踩）

1. **模拟器上静态 import 不支持的 Kit 会直接闪退。** 报错形如 `resolveBufferCallback get hsp buffer failed，hsp path:/data/storage/el1/bundle/com.huawei.hmos.{KitName}.kit`。官方规避手段是**动态引入 Kit**（`import()` 而非顶部 `import`）。→ 所有 AI 能力的调用点统一包一层 `service/ai/`，在那一层做动态引入与降级。
2. **`repeat` 取代了 `rrule`。** 从 5.0.1.130 起 `rrule` 不再输出，周期判断必须用 `repeat`。我们的解析结果如果落了 `rrule` 字段，会在新系统上静默失效。→ 数据模型只存 `repeat`，并保留原始 `jsonObject` 原文以便回溯。
3. **`notificationId` 相同的提醒会互相覆盖。** → 提醒 id 必须与任务 id 建立确定性映射，不能随手取随机数。

### W1-T09 可行性验证 C：分享接收被拉起

- **目标**：回答「用户在 QQ 里分享一条消息给知了，我们能不能拿到这条文本」，并在验证过程中**定下接收形态**。
- **交付物**：可运行的分享接收实现 + 一页验证记录（含形态选择结论）。
- **依赖**：W1-T02、真机。
- **先说一个会省下一天的决定**：官方**两条**接收形态都合法，且**取值 API 与 `skills` 配置完全一致**，区别只在承载者与界面形态：

  | 维度 | UIAbility（应用内处理） | `ShareExtensionAbility`（分享详情页） |
  | :-- | :-- | :-- |
  | 配置位置 | `abilities[].skills` | `extensionAbilities[]`，`"type": "share"` |
  | `skills.actions` / `uris` | `"ohos.want.action.sendData"` + 穷举 UTD | **完全相同** |
  | 取值 API | `systemShare.getSharedData(want)`（同一个） | 同一个 |
  | 拿 want 的入口 | `onCreate` **或 `onNewWant`** | `onSessionCreate`（唯一入口） |
  | 界面形态 | 全屏进入应用 | **内嵌在分享面板里的详情页** |
  | 能否退回分享面板 | 否 | 可以（另有官方专篇） |
  | 对知了的意义 | **直接进「解析确认页」，复用 W2-T03 已有的页面与 MVVM 分层，改造成本最低** | 体验更轻，但要为它单独做一页确认界面，等于把「解析确认」写两遍 |

  **建议：W1-T09 用 UIAbility 形态验证并据此定案。** 理由是本项目的确认界面（W2-T03）本来就要做到「字段可编辑 + 原文对照 + 失败重试」，再做一套内嵌详情页是纯重复劳动；且第 2 周时间要留给解析与提醒。**若验证中发现 UIAbility 形态拿不到内容，再改 `ShareExtensionAbility`** —— 因为取值 API 相同，切换只动 `module.json5` 与承载类，不动业务代码。
  > 依据：`_调查/01-分享接收取证.md` §7（官方 `share-interface-description` 与 `share-design-specification` 两篇都并列给出两种形态的示例，`actions`/`uris` 一字不差）。
  > 代价（要主动接受）：用 UIAbility 形态**用户不能退回分享面板**，分享后落到知了应用内。这符合本项目「分享进来就开始确认」的流程。

  - 基类（若最终选扩展形态）：`ShareExtensionAbility`（`@since 10`，继承 `UIExtensionAbility`）。
  - 取值：`systemShare.getSharedData(want)` → `data.getRecords()` → 文本取 `record.content`，图片取 `record.uri`。
  - 注册：`skills.actions` 为 `"ohos.want.action.sendData"`，`uris` **穷举 UTD**（`general.text` / `general.png` / `general.jpeg`，或全部图片用 `general.image`），每条给 `maxFileSupported: 1`（**默认 0 表示不支持**）；三份官方文档**都没有配置 `entities` 字段**，我们也不要加。
  - 约束：一个 `SharedData` ≤ 500 条记录、总大小 ≤ 200 KB；缩略图 < 32 KB；`scheme` 是预留字段不生效（写成 `"scheme": "file"` 只是惯性，不表示限制）。
  - **调试方式（这条不做会白等一整天）**：分享是由**系统分享面板**拉起的，`devecocli run` 与普通 Debug 抓不到断点。官方手段是 **Attach Debugger to Process → 勾选 Show all process → 选中知了进程 → Debug type 选 ArkTS → 看到 `Waiting for debugger` 进度条 → 再去 QQ 里分享**。官方原文还写明 **attach 仅支持 debug 签名的应用**（手机上无例外）。
- **验收标准**：
  - [ ] 从 QQ 分享一条纯文本，知了被拉起且取到文本原文（`record.content`）
  - [ ] 从相册分享一张截图，能取到 `record.uri`（图片对应的文件 URI）
  - [ ] **记录 `want.flags` 里是否带 `FLAG_AUTH_READ_URI_PERMISSION`**——没这个标志位，第 2 周 W2-T08 拿到的 URI 可能读不出内容（**本条必须和第 2 周做图片识别的人一起确认**）
  - [ ] 记录实际取到的 `record.label` 与 `record.utd` 值（这是后面做类型分流的依据）
  - [ ] 若选 UIAbility 形态：**后台转前台时能从 `onNewWant` 拿到 want**（官方 FAQ 明文：`onForeground` 拿不到新 want）
  - [ ] 若选扩展形态：原文在 `onSessionCreate` 阶段完成落盘（不依赖 `onDestroy`）
  - [ ] 多选分享时记录 `getRecords()` 的实际条数与顺序
  - [ ] **连续分享两次（上一次还没处理完）时不崩**，并记录第二次是被拒绝还是新开一次
  - [ ] 失败路径不留空白页（扩展形态走 `session.terminateSelf()`）
  - [ ] **明确写下接收形态的结论：UIAbility / `ShareExtensionAbility`，以及为什么**
  - [ ] 结论明确写成「通过 / 不通过 / 未验证」
- **风险**：不同来源应用（QQ / 微信 / 浏览器）传的 UTD 可能不同 → 验证记录里**必须写清每条样本来自哪个应用**；若某来源的 UTD 不在我们声明的 `uris` 里，表现为「分享面板里找不到知了」。
- **注意**：这是三张验证卡里**最耗机器时间**的一张（要反复从 QQ 分享、attach 调试、再分享）。**提前把测试样本准备好**（2 条纯文本、1 张截图、1 条超长消息），进手机后一次跑完，不要现场找消息。
- **归属**：谢忠宇。
- **预估**：1 天。

### W1-T10 假数据主链路闭环

- **目标**：先把「粘贴 → 解析 → 确认 → 任务」这条路的**页面跳转与数据流**跑通，解析结果先用假数据。
- **交付物**：可在模拟器上演示的闭环 Demo。
- **依赖**：W1-T05、W1-T08。
- **验收标准**：
  - [ ] 粘贴一段文本，进入解析确认页并展示候选字段（假数据）
  - [ ] 字段可编辑，编辑后保存进入任务列表
  - [ ] 任务出现在首页时间线对应分档
  - [ ] 重启后任务仍在
  - [ ] 全程无崩溃、无白屏
- **风险**：闭环跑通后误以为「解析已完成」 → 周会上明确区分「闭环已通」与「解析未接」。
- **归属**：三人。
- **预估**：2 天。

### W1-T11 云端中继可行性 spike

- **目标**：用**半天**回答一个问题——AGC 云函数的**HTTP 触发器 URL 能不能被第三方从公网直接 POST**。这个答案决定机器人链路走哪条路（见 §6.2 的两条路径）。
- **交付物**：一段实测结论（通 / 不通）+ 最小云函数工程（Node.js）+ 一条写进云数据库的测试记录。
- **依赖**：W1-T02。
- **验收标准**：
  - [ ] AGC 侧已建云函数并开通云数据库，DevEco 能部署成功
  - [ ] **从公网**（不是本机 localhost）用 `curl` POST 到 HTTP 触发器 URL，云函数日志里能看到这次调用
  - [ ] 手机或模拟器用 `cloudfunction.call` 调用同一函数成功返回
  - [ ] 用云数据库写入一条记录并读回
  - [ ] 结论写进周会记录：**若「不通」，直接确定走 §6.2 的 WebSocket 主路径，不再纠缠**
- **风险**：把「本机 localhost 调试通过」误判成「公网可达」。**必须从另一台网络上的机器或手机热点发这个请求**，否则测的不是同一件事。
- **注意**：这是**可行性 spike，不是开发任务**——故意只做最小可跑通的函数，不写业务逻辑、不做字段校验、不考虑异常。跑通即停，把时间还给 W1-T10。

- **归属**：谢忠宇。
- **预估**：0.5 天。

## 5. 开题报告「退路」的对照落实

> 这一节的作用是**避免开题报告与开发脱节**：报告里写下的每条退路，在平台上真实对应的动作是什么。凡是报告写「第一周真机验证」的，就是本指南里的可行性验证任务。

### 5.1 逐条对照

| 开题报告中写下的退路（原文要点） | 平台上的真实情况 | 本指南落实动作 | 状态 |
| :-- | :-- | :-- | :-- |
| 「代理提醒受限或配额不足 → 第一周真机验证；失败则退回普通通知并在设置页写明提醒可能延迟」（`tab:risk`） | 管控**确实存在**；替代路径是日历或申请开放能力；配额确有上限（30 条） | **W1-T06 提交申请 + W1-T07 真机验证 + 日历兜底**；普通通知降级为「次级兜底」而非主兜底 | 已落实，**升格为头号风险** |
| 「无障碍读屏未获批 → 第一周真机验证；失败则标为实验性默认关闭，主链路改用分享与粘贴」（`tab:risk`） | **不是「未获批」，而是「平台已不再开放」**：接口 @deprecated since 12，官方原文「系统不再开放相关能力」；审核指南 2.10 还禁止诱导开启辅助功能 | **直接砍掉，不排期**；主链路用分享与粘贴；答辩材料里写进「未做项」并附依据 | **已升级为确定结论** |

| 「四条采集通道中机器人转发与分享接收是主链路，语音输入与无障碍读屏可晚一步」（可行性说明） | 四条里**无障碍读屏不可用**，语音**模拟器可验**（需实测麦克风） | 主链路收敛为**粘贴 + 分享 + 机器人转发**三条；语音降为 P2 且只占 W3-T02 一个任务卡 | **已收敛** |
| 「服务端若最终不需要，整块砍掉不影响演示」（可行性说明） | **这条后来被用户需求改写**：bot 收集的数据要经云中转、APP 再拉取 → 服务端重新成为需要项，但用官方 Cloud Foundation Kit（云函数 + 云数据库）实现，**仍然不写自建后端** | `service/cloud/` 走 `cloudFunction` / `cloudDatabase`；`service/backend/` 只放 bot 与云函数的契约与字段约定，不放 ArkTS 代码；机器人通道**可整块关闭**（见 §6.2 的退路） | **已由「不做」改为「用官方能力做」** |

### 5.2 一条被报告写对、被我们验证放大的判断

报告在风险表里把「最大不确定项是系统能力能不能用（尤其代理提醒），排在第 1 周验证，不等开发末期才发现没有退路」写成原则。**本指南把这句原则落成了三个带编号、带验收标准、带归属人的任务卡（W1-T07 / W1-T08 / W1-T09），并且要求结论必须写成「通过 / 不通过 / 未验证」，不许写「大概可以」。**

> 换句话说：报告负责说「要验证」，本指南负责说「谁来验、验什么、验完写在哪」。这一步不做，四周后的答辩上就会出现「我们以为可以」。

## 6. 机器人中继链路与数据边界（新增链路）

> 这一节回答两个问题：**云服务器怎么做**、**数据边界划在哪里**。它是全篇唯一描述「数据离开手机」的章节，所以每个结论都要能落到代码或配置上。

### 6.1 云服务器怎么做：用 Cloud Foundation Kit，不自建

**结论：不需要租服务器，也不需要自己写后端服务。** 华为官方在 DevEco 里提供了端云一体化能力，用的就是 `@kit.CloudFoundationKit`（`@since 5.0.0(12)`）。

| 官方服务 | 我们用它做什么 | 关键 API | 计费 |
| :-- | :-- | :-- | :-- |
| 云函数 `cloudFunction` | 接收机器人转来的消息 → 解析 → 写入云数据库 | `call(parameters: FunctionParams): Promise<FunctionResult>`（`@permission ohos.permission.INTERNET`） | 有**免费额度** |
| 云数据库 `cloudDatabase` | 存「已解析的结构化任务」供手机拉取 | `zone(zone: string): DatabaseZone` + `DatabaseQuery` | 有**免费额度** |
| 云存储 `cloudStorage` | **不用**。存原图就等于把图片留在云上 | `bucket(name?: string): StorageBucket` | —— |
| 云开发服务总览 | 端云一体化：DevEco 里建工程、写函数（Node.js）、本地调试、部署 | `cloudCommon.init(options?)` | 「弹性伸缩、**按量计费**」 |

**官方原文**（`开发指南/Cloud_Foundation_Kit_云开发服务/Cloud_Foundation_Kit简介/cloudfoundation-introduction`）：「应用运行所需的服务器和环境均可由云端平台提供，开发者只需关注业务的业务逻辑，而无需关心基础设施」；「云函数、云数据库、云存储服务提供了免费额度以供试用」。

> [!important] 一个没有替代方案的未知项
> **「AGC 云函数的 HTTP 触发器 URL 能不能被第三方平台（QQ 侧）从公网直接 POST」在官方文档里没有明确依据。** 官方只写了「端侧通过 `cloudfunction.call` 调用」和「Server SDK 通过 HTTP 触发器调用」两种用法，**没有说它是通用 Webhook 接收端点**。
>
> 所以本指南**不把它当既定事实**：要么第 1 周用 `curl` 半天验掉（W1-T11），要么走下面 6.2 的主路径（根本不依赖它）。

### 6.2 数据怎么走：两条链路，主路径不依赖公网入口

```text
路径 A（备选，依赖上面那个未知项）
  QQ 群消息 → QQ 平台 → WebHook → AGC 云函数 HTTP 触发器 → 解析 → 云数据库 → 手机拉取
                                    ↑ 这一步能不能通，未取证

路径 B（推荐，第 1 周就实现这一条）
  QQ 群消息 → QQ 平台 → WebSocket 长连接 ← bot 进程 ← 调 AGC 云函数 → 云数据库 → 手机拉取
                                            （订阅事件）

手机侧（两条路径完全相同）
  冷启动 / 用户下拉刷新 → cloudDatabase 查询「未同步」记录 → 进入本机待确认列表
  → 用户在确认页点确认 → 写入本机 relationalStore → 回写云端标记已同步或直接删除该条
```

**为什么主路径推荐 B**：QQ 官方文档明确「支持 WebSocket、WebHook 回调连接方式灵活切换」，且 WebSocket 的定义是「**不依赖公网服务器部署，适合个人单机使用**，需维护长连接」。用它我们就不需要**任何**公网 HTTPS 入口，也不用回答「QQ 怎么找到我们」。

**随之而来的一个必须写清的取舍**：WebSocket 要有人保持长连接。第 1 周开发和第 4 周答辩演示期间，**bot 进程就跑在一台笔记本上**（必须是开机且联网的时段），不产生任何租用成本；只有将来要做成 7×24 对外服务，才需要一台常驻主机。开题报告里「不建服务端」的说法，准确表述是「**不建需要自己运维的服务端**」。

**手机侧不要做常驻后台拉取。** 冷启动拉一次 + 下拉刷新即可；这既符合开题报告「不申请非必要权限」的原则，也避开了后台任务在目标系统上的配额限制。

### 6.3 云上存什么：一个对象、十个字段，原文字段不存在

```text
云数据库对象 BotTask（存储区 bot）
├── client_task_id  STRING   必填   端侧幂等键：同一 client_task_id 重复写入按同一条处理
├── title           STRING   必填   解析出的事项
├── due_at          NUMBER   可空   截止时间戳（毫秒）
├── due_text        STRING   可空   截止时间原文，如「本周五」
├── location        STRING   可空   地点
├── repeat          STRING   可空   平台 repeat 原样字符串
├── confidence      NUMBER   必填   0~100
├── status          NUMBER   必填   0 未同步 / 1 已同步 / 2 用户已确认
├── from_channel    STRING   必填   固定 bot
└── created_at      NUMBER   必填   写入时间戳（用于 TTL 清理）

明确不存的字段（这是数据边界的核心）
  ✗ raw_text        原文不落云
  ✗ raw_json        平台原始 jsonObject 不落云
  ✗ sender / sender_id / group_id / message_id  任何可以用来还原「谁在哪个群说了什么」的标识
  ✗ 图片、语音、缩略图
```

**服务端解析产出一落库即丢弃原文**：云函数把结构化字段写进云数据库后直接返回，**原文只作为函数入参存在于内存中**，不落库、不写云存储、不打日志。

### 6.4 数据边界表（写隐私政策、答辩、被审核问到时都用这一张）

| 数据元素 | 本机（relationalStore） | 云端 | 保留多久 | 谁能清掉它 |
| :-- | :-- | :-- | :-- | :-- |
| 原文 `raw_text` | **存**（原文对照功能依赖它） | **不存**，只作为云函数的内存入参 | —— | 用户删任务即删 |
| 原始抽取结果 `raw_json` | **存**（第 3 周调参依赖它） | **不存** | —— | 同上 |
| 结构化任务字段 | 存 | **存**（见 6.3 的对象） | 默认 TTL 7 天，到期自动清理 | 设置页一键清空；删除任务时同步删除云端记录 |
| 图片 / 截图 | 存（用户主动添加的） | **不存** | —— | 用户删任务即删 |
| 语音音频 | **不存**（识别完即丢，只留文字） | **不存** | —— | —— |
| 从别的应用分享时的来源信息 | 只记一个值：`source = paste / share / bot / voice / manual` | **不存** | —— | —— |
| 通讯录 / 位置 / 账号 | **不申请、不读取**（开题报告已冻结） | —— | —— | —— |

> 第四行「删除任务时同步删除云端记录」的准确含义：**端侧删任务时，同时删除以该 `client_task_id` 为键的云端记录**，不是维护一张同步删除队列。云端另有 TTL 7 天兜底，两条路任意一条生效即可。

**两句话概括边界**：**「进得来的是文字，上得云的是字段」**、**「能还原出谁在哪个群说了什么，一律不上云」**。

### 6.5 上架风险怎么办：六条工程约束 + 一份口径

**先承认一件事**：这条链路会让**群里的第三方内容**（可能含他人信息）经过我们的服务。这不是「有没有风险」的问题，而是「能不能说清、能不能关掉、能不能删掉」的问题。所以约束按这六条执行：

1. **原文不落云**：见 6.3。函数返回前原文就从内存中消失，不写库、不写云存储。
2. **日志脱敏**：bot 进程与云函数**都不打印消息正文**，只打 `client_task_id`、字段数量、耗时。**日志是最常见的泄露面**，比数据库更容易被忽略。
3. **数据最小化**：云上只有 6.3 的十个字段，且没有发送者、群、消息标识。**字段表本身就是合规手段**——云上存不了的，泄露时也不会存在。
4. **可删可清**：设置页必须有「云端数据」一节，能看清单、能一键清空；删除本机任务时同步删除云端记录；云端记录默认 TTL 7 天。
5. **默认关闭 + 双开关**：云端同步默认**关闭**，用户手动开启时说明「哪些字段会离开手机、存在哪、保留多久」；关闭时同时停止 bot 转发与云端拉取。
6. **口径与实现一致**：隐私政策里写的字段范围必须与 6.3 的对象逐字对应。**「说出去的比存下去的多」比「真的存了」更危险**——被驳回通常不是因为存得多，而是因为说得不清。

**一份可直接改写的口径**（隐私政策原文建议）：

> 「知了」的 QQ 机器人转发通道默认关闭。开启后，机器人在群内收到的消息文字会被发送至华为云进行**一次解析**，解析完成后**原文不保存**；云端仅保存解析得到的待办字段（事项、截止时间、截取到的截止时间原文表述、地点、周期、置信度，共十项，见下节字段表）。本应用不读取聊天记录、通讯录与位置信息，不保存消息发送者与群标识。用户可在「设置 → 云端数据」查看并一键清空云端记录，云端记录默认保留 7 天。

**还有一些必须一起说清的责任与条件**（来自 QQ 机器人官方文档）：

- QQ 侧规则原文：「**QQ 平台仅向开发者及用户提供 QQ 机器人运行的相关技术支持。机器人相关服务由开发者提供，开发者对相关服务信息内容、数据资料及其运营行为等的真实性、合法性及有效性承担全部责任。**」→ 隐私责任在我们身上，不能推给平台。
- 机器人主体需要**个人实名认证**（姓名、身份证号需与手机号运营商登记一致）；**未认证时机器人只能被管理员添加到「管理员作为群主」的群**（可配合「内部体验号码」最多 20 个做内邀）。对课程项目这反而是可控的：小范围真群样本足够做完验证。
- QQ 侧「服务器 IP 白名单」只影响它调用机器人 OpenAPI，**不影响我们接收事件**。

**退路（和开题报告的克制原则一致）**：把机器人通道做成**可整块关闭的功能**。上架审核若对这条通道有异议，直接关掉它——粘贴与分享两条主链路不受任何影响。这也是本指南把机器人通道排在 P1 而不是 P0 的原因。

## 8. 风险与兜底

### 8.1 头号风险：代理提醒（P0 依赖项）

**事实**：手机、平板、PC/2in1 设备**存在管控**，管控后应用无法直接使用；替代路径有两条——用日历实现提醒，或向华为申请开放能力（8 个工作日反馈，需提交功能场景截图与应用分类截图）。

**我们的处境**：「知了」定位是效率类 / 工具类应用，场景是「学习类提醒（课程提醒）」与「生活类提醒（时间/日程提醒）」，**在可申请的场景清单内**（原文列举含「学习提醒、课程提醒」「时间/日程提醒」）。

**双轨动作**：

1. **第 1 天提交申请**（W1-T06），记录提交日期，按 **8 个工作日**回推预期反馈日（约落在第 2 周下半段）。
2. **第 1 周同一时间做日历兜底方案设计**（W1-T06 的后半段），第 2 周按下面的「界面收口」实现。
3. **第三条兜底**：普通通知（`notificationManager`）。它不解决「应用被杀后仍按时提醒」的问题，因此**只能作为降级提示，不能作为主方案**。

**界面收口（第 3 天定的事）**：架构上**只做一套提醒能力，内部分两条实现路径**，全部收口在 `service/system/ReminderService.ets` 里，对上层暴露同一个接口：

```text
ReminderService（唯一对外接口）
├── 路径 A：代理提醒 reminderAgentManager.publishReminder   ← 开放能力获批 + W1-T07 通过才启用
└── 路径 B：系统日历   calendarManager.addEvent             ← 申请未获批或 W1-T07 不通过时启用
```

理由：日历路径同样依赖用户在系统日历里能看到，**但它不需要等华为审批、也能在应用被杀后按时提醒**。两条路径都不存在时（比如用户不开通知、也不开日历权限），才退到「应用内提示 + 首页时间线」。

**判断点（明确写成日期动作）**：

| 时点 | 判断 | 动作 |
| :-- | :-- | :-- |
| 第 1 周周末 | 申请已提交？W1-T07 通过？ | 两项都「是」→ W2-T06 主实现路径 A；任一「否」→ **不等审批**，W2-T06 直接实现路径 B |
| 第 2 周周三（中期同步） | 若仍在等审批 | **仍按路径 A 继续开发**，但把「切换到路径 B」的工时按 0.5 天预留（因为收口在同一接口，切换成本主要是写实现和改设置页文案） |
| 第 2 周周末 | 申请结果 | 无论结果如何都在此处出结论；若此时才获批而路径 B 已上线，**保留路径 B**，路径 A 作为第 3 周的增强 |

> [!important] 不要做的事
> **不要为了「保险」把两条路径都完整实现再各接一套界面。** 四周项目里，同一个能力做两遍是最典型的范围膨胀——开题报告 `tab:notdo` 的精神就是不重复建设。收口到一个接口，同一时间只上线一条路径。

**提醒条数限制**：单应用有效提醒 ≤ 30 条。→ 实现规则：只为「最近 30 条未完成任务」发布提醒；超出的任务在首页显示「提醒已合并」，并在设置页写明。

**这条风险的一个直接推论（提醒的两条路径必须收口）**：`service/system/ReminderService.ets` 对外只暴露「为任务发布提醒 / 撤销提醒 / 查询有效提醒」三个动作，内部走哪条路径**由它自己决定**，页面与 ViewModel 里**不许出现** `if (用了日历)` 这种分支。

### 8.2 二号风险：只有一台真机

**现状**：团队唯一达标的真机是**杜俊廷那台 HarmonyOS 6.0.2(22)**。本机 `devecocli device list` → `No active devices`，因为手机没有连在这台开发机上——**这是正常的，不是设备不存在**。而**解析质量（实体抽取、文字识别）在模拟器上根本跑不起来**。

**动作（按优先级）**：

1. **把杜俊廷这台 6.0.2(22) 手机固定为「验证机」**，并约定使用时段。设备只有一台时，最贵的不是机器而是**换手成本**：每次换人连接、装包、复现环境都是 20–30 分钟，所以验证任务要成组做。
2. **能用模拟器的一律不占真机**：数据层、假数据闭环、UI 走查、分享接收的 UI 表现都能在模拟器上做（`devecocli emulator list` 有 `Pura 90`(6.1.1(24)) 与 `Pura X View`(7.0.0(26.0.0) Beta2)）。真机只留给三件模拟器做不到的事。
3. **需要第二台设备（或手机不在手上）时用 AGC 云调试**——这确实是华为官方提供的途径，不是传闻：
   - **入口与文档**：AppGallery Connect →「云调试」（官方文档树 `上架分发与运营 / 上架-AppGallery Connect 应用上架 / 云调试`，含总览、业务介绍、单机调试流程、申请调试设备、预约调试、调试应用、使用限制、计费说明、FAQ）。**注意这些 AGC 篇不在 `devecocli docs read` 的本地库里**，要按官方 URL 打开（17 篇的 slug 与证据见 `docs/99-附录-取证台账.md` §11 与 §11.1）。
   - **官方能在本地文档库查到的两条硬约束**：
     - **云侧设备的 API 必须 ≥ 你工程的 `compatibleSdkVersion`**。我们的 `compatibleSdkVersion` 是 `6.0.2(22)`（见 §8.1），所以**云调试时只能筛 API ≥ 22 的设备**；选到低版本设备会报「应用不匹配当前系统版本，请选择其他系统版本设备」。
     - **HarmonyOS NEXT 设备只能上传 HAP / APP 包**；release 包装在低版本云设备上会报 `error: failed to install bundle. code:9568297 ... older sdk version in the device`。
   - **一条省时技巧（官方给的）**：进设备之前先在「云调试 → 我的信息 → 应用」里**提前上传**要调试的包，再进设备点安装。免费体验时长是按设备会话计的，上传耗时不必花在里面。
   - **画面是截屏流**：云真机上看到的是截屏，**任何防截屏行为都会让画面变黑**（官方 FAQ 明确说这是「应用登录页设了防截屏」导致的）。我们不做登录，但**第 4 周若给分享进来的图片加隐私保护/防截屏，云调试上就会黑屏**——那时要用官方给的「获取控件树」按钮绕过去。

   - **仍未取证**：云调试的账号门槛（是否需要实名/登录）、免费额度与计费细节，**本地文档库中查不到官方原文**，启用前按官方 `-restriction-` 与 `-price-` 两篇自行核实（见 `docs/99-附录-取证台账.md` §11.1 与 §12 第 15 条）。
   - **代价要提前算**：走云调试意味着**W4-T03 的签名要提前到第 2 周**（与 §9.5 那条 `unsigned` 告警是同一件事：`devecocli build` 默认产出的是没签名的 HAP，云调试装不了）。
4. **若连这一台也用不了**（手机损坏、系统版本不符、长期借不到），**必须当场改演示口径**：答辩时演示「数据层 + 提醒 + 分享接收 + 假数据闭环」，解析质量用预先跑好的真机结果截图说明。**这条口径要在第 1 周出口条件里就写下来**，不能等到第 4 周。

> 不要用模拟器跑不起来的截图去凑「解析可用」的结论。这一条比任何技术风险都危险，因为它会把「项目没做出来」包装成「项目做出来了」。

### 8.3 权限清单与用途说明（写隐私政策时逐条对应）

| 权限 | 用途 | 触发时机 | 未授予时的降级 |
| :-- | :-- | :-- | :-- |
| `ohos.permission.PUBLISH_AGENT_REMINDER` | 发布代理提醒 | 首次开启提醒功能时 | 改用系统日历或普通通知 |
| `ohos.permission.MICROPHONE` | 语音输入转文字 | 用户按下录音按钮后 | 语音通道不可用，提示改用文字输入 |
| `ohos.permission.WRITE_CALENDAR` | 日历兜底路径：建立知了专用的日历账户并写入带提醒的日程 | 用户选择「用系统日历提醒」时 | 该兜底路径不可用 |
| `ohos.permission.INTERNET` | ① 机器人中继链路（P1）：调云函数、拉云数据库；② 语音识别是否需要该权限**未取证** | ① 用户开启「云端同步」后；② 按下录音按钮后（若最终确认需要） | 云端同步关闭时该通道不可用；其余通道不受影响 |

> [!warning] 关于 `INTERNET`
> 语音识别与 OCR 是否**需要** `ohos.permission.INTERNET`，在本地全部文档中检索 `INTERNET` **零命中**，而文档反复声明语音识别「当前仅支持离线模式」。**在拿到依据之前不要凭印象写进去**；若最终不加而真机报网络类错误，再按错误码回溯补上。
>
> 但**云中继这条链路是确定要 `INTERNET` 的**：`@hms.core.deviceCloudGateway.cloudFunction.d.ts:35` 的 `call` 明确标了 `@permission ohos.permission.INTERNET`，错误码 `201 No Internet permission` 就是它。**这一条没有争议，可以写进隐私政策**——措辞是「用于把解析后的待办字段同步到华为云」，不是「用于采集你的信息」。

> [!important] 不申请的权限
> **不申请定位与通讯录**（开题报告已明确）。分享接收由用户在别的应用里主动发起，不需要额外权限。

> [!note] 一条会影响隐私政策措辞的细节
> `calendarManager` 的 `createCalendar`（`openharmony/ets/api/@ohos.calendarManager.d.ts:70`）**自 @since 10 起就要求写权限**，而 `addEvent`（`:286`）的 `@permission` 标注是 **`[since 23]`**——也就是说在目标系统 **6.0.2(22)** 上写日程本身不要求该权限，**要求它的是「建知了自己的日历账户」这一步**。
>
> 对隐私政策的影响：措辞应写「知了需要写入日历权限，用于创建「知了」日历账户并在其中写入提醒日程」，**不要写成「为了读取你的日程」**——我们既不读也不改用户已有的日程。

**几条落位规则**：

- `service/` 每个子域一个目录，目录下有 `index.ets` 做桶导出。**页面不直接 import 子域内的实现文件**，只 import 桶。
- `service/cloud/` 是**唯一能碰云端**的地方。它只从 `repository/` 读、只往 `repository/` 写，**不许把云返回的对象直接交给页面**——外部来的结构必须先过一遍字段白名单（理由见 §6.3）。
- 页面路由走「单入口 + 内部 Navigation」，`resources/base/profile/main_pages.json` **只注册入口页**。
- `state/` 目录**不建**。页面级状态留在页面的 ViewModel 里；跨页共享状态在第 2 周真正出现需求时再决定放哪，不预先建空目录。

### 9.2 数据模型（字段约定）

```text
任务 Task
├── id              INTEGER PRIMARY KEY AUTOINCREMENT
├── title           TEXT NOT NULL          # 事项，来自规则提取或用户输入
├── detail          TEXT                   # 补充说明，允许为空
├── source          TEXT NOT NULL          # 来源通道：paste/share/bot/voice/manual
├── raw_text        TEXT NOT NULL          # 原文，永久保留，用于「原文对照」
├── raw_json        TEXT                   # 平台抽取的原始 jsonObject，用于回溯与调参
├── due_at          INTEGER                # 截止时间戳（毫秒），可为空
├── due_text        TEXT                   # 截止时间的原文表述，如「本周五」
├── repeat          TEXT                   # 周期，平台 repeat 字段原样存
├── location        TEXT                   # 地点，平台 LOCATION 实体
├── priority        INTEGER NOT NULL       # 0 普通 / 1 重要 / 2 紧急
├── confidence      INTEGER NOT NULL       # 0~100，低可信字段在确认页高亮
├── missing_fields  TEXT                   # 缺失字段名列表，缺失不猜测
├── status          INTEGER NOT NULL       # 0 待确认 / 1 已确认 / 2 进行中 / 3 已完成 / 4 已过期 / 5 已删除
├── remind_at       INTEGER                # 实际提醒时间，按提前量算得
├── reminder_id     INTEGER                # 代理提醒 id，与任务 id 确定性映射
└── created_at / updated_at INTEGER
```

**三条字段纪律**：

1. **`raw_text` 和 `raw_json` 必须存。** 前者是「原文对照」功能的唯一依据，后者是第 3 周调解析规则的唯一依据。删掉任何一个，后面都会回来重做。
2. **缺失字段进 `missing_fields`，不编造值。** 这是开题报告里「缺失不猜测」的工程实现形式。
3. **`repeat` 存平台原样字符串**，不要在写入时就翻译成周期对象——翻译规则会在真机验证后调整。

> [!warning] 本机 Task 与云端 `BotTask` 不是同一个东西
> 上表是**手机上**的完整任务（含 `raw_text` / `raw_json`，**这两列永远不上云**）。云上只有 §6.3 那个**十字段**的 `BotTask`。两者靠 `client_task_id` 对齐，**字段名不完全一致是故意的**——云上少一个字段，就不可能被误同步上去。写代码时不要让同一个类同时承担两种形态。

### 9.3 状态机（与开题报告一致）

```text
待确认(0) --用户确认--> 已确认(1) --> 进行中(2) --> 已完成(3)
                                        |
                                        +--截止时间已过（唯一由系统自动标记）--> 已过期(4)

任一状态 --用户删除--> 已删除(5)
删除后：不再参与提醒，不再出现在时间线
```

> 实现要点：**「已过期」只有系统能写，用户不能手动把任务标成已过期。** 这条判断在第 2 周 W2-T05 的实现里要看得出来。

### 9.4 调用约定（三条硬规矩）

1. **AI 能力必须在 `service/ai/` 里动态引入。** 直接原因：模拟器上静态 import 不支持的 Kit 会闪退。所有 AI 调用统一返回「成功 / 失败 + 错误码」，不允许把异常抛到页面层。
2. **页面不直接调系统能力。** 页面 → ViewModel → service → repository，中间不跳层。
3. **所有权限申请集中在 `service/system/`。** 页面只拿结论（已授权 / 未授权 / 被拒绝），不关心申请细节。

### 9.5 提醒路径的收口接口（第 2 周 W2-T06 的骨架）

```text
ReminderService
├── publish(task: Task): Promise<number>      # 返回本地 reminder 键，失败抛业务错误码
├── cancel(taskId: number): Promise<void>     # 已完成 / 已删除 / 编辑时间后都要调
├── listValid(): Promise<Task[]>              # 供设置页显示「当前生效提醒 N / 30 条」
└── 内部
    ├── 路径 A：reminderAgentManager.publishReminder（需 PUBLISH_AGENT_REMINDER 权限 + 开放能力获批）
    └── 路径 B：calendarManager.createCalendar → addEvent（需 WRITE_CALENDAR 权限）
```

**「本地 reminder 键」在两条路径下的含义不同，但表里只留一列 `reminder_id`**：

| 路径 | `publish` 返回并写进 `task.reminder_id` 的值 | `cancel` 时怎么用 |
| :-- | :-- | :-- |
| A 代理提醒 | `publishReminder` 返回的 `reminderId`（`number`），**同时用同一个值当 `notificationId`** | `cancelReminder(task.reminder_id)` |
| B 日历 | `addEvent` 返回的 **eventId**（`number`） | `deleteEvent(task.reminder_id)` |

> [!important] 切路径时必须把已有任务的 `reminder_id` 全部作废
> `reminder_id` 在两套系统里是两套编号空间，**同一个数字在路径 A 是提醒 id、在路径 B 是日程 id**。如果第 2 周中途从一条路径切到另一条，**旧路径已发布的提醒必须逐个撤销、并且把已有任务的 `reminder_id` 清空后重新发布**。不清空就会出现「按 id 去撤，撤掉了不相关的提醒/日程」——这是切换路径时最容易造成的隐蔽缺陷。

**三条实现纪律**：

1. **发布要幂等**：同一个任务重复调 `publish` 必须收敛成一条（路径 A 靠确定性 `notificationId`，路径 B 靠「先按 `taskId` 查有无日程，有则改、无则建」）。
2. **撤销要成对**：任务状态变成已完成 / 已删除，或截止时间被编辑时，**必须调 `cancel`**；否则用户会收到一条指向已消失任务的提醒。这是第 3 周试用阶段最容易被同学报的缺陷。
3. **`publish` 的失败要可解释**：`1700002`（数量超限）要翻译成「提醒数量已达上限，请在任务列表里完成或删除一些任务」；权限类错误码要翻译成可执行的下一步，不能只弹「操作失败」。

**路径 B（日历）落地时唯一容易写错的地方**：设置页的「提醒提前量」直接对应 `Event.reminderTime`（**单位分钟，值 5 表示开始前 5 分钟，不设则不提醒**，见 `docs/99-附录-取证台账.md` §6.1）；周期任务要把平台的 `repeat` 字符串（`W3` / `M2` / `workingDay` 等）映射成 `recurrenceRule` 的 `RecurrenceFrequency` + `daysOfWeek` / `daysOfMonth` / `monthsOfYear`。**这张映射表要做成纯函数并配单元测试**，否则每周/每月周期一上线就会出现「每周三的提醒跑到周三以外」。另外 `EventType` 一律用 `NORMAL`——SDK 原文明确 `IMPORTANT` 不推荐三方开发者使用且**不支持自定义提醒时间**。

## 10. 验证与提交

### 10.1 每一步的验证闭环

| 层次 | 手段 | 何时用 |
| :-- | :-- | :-- |
| 静态检查 | `mcp__deveco__check`（ArkTS 语法） | 每改完一个文件 |
| 编译 | `devecocli build`（可选 `--modules entry`） | 每次提交前 |
| 产物 | `entry/build/default/outputs/default/entry-default-unsigned.hap` | 构建成功后核对路径 |
| 运行期 | `devecocli run`（可带 `--device`、`--uninstall`） | 有设备时 |
| 日志 | `devecocli log --level E` / `--crash` / `--bundle-name <包名>` | 排查崩溃与异常 |

> [!warning] 两条工具的实际脾气（用之前先知道，省半小时）
> 1. **`mcp__deveco__check` 不接受绝对路径**（传绝对路径会报 `Error: Absolute path is not allowed`），**必须传相对工程根的路径**（例如 `entry/src/main/ets/pages/A_Home.ets`）。它还有可能返回「没有有效的 .ets 文件」/「No diagnostics collected」——这时不要以为检查通过了，**改用 `devecocli build` 兜底**。
> 2. **产物文件名带 `unsigned`**：未配置签名时产出的是 `entry-default-unsigned.hap`（实测 121404 字节）。**文件名里的 `unsigned` 就是「装不进真机」的提示**，看到它就不要浪费时间去 `devecocli run`。

### 10.2 提交约定

- 提交信息格式：`[W1-T03] 六页静态原型`。**没有任务号的提交不接受。**
- 提交前必须：`mcp__deveco__check` 无新增报错 + `devecocli build` 通过。
- **不许为了「看起来有进展」而提交编译不过的代码。** 编译不过就说明当前进度，不要包一层注释让它编过。

> [!note] 一条已经跑通过的基线
> 本指南的工程章节不是纸面推演：`devecocli create --app-name Distiller --project-path "E:\Program_File\HMOS_proj\Distiller" --bundle-name com.xjtu.distiller --api-level 22` 已真实建出工程，`devecocli build --modules entry` 实测 **`BUILD SUCCESSFUL in 15 s 669 ms`**（`Build completed successfully`，退出码 0；其中 `CompileArkTS` 6 s 585 ms、`PackageHap` 808 ms）。
>
> 唯一告警要记住：`hvigor WARN: Will skip sign 'hos_hap'. No signingConfigs profile is configured in current project.` ——**模板构建出来的 HAP 是未签名的**，装不进真机。所以第 4 周的签名配置（W4-T03）不是走形式，是主链路上的一环。
>
> 顺带一条已验证的事实：模板的 `targetSdkVersion "6.0.2(22)"` 与本机 SDK（HarmonyOS 26.0.0 Beta2，`apiVersion 26`）**兼容，不需要改版本号就能编译**。

### 10.3 每周必须留下的一句话

每周进度记录的**最后一行**固定写：

> 本周最重要的一句话：______

格式照搬开题报告的态度——**如果这一周只能让一个人记住一件事，那件事是什么。** 第 1 周这句话大概率是「代理提醒已申请，反馈日期是 X 月 X 日」；第 2 周大概率是「真机上真解析真提醒跑通了」；第 3 周大概率是「主链路阻塞缺陷清零了」；第 4 周是「已提交审核」。

### 10.4 两个「按正常方式调不出来」的场景
