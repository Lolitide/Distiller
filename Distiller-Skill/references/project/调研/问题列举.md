## 一、平台能力与准入（最会卡死项目的一类）

**1. 代理提醒在手机上被管控**
- 已确证：手机/平板/PC 存在管控，应用无法直接使用；智慧屏、穿戴无此限制。只能走两条路：改日历，或向华为申请开放能力（AGC → 项目设置 → 开放能力管理 → 代理提醒），反馈期 8 个工作日。
- 已确证：申请通过后调试与发布都必须重新生成 Profile 并改用手动签名。
- **未验证**：获批后杜俊廷那台 6.0.2(22) 是否还受管控——申请过了不等于这台能用。

**2. 提醒条数有硬上限**
- 已确证：单个普通应用有效提醒不超过 30 条，超了报 `1700002`；点 CLOSE 才算过期，周期性提醒永远算有效；点击提醒跳转的应用必须是申请能力的本应用。
- 已确证：代理提醒到点后用 Notification Kit 发通知，所以通知授权是前置条件。

**3. 无障碍读屏这条路已经断了**
- 已确证且是最彻底的结论：`AccessibilityExtensionContext` 与 `AccessibilityElement` 的方法全部 `@deprecated since 12`，官方 note 原文「系统不再开放相关能力」；Accessibility Kit 简介原文「不支持通过无障碍节点查询获取界面节点及屏幕内容信息」；消费者口径「升级后第三方读屏软件不支持屏幕朗读」；审核指南 2.10 把「开启辅助功能」列为驳回情形；权限总表里没有 `ohos.permission.ACCESSIBILITY`。
- 结论：P2 这条通道直接砍掉。**未调研**：真机设置页是否仍列出该服务、HMS 闭源白名单。

**4. 云开发的门槛是账号不是技术**
- 已确证：AGC 账号须已完成实名认证；DevEco 需 NEXT Developer Beta1 及以上；云函数用 Node.js 运行时。
- **未验证**：本机这套 Beta2 + SDK 26 是否真能跑通云函数端到端（版本号够，但没实测过）。

**5. AGC 云函数的 HTTP 触发器能不能被 QQ 侧从公网 POST**
- 状态：**官方文档零依据**。官方只写了端侧 `cloudfunction.call` 与 Server SDK 两种用法，没有声明它是通用 Webhook 端点。
- 这是唯一一个「不问出答案就得改架构」的未知项，压成半天 spike。

## 二、AI 能力（三件套各有硬约束）

**6. OCR 与实体抽取都不支持模拟器**
- 已确证：Core Vision Kit 文字识别原文「本Kit暂不支持模拟器」；Natural Language Kit 实体抽取同样不支持。
- 已确证且很容易踩：模拟器上静态 import 会让应用**直接闪退**，报错模板 `resolveBufferCallback get hsp buffer failed，hsp path:/data/storage/el1_bundle/com.huawei.hmos.{KitName}.kit`。官方规避手段是动态引入 Kit。

**7. 实体抽取有 1000 字符上限**
- 已确证：文本长度不超过 1000 字符，超了必须切片。群消息长文本是常态，切片与「多段结果怎么合并」都要自己写。

**8. 事项提取没有现成能力**
- 已确证：`EntityType` 十个值里没有「事项」类，只有 `DATETIME`、`LOCATION` 这些。判断「这条消息到底要干什么」得自己写规则。

**9. OCR 的时间地点会抽错**
- 已确证：语言支持 zh-CN/en/ja/ko/zh-TW，输入只接受 RGBA_8888 的 PixelMap。
- **有冲突**：图片宽高比上限，官方 FAQ 说「2:1 以下」，另一处说「10:1 以下」，两处没对上。
- **未确证**：图片像素总量的上限（记忆中官方有类似限制条款，我没在本次调研里拿到原文），以及是否需要 AGC 开放能力。

**10. 语音识别的音频格式卡得很死**
- 已确证：仅 zh-CN、仅离线模式、`pcm`、16000Hz、单声道、16bit；`writeAudio` 的音频流长度只接受 640 或 1280。
- **未确证**：AudioCapturer 实际输出与 speechRecognizer 期望输入是否严丝合缝——官方**没有**两者联用的示例，参数对齐是我们从两侧枚举推出来的。
- **未确证**：`ohos.permission.INTERNET` 是不是必需。
- **未确证**：模拟器的麦克风输入是否可用（6.1.1(24) 版本号够，但实时识别没试过）。

## 三、集成与接口

**11. 分享接收的 `maxFileSupported` 默认值是 0**
- 已确证：默认 0＝不支持该类文件，不显式写就收不到分享内容。`actions` 必须按字面量写 `ohos.want.action.sendData`，Stage 版 `wantConstant` 没有这个常量。
- **未确证**：UTD 该用 `general.image` 还是 `general.png`+`general.jpeg`，官方三份片段写法不一致。

**12. 分享接收的调试方式很反直觉**
- 已确证：分享由系统面板拉起，普通 Debug 抓不到，必须 Attach Debugger to Process → 勾 Show all process → 选进程 → Debug type 选 ArkTS → 看到 `Waiting for debugger` → 再去 QQ 分享。而且 attach **只支持 debug 签名的应用**。

**13. 两种承载形态的选择**
- 已确证：`abilities[].skills` 与 `extensionAbilities[]` 加 `"type":"share"` 官方并列支持，取值 API 相同。
- **未确证**：`want.flags` 是否带 `FLAG_AUTH_READ_URI_PERMISSION`（决定图片 uri 能不能读出来）；分享记录的多选条数与顺序；连续两次分享会不会崩。

**14. QQ 机器人相关**
- 已确证：WebSocket 与 WebHook 官方并列支持，WebSocket 原文「不依赖公网服务器部署，适合个人单机使用」；未认证时机器人只能进「管理员作为群主」的群；「内部体验号码」最多 20 个、不受服务范围限制；个人主体可建 5 个机器人；IP 白名单只支持单个 IPv4、最多 50 个、只影响调用 OpenAPI 不影响接收事件；隐私责任原文写的是由开发者承担全部责任。
- **未调研**：WebSocket 心跳与重连机制、事件推送速率上限、消息去重与乱序处理。

**15. 云端中继的落地细节**
- 已确证：Cloud Foundation Kit 提供云函数/云数据库/云存储/预加载，有免费额度、按量计费，云函数需 `ohos.permission.INTERNET`。
- **未确证**：免表额度与配额的**具体数字**。
- **未调研**：云函数的幂等与重试、bot 进程与云函数之间谁来去重、云数据库的访问控制策略怎么做。

## 四、数据与隐私合规

**16. 群聊内容上云的责任在我们**
- 已确证：QQ 平台不承担机器人服务的数据责任；HarmonyOS 侧应用隐私政策要如实写明采集范围。
- 已定的边界：云上只存十个字段，不存 `raw_text`、发送者、群号、消息号、图片、语音；原文只作云函数内存入参。
- **未确证**：把群聊中的他人消息送进个人云数据库，在审核时是否会被要求说明「是否获得群成员同意」。
- **未确证**：审核是否要求提供「机器人通道可关闭」这一功能开关的证据。

**17. 隐私政策的口径风险**
- 已确证：`createCalendar` 自 API 10 起要求写权限，而 `addEvent` 的 `@permission` 标注是 **`@since 23`** → 目标系统 6.0.2(22) 上写日程本身不要该权限。所以隐私政策**不能写「为了读取你的日程」**。
- **未调研**：应用审核对隐私政策的具体字段要求清单。

**18. 数据本地优先与联网的边界**
- 未调研：离线队列、失败重试策略、数据导出与清理的具体实现（功能在 P0/P1 里，但做法没推演过）。

## 五、界面与交互

**19. 状态管理 V1/V2 不能混用**
- 已确证：新代码用 `@ComponentV2`/`@Local`/`@Param`/`@Event`/`@ObservedV2`/`@Trace`；旧工程才走迁移。混用是编译期问题，早点定下来省事。
- **未确证**：`utils/Theme.ets` 用 `AppStorageV2` 还是普通常量对象、V2 下跨页共享主题怎么传。

**20. 列表性能与组件复用**
- 未调研：任务条数多起来后长列表用 `LazyForEach` 还是 `Repeat`、组件复用怎么做、有没有实测基线。

**21. 多设备与字体缩放**
- 已确证：产品只声明了 `phone`；可用机型表里 Pura 90 是 1320×2856/560dpi、Pura X 外屏 1080×2444、Mate X7 折叠 2210×2416。
- 已定：360vp 宽度下不出现横向滚动。
- **未调研**：字体缩放（用 fp 写的中大字体）会不会撑破布局；折叠屏悬停态要不要管。

**22. 异步状态的真实性**
- 未调研：分享 want 与 AI 解析都是异步，loading/失败/重试三态的呈现规范还没定。

## 六、构建、签名与测试环境

**23. 没有可用真机，而这是最硬的约束**
- 实测：`devecocli device list` → `No active devices`；模拟器 `Pura 90`(6.1.1(24)) 与 `Pura X View`(7.0.0 Beta2) 均 stopped，只能由你在终端启动。
- 已确证：团队真机只有杜俊廷那一台 6.0.2(22)，手机不在开发机上 → **三张验证卡必须串行**，每次换手 20–30 分钟。
- 已确证：AGC 云调试官方存在（17 篇文档），但账号门槛、免费额度、计费方式**未取证**。

**24. 构建产物未签名**
- 实测告警原文：`WARN: Will skip sign 'hos_hap'. No signingConfigs profile is configured in current project.` 产物是 `entry-default-unsigned.hap`（121404 B），能编译、装不了机。
- **未调研**：用学校账号还是个人账号签名、证书怎么申请、云调试对签名有什么要求。

**25. 模拟器的能力缺口比想象中大**
- 已确证：ArkData 原文「RelationalStore 只支持在模拟器使用本地数据库增删改查能力，其余能力不支持」；代理提醒自 API 20 起支持模拟器；语音识别自 6.0.0(20) 起支持模拟器；OCR 与实体抽取不支持。

**26. 工具链版本**
- 实测：`devecocli` 1.2.0；DevEco Studio beta + SDK 26（26.0.0.32, Beta2）；无 `pwsh`，只有 `powershell.exe` 5.1，脚本要写 UTF-8 with BOM 否则中文路径解析失败。
- **未确证**：Beta 版 SDK 与 hvigor 的版本匹配在团队三台机器上是否一致（另两人环境完全没查过）。

**27. 测试与回归**
- 未调研：`ohosTest` 单元测试还没开始，自动化 UI 测试用什么、每周回归谁做、日志怎么从组员手机上取。

## 需要你优先问出答案的三条

如果全链路调研只做三件事，我建议是这三条——它们各自能推翻一块架构：

1. **代理提醒获批后，那台 6.0.2(22) 上到底能不能用**（一台真机、半天，卡住提醒整条主链路）。
2. **AGC HTTP 触发器能不能从公网被 POST**（半天 curl，决定 bot 中继是「零服务器」还是「必须有个常驻主机」）。
3. **分享传来的 `uri` 能不能读出字节**（一次验证，决定图片通道是第 2 周做还是直接砍到第 3 周）。

其余问题都能在开发过程中撞见再解，这三条撞见的代价最大。
