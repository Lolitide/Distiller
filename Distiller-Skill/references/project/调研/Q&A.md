## 平台能力和准入

### 1. （X2）代理提醒在手机上被管控

- **问题对应的需求**
	- 代理提醒：当应用退至后台或进程终止后，系统会代理应用做定时提醒
- **问题描述**
	- 代理提醒功能需要申请，**8 个工作日**反馈申请结果
- **解决方案**
	- **需要提前申请**，并表示为生活/学习类软件

### 2. （X4）提醒条数有硬上限

- **问题对应的需求**
	- 代理提醒：当应用退至后台或进程终止后，系统会代理应用做定时提醒
- **问题描述**
	- **单个普通应用有效/未过期的提醒数量不超过 30 个**。
	- 若未点击提醒上的关闭/CLOSE 按钮，则代理提醒是有效/未过期的；
	- 若点击了关闭按钮，则代理提醒过期。当代理提醒是周期性提醒时……**无论是否点击关闭按钮，代理提醒都是有效的**。
	- 当到达设置的提醒时间点后，代理提醒使用 **Notification Kit** 发布通知，需要授权
- **解决方案**
	- 上层动作有四个，按优先级排：
		1. **周期性提醒一律不用代理提醒**，重复类事项改用 Calendar Kit 的重复日程。这是唯一能彻底避免名额被永久占用的做法。
		2. **发提醒前先清**：每次设置新提醒时调 `getValidReminders()` 拉一遍，对已经过期或已被用户处理的一次性提醒调 `cancelReminder(reminderId)`。用 `notificationId` 做去重，相同 id 的后一条会覆盖前一条，避免重复占位。
		3. **两条路径在 `ReminderService` 内部收口**：代理提醒可用就走它，不可用（未获批、被管控、配额满）就退到通知 + 应用内调度。上层调用方不感知差别。
		4. **客户端自己记一份计数**，接近上限时提示用户，而不是等系统抛 `1700002` 才发现。

### 3. （X0）无障碍读屏不可行

- **问题对应的需求**
	- 通过无障碍功能获取屏幕信息
- **问题描述**
	- Accessibility Kit目前仅支持上述无障碍状态查询和无障碍事件发送能力，不支持通过无障碍节点查询获取界面节点及屏幕内容信息。
- **解决方案**
	- 弃用此方案

### 4. （X0）云服务器申请流程？

四步，前两步是前置条件，不是可选：

1. 登录 AGC →「开发与服务」→ 选中项目。
2. 左侧导航「**云开发（Serverless）> 云函数**」，点「立即开通」。若未设置数据处理位置，系统会弹框强制引导设置；云函数支持启用多个位置，后续在页面下拉框切换。
3. 左侧导航「**云开发（Serverless）> 云数据库**」，点「立即开通」。同样会要求数据处理位置。
4. 创建函数：函数名称 → 触发方式**必须选「事件调用」**（触发器调用走这条）→ 超时时长（同步 55s / 异步 1800s 上限）→ 实例并发 → 运行环境 nodejs 20.x → 内存 500/1000/2000/4000 MB → 触发器页配 HTTP 触发器与认证类型 → 创建。

### 5. （X0）云函数的 HTTP 触发器能不能被 QQ 侧从公网 POST？

HTTP 触发器「**目前仅支持 POST 请求方式**」，认证类型只有「端侧网关认证」与「云侧网关认证」两种，**都是 SDK 调用方**，没有免认证入口。QQ 侧不是 HarmonyOS 客户端、也不在云函数内，所以它拿不到这两种凭据。**结论：QQ 机器人直接 POST 触发 URL 不可行，W1-T11 这个 spike 其实已经有答案了，不用等真机验证。**

## AI 能力

### 1.（X4）OCR 与实体抽取都不支持模拟器

- **问题对应的需求**
	- 通过Core Vision Kit和Natural Language Kit获取信息
- **问题描述**
	- 模拟器上不能跑
- **解决方案**
	- 云真机测试

### 2.（X1）实体抽取有 1000 字符上限

- **问题对应的需求**
	- 通过Natural Language Kit抽取信息
- **问题描述**
	- 文本长度不超过 1000 字符，超了必须切片。群消息长文本是常态，切片与「多段结果怎么合并」都要自己写。
- **解决方案**
	- 先测试长文本抽取效果
	- 再针对长文本做切片、合并算法

### 3.（X1）事项提取没有现成能力

- **问题对应的需求**
	- 通过Natural Language Kit抽取信息
- **问题描述**
	- Natural Language Kit可以抽取时间、地点、人名、手机号、邮箱、URL等信息，可以抽取 wordTag （词性），不能抽取具体事项
	- 判断「这条消息到底要干什么」得自己写规则
- **解决方案**
	- 结合[wordTag（词性）](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/natural-language-word-tag-api)参考，先找现有的应用此 kit 的解析文本项目，如果没有，尝试：人工干预+AI生成规则解析算法

### 4.（X2）OCR 的时间地点会抽错

- **问题对应的需求**
	- 通过Core Vision Kit识别屏幕内容
- **问题描述**
	- 支持识别的语言有：简体中文、英文、日文、韩文、繁体中文五种语言。在使用文字识别服务时，建议图像清晰、文字无遮挡、背景简洁，以获得最佳识别效果，不适用于模糊不清或倾斜严重的图像
- **解决方案**
	- 结合[textRecognition（文字识别）](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/core-vision-text-recognition-api)参考，先尝试OCR识别文字或图像主体，由Natural Language Kit抽取识别的文字信息，然后由AI判断/润色（可选/可写算法），最后由用户确认

### 5.（X2）语音识别卡音频格式

- **问题对应的需求**
	- 通过Core Speech Kit识别用户语音输入内容
- **问题描述**
	- 目前本服务支持的语种为中文，支持的模型为离线
	- 短语音模式最大 60s；长语音模式最大 8h
	- 不支持模拟器
	- 音频格式：`pcm`、16000Hz、单声道、16bit
- **解决方案**
	- 结合[speechRecognizer（语音识别）](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/hms-ai-speechrecognizer)参考
	- **可以直接调用麦克风识别**：设置 `recognitionMode = 0` 即可，但需申请麦克风权限
	- **如果是音频流写入模式**：需严格按 640 字节/20ms 或 1280 字节/40ms 的节奏分片发送，否则识别失败
	- 得到的识别结果`SpeechRecognitionResult`交给AI判断/润色（可选/可写算法），最后由用户确认

## Agent 能力

### 1.（X3）怎么建立用户画像？

做成本地的一张降频表，全部留在端侧。

- **建画像**：信息解析时给每条消息打一个 `类别`（教务 / 活动 / 招聘 / 二手 / 闲聊 …），随任务一起落库。类别是画像的载体。
- **改画像**：用户在任务卡片或消息上长按选「不感兴趣」，写一条 `(类别, 权重, 时间)` 记录；同一类别累积到阈值后下调权重。
- **用画像**：只在两个点生效——**收录**（同类别消息进解析队列的优先级）和**提醒**（同类任务的通知频率/是否合并成一条）。
- **初始画像**：首启引导页可选勾选「我关心：教务 / 招聘 / 活动」，不勾也能用，靠后续行为补。
- **数据边界**：端侧自足、不上传，因此不进隐私政策的「向第三方共享清单」。

**必须写进文档的边界**：只能降低知了自身的收录与提醒频率，**不能替用户屏蔽 QQ 群消息**，机器人也没有删消息的能力。不要写成「帮你屏蔽不想看的信息」。

### 2.（X0）怎么创建日程？

走 Calendar Kit，不用一键服务、不用企业账号。

| 层级   | 字段                              | 要求                        |
| ---- | ------------------------------- | ------------------------- |
| 日历账户 | `CalendarConfig.enableReminder` | 必须 `true`                 |
| 日程事件 | `Event.reminderTime`            | 分钟数组如 `[10]`；**不填 = 不提醒** |
| 日程事件 | `Event.startTime`               | **秒数与毫秒数必须都为 0**          |

### 3.（X0）怎么创建备忘？

- **问题对应的需求**
	- 自动创建备忘/待办
- **问题描述**
	- **系统备忘录完全没有开放能力，这条路彻底不通**
- **解决方案**
	- 弃用此想法
	- 自己做备忘、待办页面

### 4.（X0）怎么管理用户的日程、备忘？

| 任务事件      | 对本地表           | 对系统日历                                      |
| --------- | -------------- | ------------------------------------------ |
| 确认且带 DDL  | 落库，存 `eventId` | `addEvent` 写一条，带 `reminderTime`            |
| 改时间       | 更新 `due_at`    | 先 `deleteEvent(旧 eventId)`，再 `addEvent` 新的 |
| 完成 / 删除   | 置状态位           | `deleteEvent(eventId)`                     |
| 用户在系统日历手删 | **不动任务**       | 下次同步查不到 → `eventId` 置空 + 提示「日历项已被移除」       |

## 集成与接口

### 1.（X0）分享功能怎么实现？

- **问题对应的需求**
	- 通过Share Kit获取到用户分享给APP的内容
- **问题描述**
	- 知了怎么被分享面板认成可接收方？
		- 分享面板按目标应用在 `module.json5` 里声明过的数据类型来推荐应用
			- `UTD` 写 `general.image` 还是逐一列举 `general.jpeg` / `general.png`
			- `maxFileSupported` 不写会怎样
			- `exported` 与 `entities` 该怎么处理
	- 点进来之后内容从哪取？
		- 分享由系统拉起应用，不走应用自己的启动流程。要回答的是：
			- 用哪种应用形态承载（UIAbility 还是 ShareExtensionAbility），取值 API 是否相同
			- 在哪个生命周期能拿到有效的 want
			- 拿到的数据是什么结构，文本和图片分别落在哪个字段
			- 分享的数据量有没有上限，超限时报什么、怎么兜底
	- 这件事怎么被看见和验证？
		- 分享由系统面板触发，`devecocli run` 抓不到这个入口。要回答的是：
			- 用什么方式调试才能断在取值代码上
			- 有哪些点只能靠真机实测拿到答案（URI 读取权限、连续两次分享、多选顺序）
- **解决方案**
	- 结合[systemShare（分享）](https://developer.huawei.com/consumer/cn/doc/doccenter-references/api/share-system-share)参考
		- **声明侧**：走 UIAbility 形态，注册一个独立的 `ShareAbility`，不改造 `EntryAbility`。文本与图片各声明一条接收规则，图片用 `general.image` 覆盖全部图片类型。`exported` 必须显式打开，否则面板里看不到。
		- **取数侧**：在应用启动入口取 want，拿到的是一组记录，按 `utd` 分两路：文本走 `content` 字段，图片走 `uri` 字段。若返回记录超限的错误码，改从 want 自带的 uri 取——这是官方指定的兜底路径。
		- **与主链路的接缝**：产出统一成一个「待确认草稿」，文本和图片走同一个确认页。图片先经本地文件解码成位图，再交给 OCR，这样 OCR 不需要知道分享的存在，粘贴图片和分享图片可以共用同一段实现。
		- **验证侧**：用 Attach 方式挂上调试器，等进程进入等待状态后再去 QQ 里执行分享。URI 读取权限、连续两次分享、多选顺序这三条文档答不了，列进真机验证清单一次做完。

### 2.（X0）QQ-bot的上云方式？

- **问题对应的需求**
	- QQ-bot支持WebSocket 与 WebHook
		- WebSocket「不依赖公网服务器部署，适合个人单机使用」
			- 未认证时机器人只能进「管理员作为群主」的群；
			- 「内部体验号码」最多 20 个、不受服务范围限制；
			- 个人主体可建 5 个机器人；
			- IP 白名单只支持单个 IPv4、最多 50 个、只影响调用 OpenAPI 不影响接收事件；
			- 隐私责任由开发者承担全部责任。
	- 通过WebSocket方式将信息上传到云服务器
- **问题描述**
	- 长连接的心跳与断线恢复怎么定义
		- WebSocket 建立后服务端下发 `OpCode 10 Hello`，携带心跳周期。客户端按周期发 `OpCode 1`，收到 `OpCode 11` 确认。断开后短时间内重连会补发遗漏事件，此时不能重新鉴权，要发 `OpCode 6 Resume` 并携带上次处理过的序号。
			- 心跳周期是固定的还是每次连接下发？
			- 断线后什么时候该 Resume 什么时候该重新 Identify？
			- 事件补发完了怎么知道？
	- 事件推送有没有速率约束
		- `/gateway/bot` 返回 `session_start_limit`，含总量、剩余、重置周期与最大并发。
			- 单个机器人能建几条连接？
			- 同一时刻能并发几条？
			- 事件本身是否会被限流丢弃？
	- 重复事件与乱序怎么识别
		- Resume 会补发事件，网络抖动也天然会造成重复。
			- 有没有可以作为幂等键的字段？
			- 有没有可作为排序依据的字段？
			- 要不要自己维护去重表？
- **解决方案**
	- **文档**：[WebSocket 方式](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/event-emit/websocket.html)、[使用 Websocket 接入](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/reference.html)
	- **心跳与重连**：心跳周期不写死，从 Hello 里读，配一个漏发检测（连续几个周期没收到 ACK 就主动重连）。重连走「优先 Resume，特定错误码转 Identify」的分支——协议规定了哪些错误码可以重试 Resume、哪些只能重试 Identify，按这张表实现即可，不用自己判断。本地持久化最新的序号，进程重启也能续上。
	- **连接数**：这个规模的项目用 `[0, 1]` 单分片。连接数上限从接口返回里读，不写死在代码里。
	- **去重与排序**：事件本身带事件 id、序号、以及群消息自己的消息 id 和时间戳，三者都能用。以事件 id 做去重键、以消息 id 做业务幂等键，落库时做成唯一约束，重复事件直接丢弃而不是报错。补发阶段服务端是按序号顺序推的，但不同消息之间没有顺序承诺，所以排序以消息自带的时间戳为准，不依赖到达顺序。
	- **对项目的实际影响**：机器人只需接收不需要发送。官方已停止主动推送能力，被动回复也有严格时限，但接收事件不受影响——这条链路的职责就是「收到群消息 → 中继」，不回复。

### 3.（X0）云端中继怎么实现？

- **问题对应的需求**
	- Cloud Foundation Kit 提供云函数/云数据库/云存储/预加载，有免费额度、按量计费，云函数需 `ohos.permission.INTERNET`
	- 通过Cloud Foundation Kit实现云端中继，把从QQ-bot传来的信息内容发送到云端，再由APP拉取下来处理。
- **问题描述**
	- 云函数的幂等与重试由谁负责
		- 平台是否保证「最多执行一次」？
		- 失败后是否自动重试？
		- SDK 有没有幂等键参数？
		- 重复执行会不会写出两条记录？
	- bot 进程与云函数谁去重
		- 去重放在 bot 侧、云函数侧还是两侧都做？
		- 用什么字段做键？
		- 重复到达时是丢弃还是报错？
	- 云数据库的访问控制怎么做
		- 写入权限按什么维度控制？
		- 不接账号系统能不能限定「只有云函数能写」？
		- 安全规则在 AGC 侧怎么配？
- **解决方案**
	- **幂等与重试：不做在平台层，做在数据层。** 在云数据库的对象类型上给幂等键加唯一约束，云函数先按幂等键查一次、不存在再写。写操作做成「查询 + 插入」两步，不依赖事务。
	- **去重分两层，各管一件事。** bot 进程侧用事件 id 与消息 id 做本地去重，挡住重连补发造成的重复；云函数侧用 `client_task_id` 做数据库层幂等，挡住并发与重试造成的重复。
	- **访问控制走对象类型的角色权限。** 官方框架是「支持 APP、用户和服务三重认证」加「基于角色的权限管理机制」。数据库写入受对象类型的权限配置约束，权限不足报 `2001015: permission denied`，报错信息本身就指向「检查操作的对象类型的权限配置」。云存储侧同理，403 Forbidden 的官方解法之一是「将安全策略配置为始终可读写」，另一种是配 `AuthProvider` 拿用户凭据。
	- **落到我们的架构上**：云数据库只给云函数写，客户端只读——这条如果 AGC 侧能做，就省掉了「客户端误写」的整类风险。

### 5.（X0）QQ-bot 怎么部署？

#### 一、架构定版：WebSocket + 本地 bot + 本地中转

![本地架构流程图](diagram1-local-architecture.excalidraw)

**bot 部署在开发者的常驻 PC 上**，理由四条：

1. WebSocket 是出站连接，PC 不需要公网 IP、域名、备案。
2. bot 与中转同机，写入走本地回环，少一跳、少一处故障点。
3. 消息原文不出局域网，隐私政策可以直接写「群消息原文不上传任何第三方服务器」——这比走云端中转干净得多。
4. 零成本。

对应档位选择：**课程项目用「PC 常驻 + 局域网直连」**。

>[!important] 先不用Cloud Foundation Kit 
>测试阶段与MVP阶段不使用，最多租用云服务器测试，因为涉及ICP备案等问题

#### 二、职责划分：bot 只搬运，解析在 App

| 环节            | 归属      | 理由                                         |
| ------------- | ------- | ------------------------------------------ |
| 连 QQ、收事件      | bot 进程  | 长连接必须在常驻机器上                                |
| 原样转发 + 去重     | bot 进程  | 无业务逻辑                                      |
| 类别标注、实体抽取、结构化 | **App** | 这是 HarmonyOS 课程项目的核心能力，要落在 App 里；也保证原文不出端侧 |
| 落库、待确认、提醒     | App     | 单一真值源在本地任务表                                |

#### 三、要走的流程

1. **QQ 开放平台**注册机器人 → 拿 `AppID` / `AppSecret`。鉴权用 `AccessToken`（格式 `QQBot {AccessToken}`），旧的 `Token` 方式官方已标「已弃用」。
2. **申请 `GROUP_AND_C2C_EVENT (1<<25)`** 事件权限，并在机器人设置里打开「接收所有消息」。这一步是外部审批，**立刻发起**，不要等到要做的时候才发现卡住。
3. **bot 进程**用腾讯官方 SDK DEMO 起步（Go `botgo` / Python `botpy` / Node.js `bot-node-sdk`，文档直接给了这三个），实现 Hello → Identify → 心跳 → Resume 四段。
4. **中转服务**：`POST /ingest` 写入 + `GET /messages?since=` 增量读取，落本地 SQLite；绑定局域网 IP，加一个共享 token 防同网他人读取。
5. **App 侧**：`ohos.permission.INTERNET`，`@ohos.net.http` 轮询拉取，前台 10s / 后台拉到就停。

#### 四、风险与降级

| 风险                 | 降级方案                                                                    |
| ------------------ | ----------------------------------------------------------------------- |
| `1<<25` 权限申请不通过    | 退回 `GROUP_AT_MESSAGE_CREATE`（只能收@），产品口径改为「@知了 记一下这条通知」                  |
| 目标群的通知走的是「群公告」而非消息 | 让群管理员发布时顺手在群里发一条同名消息；或把口径从「群公告」改为「群里发的通知」                               |
| PC 无法常驻            | 演示前手动起进程；长期方案再挪云主机                                                      |
| 跨网演示（手机不在同一 WiFi）  | bot + 中转整体挪到一台最小云主机，代码零改动（bot 本来就只做出站连接）。**该云主机的备案口径需按所选云厂商规定确认，本轮未取证** |

>[!important] 总结
>- 选 WebSocket 模式后 bot 放哪都行、不需要公网和备案，方案就定成「开发者 PC 常驻跑 bot、同机跑中转、App 局域网拉取，解析全在 App 侧」
>- bot必须有权限 `GROUP_AND_C2C_EVENT (1<<25)`「接收所有消息」，同时确认目标群的通知是「消息」而不是「公告」

**收益**：App 不再需要和 PC 同网。

**前提**：bot 位置不变（云函数不能持长连接，bot 仍需常驻 PC）；新增签名门槛，丢掉「原文不上云」卖点。

#### 一、架构

![云架构流程图](diagram2-cloud-architecture.excalidraw)

#### 二、关键决策

| 第 4 周演示前 | 演示环境无法保证同 WiFi 时换 |
| 确定上架时 | 必须换，连带办服务器和备案 |

#### 七、风险与降级

| 风险 | 降级方案 |
| --- | --- |

## 数据与隐私合规

### （X0）怎么确保上云的信息合法合规？

- **问题对应的需求**
	- QQ 平台不承担机器人服务的数据责任；HarmonyOS 侧应用隐私政策要如实写明采集范围。
	- 云上只存十个字段，不存 `raw_text`、发送者、群号、消息号、图片、语音；原文只作云函数内存入参。
- **问题描述**
	- 群聊里别人的消息进云端，「获得群成员同意」这件事审核会不会问
		- 审核时会不会被要求说明这些消息的来源合法性？
		- 要不要提供群成员同意的证据？
		- 我们能不能说明清楚这批数据的性质？
	- 机器人通道可关闭，审核要不要看证据
		- 审核是否会主动检查这个开关？
		- 检查到什么程度？
		- 开关要不要在隐私政策里对应写一句？
	- 隐私政策到底要写哪些字段
		- 审核对隐私政策的字段有没有成文的清单？
		- 有哪些是硬要求？
		- 我们的场景需要额外写什么？
	- 离线队列、失败重试、导出与清理怎么做
		- 断网时怎么排队？
		- 恢复后怎么重试？
		- 失败几次算放弃？
		- 用户导出的数据从哪来？
		- 清理要清哪几处？
- **解决方案**
	- **一、「群成员同意」不会被单独问，但会被「收集目的与范围」这条框架兜住**
	  官方的隐私规则里没有针对群聊消息的专门条款。真正会落下来的是三条通用规则：**一，隐私政策「应描述收集个人信息目的方式和范围」；二，数据收集要「与目的相关、适当、必要」；三，要有「数据处理选择和控制」**。任何涉及他人信息的采集，都会被这三条套住。
	  对我们有利的地方在于：**用户与机器人是同一侧。** 机器人是用户自己建的（个人主体可建 5 个机器人），拿到「管理员作为群主」的群里，转发的是群里公开可见的文本。整条链路里没有第二个数据主体被我们的应用直接处理——我们不是「拿别人的数据」，而是「用户把群里看到的信息整理进自己的待办」。所以合规表述应该落在**通道级告知**上，而不是去论证群成员同意：
		  「开启机器人通道后，机器人在您所在的群聊中收到的新消息会被提取为待办事项。该通道默认关闭，您可随时关闭。开启前请确认您有权使用群内信息。」
	  这句同时满足了「明示范围」和「最小化」两条要求，而且它描述的是事实，不需要找谁补签同意。

	- **二、可关闭开关审核不会主动验证，但你要么把它做实、要么别提**
	  官方的三要素规则（明示 + 显著标识 + 关闭选项）只针对「定向推送」，我们不做定向推送，所以不适用。但它示范了一个模式：**一旦在隐私政策里宣称某个能力可关闭，审核会按你写的去核。** 「应用内不存在定向推送功能，请删除用于显著区分定向推送功能的相关内容」——反过来说，写了就该能兑现。
	  所以结论是：把机器人通道开关做成设置页里一个真实的、点了就停止拉取的开关，包括停止 bot 进程侧的中继；然后才在隐私政策里写「可随时关闭」。**不要写「可随时删除云端数据」除非云端删除真的通了。** 

	- **三、隐私政策有一份成文的字段清单，共八项**
	  这是最可交付的一条，见下面的证据表。要额外强调的是**两个容易漏掉的前置条件**：
		- **端云一体化开发的应用属于「非单机应用」，必须做 ICP 备案。** 官方 FAQ 原文：「使用端云一体化开发中的云数据库的 App **不属于单机应用，必须进行 ICP 备案**。」而且「端云一体化**没有备案码**，因此需要准备一个服务器，用于存放诸如隐私或用户协议」。这一条把「我不建服务端」这个说法彻底推翻了——服务端可以不用来自建业务逻辑，但**托管隐私政策这件事本身就需要一个可公网访问的地址**。
		- **隐私政策必须是 https 的 URL，不能是本地文件。** 标准化隐私声明托管服务要求隐私协议 url 为 https，`appgallery_privacy_link_privacy_statement` 字段注释写明「必须是 https 网址」。静态页面托管也行，但不能是 rawfile 里的一个 html。

	- **四、离线队列与清理按「能力边界」设计，不按「功能列表」设计**
		- **离线排队**：`preferences` 与 `relationalStore` 都是本地能力，断网不影响写入。所以离线时不做特殊处理，本地照写、状态标成「待同步」，靠一个后台的同步队列在恢复后重放。网络状态用 Network Kit 的连接管理监听，不用轮询。
		- **重试**：云函数错误码里没有任何幂等承诺，所以重试必须建立在幂等键之上。`client_task_id` 加唯一约束是先决条件，然后才谈重试次数。建议定成「有限次重试 + 超过次数落到待同步列表 + 由用户手动触发」，不做无限后台重试——无限重试在演示时看不出来，在审核的稳定性测试里会变成耗电与后台活动问题。
		- **导出**：从 RDB 全量读出来序列化成 JSON，写到沙箱文件，再交给系统分享面板让用户自己选去处。我们不需要自己实现分享逻辑。
		- **清理**：要清三处，缺一处就是「说一套做一套」——本地 RDB、`preferences`（设置与状态）、云端对象。云端这条是唯一需要联网的，也就意味着清理功能在网络不可用时要给明确提示，而不是假装删掉了。系统级缓存清理不需要我们操心，沙箱缓存有既有的清理机制。
		- **备份恢复**：模板里已经带了 `EntryBackupAbility`（`type:"backup"` + `ohos.extension.backup` metadata）。既然已经有备份扩展，导出与备份可以共用同一份数据模型，不必各写一套。

## 界面与交互

### （X0）有哪些页面？需要做哪些功能？

- 仅两页
	- 任务列表页
		- 包含所有待办事项
		- 默认按照时间顺序显示
		- 可以按照标签筛选任务
		- 为效率仅显示两行：第一行为任务的名称，第二行为**一个**属性+可选项
			- 属性可以是：个人、比赛、作业……
			- 属性可以自定义添加和编辑
			- 可选项可以是：“还有 xx 天截止”  ”距下一次 xx 天“……
			- 任务的类型（DDL、周期性等）决定了可选项类型
		- 任务项最左端是勾选框
		- 任务项最右端是是否添加提醒的按钮
		- 点击任务项可以查看详情
			- 详情包括任务名称、任务备注、截止日期、下一次周期日期、来源、完成耗时、重要程度等
		- 从一个最醒目按钮/长距离上滑添加任务（长距离下滑可以刷新任务列表，不冲突）
		- 添加任务时可以编辑的内容和显示详情统一
		- 需要考虑的任务类型
			- 单一DDL
			- 周期性DDL
			- 打卡性任务
			- 有多步的任务（高度相关多合一）
		- 需要设置的日程
			- 有DDL的任务
		- 需要设置的提醒
			- DDL将近的提醒（1天、2天、3天、5天、7天）
			- 可以评估重要性选择性提醒
	- 设置页
		- 包含所有设置项
		- 包含项目关于页与解释
		- 包含用户隐私政策与权限撤回
		- 设置项分块显示
		- 权限设置不能在最开始就获取
