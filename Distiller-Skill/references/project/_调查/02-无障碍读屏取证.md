# 02 · 无障碍读屏（AccessibilityExtensionAbility）接入的可行性、能力边界与审核要求

> **取证目标环境**：HarmonyOS 6.0.2(22) 真机（手机）
> **本机 SDK**：HarmonyOS 26.0.0 Beta2
> **取证日期口径**：以本机 `devecocli docs` 本地文档库 + 本机 SDK `.d.ts` 声明文件 + 华为开发者官网/消费者官网正文为准

## 0. 取证结论（先读这一段）

| # | 问题 | 结论 | 强度 |
| :-- | :-- | :-- | :-- |
| 1 | 能力入口（module.json5 + profile + 权限） | **配置形式完全存在且可声明**：`type: "accessibility"` + `metadata.name = "ohos.accessibleability"` + `$profile:accessibility_config`；`accessibility_config.json` 只需 `accessibilityCapabilities` 一项。**配置本身不需要申请任何权限**（官方完整片段里没有 `requestPermissions`） | 已取证（官方开发指南原文） |
| 2 | 能读到什么 | `AccessibilityExtensionContext`（`getWindowRootElement`/`getFocusElement`/`getWindows`/`findElement`）+ `AccessibilityElement.attributeValue(key)`，文本字段名为 **`text`**（string，`ElementAttributeValues` 内）与 **`accessibilityText`**（string，since 12）；另有 `contents`/`description`/`hintText`/`lastContent`/`error` | 已取证（SDK 声明 + 官方 API 参考） |
| 2b | 这整套 API 现在还能用吗 | **不能当作可用能力**：`AccessibilityExtensionContext` 的**全部 7 个方法**与 `AccessibilityElement` 的**全部方法**均标注「从API version 12开始废弃」；`onConnect`/`onDisconnect`/`onAccessibilityEvent`/`onKeyEvent` 四个回调同样从 API 12 废弃 | 已取证（SDK 声明 + 华为官网 API 参考） |
| 2c | 废弃原因（关键） | 华为官网本地文档库对四个回调的 note 原文：**「从API version 9开始支持，从API version 12开始废弃，系统不再开放相关能力。」** | 已取证（documentId 原文） |
| 3 | 能读到谁 | 设计上 `setTargetBundleName` 可指定「关注应用」，**不设置时默认接收所有应用的无障碍事件** → 即设计上可跨应用。但 API 12 起整套能力被收回，**在 HarmonyOS 6 上第三方应用实际不可用**；华为消费者官网原文亦明确「升级后第三方读屏软件不支持屏幕朗读」 | 已取证（API 参考 + 消费者 FAQ） |
| 4 | 能否主动「刷」聊天记录 | **能力设计上偏被动事件驱动**（回调名为 `onAccessibilityEvent`，上下文对象只能在扩展被连接后拿到），**并且**该能力自 API 12 起已废弃；`getWindowRootElement()` 只能拿到「当前活跃窗口」的根节点（或指定 windowId 的根节点），没有跨应用批量化遍历的入口 | 已取证（API 参考原文） |
| 5 | 上架审核 | 《应用审核指南》有直接命中的红线条款：**「2.10 应用不得诱导、欺骗用户，在用户主观不了解操作后果情况下，执行有损系统和应用安全的操作，包括但不限于下载或安装系统root工具、激活设备管理器选项、开启辅助功能等。」**；另有 7.17/7.18/7.19 权限最小化与目的告知要求。**没有**找到「必须是无障碍辅助工具类应用才能申请无障碍权限」这类专门条款（未取证） | 已取证（华为官网《应用审核指南》正文） |
| 6 | 本机 SDK 26.0.0 Beta2 是否支持 | **声明文件层面支持**（`@kit.AccessibilityKit.d.ts` 导出了 `AccessibilityExtensionAbility` / `AccessibilityExtensionContext` / `AccessibilityElement` 等，`ElementAttributeValues` 里已出现 `since 18` 的新字段），**但接口全部带 `@deprecated since 12`**；`ohos.permission.ACCESSIBILITY_EXTENSION_ABILITY` 在权限总表内 `since 20`、`system_basic` | 已取证（SDK 声明 + 权限定义 JSON） |

**对《知了》的工程含义（基于上述事实推导）**：

- 「读屏读取 QQ/微信聊天记录」这条通道，**在当前 HarmonyOS 6.0.2(22) 真机 + 三方应用身份下不可用**：能力入口与配置形式存在，但承载能力的全部 API 自 API 12 起被系统收回，且华为消费者官网对第三方读屏软件有明确的「不支持」口径。
- 只有**系统应用**（APL ≥ system_basic + 系统签名 + 申请 `ohos.permission.ACCESSIBILITY_EXTENSION_ABILITY`）才能走 API 20 起的那套系统接口（`onAccessibilityConnect`/`onAccessibilityDisconnect`/`onAccessibilityEventInfo`/`onAccessibilityKeyEvent`）。
- 因此 P2 通道应按「**实验性、默认关闭；且不要在 HarmonyOS 6 真机上承诺任何读屏能力**」处理；第 1 周真机验证的预期结果是**接口可编译、运行期无法获得有效数据/无法被系统连接**。

## 2. 能力入口：`AccessibilityExtensionAbility` 的声明与配置

### 2.1 `type` 取值 —— `accessibility`（合法）

本机 module.json5 的 JSON Schema（`hms/toolchains/modulecheck/module.json:614`）中 `extensionAbilities.properties.type.enum` 含 `"accessibility"` 字符串，**schema 层面未对 `accessibility` 附加系统应用限制标注**（同 enum 中 `service`/`dataShare` 等项在官方文档里才写「三方配置不生效/需要特权」）。

`[documentId] 开发指南/开发基础知识/应用配置文件/module_json5配置文件/module-configuration-file` 的 `#### type标签` 表格中，原文一行：

> | accessibility | 辅助能力的ExtensionAbility。 |

【开发指南-md】原文进一步说明：

> `type`标签要按照与无障碍子系统的约定进行配置，需要注意的是该值固定为`accessibility`，否则将无法正常连接。

### 2.2 `module.json5` 完整配置片段（官方原文，照抄）

【开发指南-md】给出的完整 `extensionAbilities` 片段：

```json
"extensionAbilities": [
  {
    "name": "AccessibilityExtAbility",
    "srcEntry": "./ets/AccessibilityExtAbility/AccessibilityExtAbility.ets",
    "label": "$string:MainAbility_label",
    "description": "$string:MainAbility_desc",
    "type": "accessibility",
    "metadata": [
      {
        "name": "ohos.accessibleability",
        "resource": "$profile:accessibility_config"
      }
    ]
  }
]
```

原文对四个标签的说明：

> `srcEntry`标签为`extensionAbility`对应的路径。`label`标签为`extensionAbility`在已安装扩展服务列表中显示的名称。`description`标签为`extensionAbility`在已安装扩展服务详情页的帮助信息。`type`标签要按照与无障碍子系统的约定进行配置，需要注意的是该值固定为`accessibility`，否则将无法正常连接。

**要点**：

- `metadata.name` 的**精确取值是 `ohos.accessibleability`**（不是 `accessibility`、也不是 `accessibilityCapabilities`）。
- `metadata.resource` 写法为 `$profile:accessibility_config`，即指向 `src/main/resources/base/profile/accessibility_config.json`。
- **该片段中没有 `requestPermissions` 字段**，全文（除外链外）也没有出现任何 `ohos.permission.*`。
- 【开发指南-md】另有两句约束原文：
  > 一个工程仅支持创建一个无障碍扩展服务。
  > 如需新增独立的无障碍扩展服务应用，在DevEco Studio中新建一个API 9以上的Stage工程。

### 2.3 profile 文件 `accessibility_config.json` 的结构

文件名与路径：`src/main/resources/base/profile/accessibility_config.json`。官方给出的字段结构原文：

```json
{
  "accessibilityCapabilities": [
    "retrieve",
    "gesture",
    "touchGuide"
  ]

```

原文说明：

> 在该文件中声明此无障碍扩展服务具备的[能力类型](../reference/apis-accessibility-kit/js-apis-accessibility.md#capability)

取值集即 `accessibility.Capability`（`openharmony/ets/api/@ohos.accessibility.d.ts:164` / 【华为ax】第 142 行）：

```ts
type Capability = 'retrieve' | 'touchGuide' | 'keyEventObserver' | 'zoom' | 'gesture';
```

【华为ax】对每个取值的中文原文解释：

| 取值 | 官方说明（原文） | 来源（【华为ax】行号） |
| :-- | :-- | :-- |
| `'retrieve'` | 具有检索窗口内容的能力。 | L154 |
| `'touchGuide'` | 具有触摸浏览模式的能力。 | L155 |

【权限清单-md】（华为/OpenHarmony 官方「可使用ACL申请的系统应用可用权限（系统授权）」页）原文：

> **权限级别**：system_basic
> **授权方式**：系统授权（system_grant）
> **支持设备**：General

> **起始版本**：20

- `ohos.permission.READ_ACCESSIBILITY_CONFIG` / `ohos.permission.WRITE_ACCESSIBILITY_CONFIG`：均 system_basic + system_grant + ACL true + **起始版本 9**。
- `ohos.permission.QUERY_ACCESSIBILITY_ELEMENT`（允许批量查询无障碍节点）：**system_core** + system_grant + ACL true + 起始版本 11。
- 同页还有 `ohos.permission.GET_SCREEN_CONTENT`（允许应用获取屏幕上的内容）：**system_core** + 起始版本 20；`ohos.permission.SIMULATE_USER_INPUT`（允许应用模拟用户操作）：**system_core** + 起始版本 20。

**关键判定**：

1. 三方可声明的 `accessibility` 扩展**本身不要求权限声明**（2.2 的官方片段无 `requestPermissions`）。也就是说「声明一个无障碍扩展」这个动作本身不卡权限。
2. 但**要真正拿到节点数据**（`retrieve` 路径）依赖的权限全部是 `system_basic` / `system_core` 级系统权限。
3. 【受限开放权限】（华为给三方应用开放的受限权限清单页）中**没有** `ACCESSIBILITY_EXTENSION_ABILITY`（在该页 grep `ACCESSIBILITY|无障碍|辅助` 仅命中一条与游戏 AI 陪玩截屏辅助相关的描述，非本能力）→ 该权限**不在三方应用可走 ACL 申请的白名单里**。

## 3. 能力边界：能读到什么

### 3.1 `AccessibilityExtensionContext` 方法与废弃状态（硬证据）

`openharmony/ets/api/application/AccessibilityExtensionContext.d.ts:35`：

```ts
declare class AccessibilityExtensionContext extends ExtensionContext
```

（`@since 9`；【华为AxEC】第 167 行给出可用设备：`phone 12+ | 2in1 13+ | tablet 12+ | wearable 18+`。）

| 方法（SDK 声明原文签名） | SDK 行号 | 废弃状态 | 官方说明（原文） |
| :-- | :-- | :-- | :-- |
| `setTargetBundleName(targetNames: Array<string>): Promise<void>` | :68 | @since 9，**@deprecated since 12** | 「设置关注应用的包名。设置后，服务仅接收关注应用的无障碍事件；未设置时默认接收所有应用的无障碍事件；取消关注应用时传空数组。」（【华为AxEC】L188） |
| `getFocusElement(isAccessibilityFocus?: boolean): Promise<AccessibilityElement>` | :115 | @deprecated since 12 | 「获取当前焦点元素」；抛 `9300003 - No accessibility permission to perform the operation.` |
| `getWindowRootElement(windowId?: number): Promise<AccessibilityElement>` | :161 | @deprecated since 12 | 「获取指定窗口的根节点元素」；`windowId` 说明原文：「指定窗口的编号，**未指定则从当前活跃窗口获取**。」（【华为AxEC】L430） |
| `getWindows(displayId?: number): Promise<Array<AccessibilityElement>>` | :207 | @deprecated since 12 | 获取所有窗口的根节点元素 |
| `injectGesture(gesturePath: GesturePath): Promise<void>` | :239 | @since 9，**@deprecated since 10** | @useinstead `injectGestureSync` |
| `injectGestureSync(gesturePath: GesturePath): void` | :253 | @since 10，**@deprecated since 12** | 【华为AxEC】L707 原文：「从API version 9开始支持，从API version 10开始废弃。建议使用injectGestureSync替代，**但该替代接口从API version 12开始也已废弃**。」 |

> **结论**：`AccessibilityExtensionContext` **现存 7 个方法在 API 12 起全部废弃**，没有任何一个「未废弃」的替代方法（官方 API 参考页面上每个方法标题都带 `(deprecated)` 上标，【华为AxEC】行号见 L171 / L218 / L266 / L317 / L364 / L413 / L464 / L511 / L560 / L608 / L652 / L698 / L752 / L802）。

### 3.3 文本内容字段名 —— 是 `text`，不是 `content` / 不是 `attributeValue`

**`attributeValue` 是方法名，不是属性名**。真正的属性集合是 `ElementAttributeValues`（`openharmony/ets/api/application/AccessibilityExtensionContext.d.ts:485` 起，`@since 9`）。其中与「文本内容」相关的属性（属性名 + 类型 + SDK 行号 + 官方说明原文）：

| 属性名 | 类型 | SDK 行号 | 官方说明（原文） |
| :-- | :-- | :-- | :-- |
| **`text`** | `string` | :821 | **「元素的文本。」**（【华为AxEC】L83） |
| **`accessibilityText`** | `string` | :910（**@since 12**） | 「元素的无障碍文本信息。」（【华为AxEC】L45） |
| `contents` | `Array<string>` | :563 | 「内容列表。根据实际场景设置，无特殊限制。」（【华为AxEC】L53） |

| `hintText` | `string` | :622 | 「提示文本。」（【华为AxEC】L60） |

>
> 旁证：官方 `accessibilityextensionability.md` 示例代码中 `wantedAttribute: ElementAttributeKeys[] = ['bundleName', 'text', 'description', 'windowId']`（【开发指南-md】），即官方示例本身就用 `text` 取文本。

## 4. 能读到谁：能否读第三方应用（QQ/微信）窗口文本

### 4.1 设计上的答案：可以跨应用（官方 API 原文）

【华为AxEC】`setTargetBundleName` 参数说明原文：

> 设置关注应用的包名。**设置后，服务仅接收关注应用的无障碍事件；未设置时默认接收所有应用的无障碍事件**；取消关注应用时传空数组。

→ 即：**按设计，无障碍扩展服务默认可接收「所有应用」的无障碍事件**，也可以显式指定「关注」某个第三方应用的包名。`Capability` 中 `'retrieve'` 的官方释义即「**具有检索窗口内容的能力**」。这两条合起来说明：**读第三方应用窗口内容在设计上是允许的、且是该能力的核心用途**（系统读屏本身就是全应用生效）。

### 4.2 现实中的答案：在 HarmonyOS 6 上第三方应用拿不到

三条互相独立的官方证据：

**证据 A（华为本地文档库 note 原文）** ——【AxEA】`onConnect` / `onDisconnect` / `onAccessibilityEvent` / `onKeyEvent` 四节的 note 均为：

> 从API version 9开始支持，从API version 12开始废弃，**系统不再开放相关能力**。

**证据 B（华为官网 API 参考）** ——【华为AxEC】中 `AccessibilityExtensionContext` 与 `AccessibilityElement` 的**每一个方法**都标注「从API version 12开始废弃」。

**证据 C（华为消费者官网 FAQ）** ——标题「第三方读屏应用不能进行屏幕朗读？」，适用产品「手机，平板」，适用版本含 **HarmonyOS 6.0**，正文原文：

> 您好，为了更好地提升屏幕朗读的用户体验，防止恶意软件滥用无障碍权限，影响您的用机安全，**升级后第三方读屏软件不支持屏幕朗读**，我们会持续优化提升屏幕朗读的读屏体验，丰富无障碍功能。

（来源：https://consumer.huawei.com/cn/support/content/zh-cn16023535/ ）

### 4.3 系统应用侧的存在形式（API 20 起，三方不可用）

【AxEA-sys-md】（`js-apis-application-accessibilityExtensionAbility-sys.md`，标题「(辅助功能扩展能力)(系统接口)」）原文：

> 本模块首批接口从API version 20开始支持
> 当前页面仅包含本模块的系统接口。其他公开接口参见[@ohos.application.AccessibilityExtensionAbility]。

其系统接口清单（**每个都标「系统接口：此接口为系统接口」「需要权限：ohos.permission.ACCESSIBILITY_EXTENSION_ABILITY」，错误码含 `202 Permission verification failed. A non-system application calls a system API.`**）：

- `onAccessibilityConnect(): void`
- `onAccessibilityDisconnect(): void`
- `onAccessibilityEventInfo(event: AccessibilityEventInfo): void`
- `onAccessibilityKeyEvent(keyEvent: KeyEvent): boolean`

同页定义系统版 `AccessibilityEventInfo { eventType: AccessibilityEventType; target?: AccessibilityElement; timeStamp?: number; extraInfo?: string }`。

**判定**：API 20 起无障碍扩展的**回调入口被改造成系统接口**；三方应用能碰到的只有 API 9 那套公开回调，而那套自 API 12 起全部 `@deprecated`（本机 SDK `device-define/api-version/AccessibilityKit.json` 中这些 API 的 `isSystemApi` 仍为 `"false"`，即**在声明上仍是公开 API，但已被标注废弃**）。

### 4.4 「受限于目标应用是否暴露无障碍节点」这条约束

**未取证**：官方文档中没有找到「无障碍扩展读取第三方应用内容取决于该应用是否暴露无障碍节点」这类明文表述。可用的间接线索是 **`retrieve` 的实现依赖 ArkUI 侧对组件无障碍属性的适配**：

- 【ArkUI无障碍】原文：「无障碍服务是为保障所有人在任何情况下都能平等、便捷地获取和利用信息打造的系统级无障碍能力体系。其中为视障用户提供的屏幕朗读功能会将设备屏幕上的可见信息转化为语音播报」
- 【ArkUI无障碍】还提供了 `accessibilityText` / `accessibilityDescription` / `accessibilityLevel`（可禁用屏幕朗读焦点）等属性 —— 说明**应用可以主动控制自己暴露给读屏的信息**（这一点在《知了》自身适配时可用，但无法作为读取第三方的依据）。
- 本报告**未**找到官方文档中「应用可以完全屏蔽第三方读取」的明文条款，**该点为未取证**。

## 5. 能否主动「刷」另一个应用的聊天记录

### 5.1 官方能力的形态：事件驱动 + 单点取根节点

1. **入口是事件回调**：`AccessibilityExtensionAbility.onAccessibilityEvent(event: AccessibilityEvent): void`（SDK :131）是能力的主入口；其参数 `AccessibilityEvent`（SDK :152–:206）字段为 `eventType`、`target?: AccessibilityElement`、`timeStamp?`、`elementId?`（@since 12）、`textAnnouncedForAccessibility?`（@since 12）、`extraInfo?`（@since 20）。
2. **上下文对象只能在扩展被连接后拿到**：【华为AxEC】使用说明原文：「使用AccessibilityExtensionContext功能前，通过AccessibilityExtensionAbility子类实例获取AccessibilityExtensionContext实例。」示例即 `onConnect()` 内 `let axContext = this.context;`。
3. **取节点的粒度是「窗口根节点」或「当前焦点」**，不是「批量遍历某应用的全部节点」：
   - `getWindowRootElement(windowId?)`：原文「获取指定窗口的根节点元素」「指定窗口的编号，**未指定则从当前活跃窗口获取**」（【华为AxEC】L419/L430）。
   - `getFocusElement(isAccessibilityFocus?)`：「获取当前焦点元素」（SDK :115）。
   - `getWindows(displayId?)`：获取所有窗口的**根节点**元素（SDK :207）。
   - 要从根节点往下走，只能靠 `children: Array<AccessibilityElement>` 逐层递归，或 `findElement('content'|'focusType'|'focusDirection', ...)`（同样自 API 12 废弃）。

### 5.2 结论

- **官方文档没有提供任何「主动拉取/订阅另一个应用聊天记录」的专用接口**。可用的原子能力是「收到无障碍事件 → 在事件里/用上下文取到某一窗口的根节点或焦点节点 → 沿 `children` 递归或 `findElement` 查找节点 → `attributeValue('text')` 取文本」。
- 也就是说：**即使能力未被收回，其形态也是「被动的、逐事件的、单窗口根节点起步的」**，而不是「后台批量刷某个应用的全部历史消息」。要拿到聊天记录，必须依赖用户在聊天界面上的真实操作触发无障碍事件（或至少让目标窗口处于活跃状态），并且只能拿到**当前渲染出来的节点**。
- **叠加 API 12 废弃这一事实**，本通道在 HarmonyOS 6 三方应用身份下**没有工程价值**，与《知了》报告中「P2 实验性通道、能否上线取决于审核结果」的假设一致 —— 但需要修正一点：**阻碍不是「审核可能不过」，而是「能力在 API 12 起已被系统收回」**。
- 「是否还存在未文档化的轮询手段」**未取证**（不做推测）。

### 6.3 「必须是无障碍辅助工具类应用才能申请」这类限制

- 在【审核指南】全文中 grep `无障碍|辅助功能|读屏|Accessibility`：**命中的 23 处里没有一处**规定「无障碍能力只能由无障碍辅助类应用申请」，也没有「普通应用不得申请无障碍权限」的明文。
- 在【受限开放权限】页中 grep `ACCESSIBILITY|无障碍|辅助`：**仅 1 处命中**，且内容与无障碍扩展无关（游戏 AI 陪玩截屏辅助场景）。→ **`ohos.permission.ACCESSIBILITY_EXTENSION_ABILITY` 不在三方应用「受限开放权限」清单内**。

- 无障碍扩展的**开启流程本身带系统级风险提示**（【开发指南-md】原文）：

  > 当前提供设备-设置中的扩展服务管理页的开关按钮来开启/关闭选择的无障碍扩展服务

  > 开启时，弹出安全提醒，在倒计时结束后，勾选"我已知晓如上风险，并自愿承担可能导致的后果。"后，可选择"开启"/"不开启"按钮

  → 说明系统把「启用无障碍扩展服务」定义为**高风险操作**，需要用户显式承担风险；这本身就是审核会重点审视的环节。

### 7.3 华为官方 Kit 简介里的一句决定性限定

【华为Kit简介】（`accessibilitykit-overview.md`，华为开发者官网「Accessibility Kit 简介」）「能力范围」小节原文：

> * **无障碍状态查询：** 为应用提供无障碍服务开启状态、触摸浏览开启状态查询接口，以便应用根据无障碍功能开启状态，更好的服务于障碍人群和障碍场景。
>
> * **无障碍事件发送：** 为应用提供主动聚焦、主动朗读等无障碍事件发送接口，以便应用结合业务场景，做到更好的无障碍体验。
>
> 说明
>
> **Accessibility Kit目前仅支持上述无障碍状态查询和无障碍事件发送能力，不支持通过无障碍节点查询获取界面节点及屏幕内容信息。**

同一文档「与相关Kit的关系」小节原文：

> ArkUI Kit为Accessibility提供无障碍组件属性定义、无障碍事件发送能力，应用可基于ArkUI Kit为组件设置无障碍文本、描述信息等属性。

**这是「读屏读取屏幕内容」在本代 HarmonyOS 上不可用的最直接官网口径。**

### 7.4 官方 Kit 目录结构中已无「无障碍扩展服务」开发指南

把华为官网 `llms.txt` 索引（`https://developer.huawei.com/config/llms.txt`）的三大分册拉到本地后统计：

- 开发指南侧（`docs-capabilities.txt`）中 `Accessibility Kit（无障碍服务）` 下**只有** 4 个章节：`Accessibility Kit 简介`、`提升应用的无障碍体验`、`测试应用的无障碍功能`、`应用长辈关怀功能体验` —— **没有**「无障碍扩展服务」开发指南节点。
- 与该 Kit 相关的全部文档条目（grep `Accessibility Kit` 命中 27 条）**全部是「应用如何让自己的界面被读屏读到」方向**（`scenario-screen-reading`、`scenario-disable-screen-reading-focus`、`scenario-focus-position-setting`、`list-item-combination-scenarios`、`proactively-notify-page-changes`、`scenario-multicomponent`、`scenario-multilingual`、`ndk-accessibility-xcomponent` 等）。
- API 参考侧（`docs-references.txt`）仍保留 `@ohos.application.AccessibilityExtensionAbility (辅助功能扩展能力)` 与 `AccessibilityExtensionContext (辅助功能扩展上下文)` 两个页面，**但页面上每个方法都带 `(deprecated)`**（§3.1/§3.2）。
