# 第一周：三个人一个打地基，两个搭前端

> [!important] 这一周要拿到什么
> 1. 三项可行性验证各有明确结论，写成「通过 / 不通过 / 未验证」，不许写「大概可以」；
> 2. 六页界面在模拟器上能走通跳转，用的是假数据；
> 3. 一套能复用的组件与一份设计规范，后面的页面照着搭。
>
> 这一周的重点是前端落地能力。存储与解析接入放在第 2 周，与真实数据一起做。
> 第 1 天到第 2 天有没有把外部依赖推出去，比这一周写了多少行代码重要得多。

## 2. 逐天安排

### 第 1 天（周一）：把外部依赖推出去

详细清单在 `docs/第一天开发文档.md`。

- 谢忠宇：范围冻结会 → 代理提醒申请提交 → 日历兜底设计 → AGC 实名状态与云端中继 → QQ 机器人实名、建号、收到第一条群消息 → 明天的验证代码与样本
- 杜俊廷：六页原型的前三页（首页时间线、解析确认、任务列表与详情）
- 袁正锟：六页原型的后三页（首次启动、添加信息、设置）+ 跑通一个最小的列表页面

当天出口：两个申请都变成「已提交、有编号」；范围冻结文档发出；机器人能收到一条消息。

### 第 2 天（周二）：上午验证，下午定规范

上午是这一周最贵的一个半天，时段第 1 天就定死。

- 袁正锟：T07 代理提醒真机跑通，紧接着 T08 实体抽取。记录表里要有设备型号、系统版本、`publishReminder` 的真实返回值、出错时的错误码原文
- 谢忠宇：T09 分享接收被拉起，用 Attach Debugger 的方式调试；同时定案接收形态（倾向 UIAbility 形态，理由是确认页只需要做一套）
- 杜俊廷：上午不占手机，把六页原型收尾并与袁正锟对齐

下午回到座位：

- 杜俊廷：T04 视觉规范。颜色、间距、圆角、字号四类常量收进 `utils/Theme.ets`，顺手把六页原型里的取值换成常量
- 袁正锟：按定稿原型开始搭组件。**只做组件，不做页面**——先做首页时间线要用到的三个：任务卡、时间分档标题、空状态
- 谢忠宇：云端中继推进，或者处理机器人那边暴露出来的问题

> [!warning] 这个上午只有一次机会，两件事想清楚再点火
> 一是 `requestEnableNotification` 的弹窗**只能弹一次**，验证前想清楚要看什么，别把通知授权浪费在没意义的试跑上。
> 二是 T08 的样本必须来自真实群消息，**不能自己编**。20 条样本第 1 天就准备好，现场现找会吃掉半个上午。

### 第 3 天（周三）：组件齐了开始搭页面

- 杜俊廷：组件补齐（确认页的字段行、任务列表项、设置项），然后把首页时间线与解析确认页搭出来。**页面只渲染假数据，不接数据层**，验的是布局、跳转、四档分组的呈现
- 袁正锟：解析确认页的字段编辑交互 + 任务列表与详情。做完自己先在模拟器上点一遍，把「设计稿有、实现里没有」的地方记下来
- 谢忠宇：T11 云端中继收尾。**这个时间是账号状态的检查点**，实名还没下来就把期望从「跑通」改成「记录未验证」，不要在它上面继续投时间

### 第 4 天（周四）：跳转串起来

- 三个人一起过一遍完整点击路径：添加信息（粘贴）→ 解析确认 → 任务列表与详情 → 首页时间线对应分档
- 六页全部可点，不留死链；返回、二次进入、空状态都要试
- 谢忠宇：把机器人那条链路与 App 侧拉取的接口约定写下来，放进 `service/backend/`，作为第 2 周 W2-T10 的依据
- 收工前把所有页面截图存一份，交答辩材料用

> [!note] 串完之后有一句话必须说清楚
> 界面走通不等于解析完成。这一周的解析结果是假数据，真解析要到第 2 周的 W2-T01。周记录里要把「界面闭环已通」和「解析未接」分开写，否则第 2 周会有人以为快做完了。

### 第 5 天（周五）：收口、对演示、写记录

- [ ] 三个人在模拟器上完整走一遍六页，确认 360vp 宽度下没有横向滚动
- [ ] 六页原型与实现逐页对照，把「原型里没有、实现里冒出来」的东西记下来
- [ ] 三项验证的结论汇总，每项写成「通过 / 不通过 / 未验证」
- [ ] 云端中继写「通 / 不通 / 未验证」。账号一直未实名就写「未验证」，并说明中继仍走 WebSocket 主路径
- [ ] 组件清单梳理一遍：哪些能直接复用，哪些要改，哪些重复了。重复的合并掉
- [ ] 按 §7.4 模板写 `docs/进度记录-W1.md`
- [ ] 填下面的看板
- [ ] 定下周验证机时段：第 2 周要真机验的是提醒的发布与撤销，还是同一个上午成组做

## 4. 每天的固定动作

| 时间 | 动作 | 谁 |
| :-- | :-- | :-- |
| 开工前 10 分钟 | 各自说昨天到哪了、今天做什么、有没有卡住 | 三人 |
| 收工前 10 分钟 | 把当天的结论写进 `docs/进度记录-W1.md` 的草稿区 | 谁验谁写 |
| 每次需要真机 | 先报一句「我要用机器，大概多久」 | 使用者 |
| 每次改文件 | 只改自己名下的；要改别人的，先在文件顶部留 `TODO(你的名字): 原因` | 三人 |

文件归属见 `docs/开发指南.md` §7.3。这一周动得最多的四条线：`pages/` 与 `utils/Theme.ets` 归杜俊廷；`model/` 与 `service/ai/TextExtractService.ets` 与 `module.json5` 归谢忠宇；`service/ai/` 里的 OcrService、SpeechService 归袁正锟；`repository/` 第 1 周不动。

前端两人之间的边界再加一条：**组件放 `components/`，谁先做谁建，用之前先在群里说一句**。两个人同时捏一个任务卡组件，第 5 天合并时要花半天。

> [!important] 一条不能碰的底线
> 不合格的结论不许包装成合格。模拟器跑不起来的东西，不能拿静态截图去凑「解析可用」；账号没实名导致没验的，就写「未验证」。
> 这条比任何技术风险都危险，因为它会把「没做出来」包装成「做出来了」，而且是在第 4 周答辩时才被拆穿。
