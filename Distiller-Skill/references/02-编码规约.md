## 1. 状态管理：只用 V2，不混 V1

**硬规则**：新代码用 `@ComponentV2` / `@Local` / `@Param` / `@Event` / `@ObservedV2` / `@Trace`；**不要混用 V1**。依据：问题列举 #19「新代码用 V2；旧工程才走迁移。混用是编译期问题，早点定下来省事」。

各装饰器的职责（依据：`开发指南/ArkUI_方舟UI框架/…/学习UI范式状态管理/MVVM模式_V2/arkts-mvvm-v2`，该页原文逐一给出这些装饰器的用途）：

| 装饰器 | 职责（官方表述要点） | 本项目里用在哪 |
| :-- | :-- | :-- |
| `@ComponentV2` | V2 的自定义组件装饰器，`@Local`/`@Param`/`@Event` 都以它为前提 | 每个页面、每个组件 |
| `@Local` | 组件**内部**状态；被装饰的变量变化时触发绑定的 UI 组件刷新 | 页面/组件自己的临时状态（输入框内容、展开态、loading 标志） |
| `@Param` | 子组件**接收父组件传入**的值，**单向**数据同步；**默认只读**，需要在子组件内更新时用 `@Param @Once` | 组件入参（任务卡数据、设置项当前值） |
| `@Event` | 子组件**向父组件输出**数据（回调） | 组件事件（删除、勾选完成、编辑） |
| `@ObservedV2` + `@Trace` | 观测**类对象**及其属性（官方把它归入「管理数据对象的状态」） | ViewModel 里的任务列表项、解析候选字段对象 |
| `AppStorageV2` / `PersistenceV2` | 全局状态存储 / 持久化存储 | **本项目是否用未定**，见「未取证」 |

> [!important] 组件复用：V2-only 工程只能用 `@ReusableV2`
> 官方**明确区分** V1 的 `@Reusable` 与 V2 的 `@ReusableV2`，并给出替换对照表。更要紧的是混用矩阵里的一条实际结论：
> **V2 普通组件当父 + V1 复用组件当子 = 「不支持，编译告警，实际使用子组件不创建」** ——
> 这是**功能性故障**（子组件根本不出现），不是风格问题。
> 所以本项目一律 `@ReusableV2`；`aboutToReuse` 在 V2 下**无入参**（与 V1 的硬差异）。
> 依据：`references/official/开发指南/ArkUI_方舟UI框架/UI开发_ArkTS声明式开发范式/学习UI范式基本语法/自定义组件/自定义组件复用/ReusableV2装饰器_V2组件复用/arkts-new-reusablev2.md`（混用矩阵、`aboutToReuse` 签名）、
> `references/official/开发指南/ArkUI_方舟UI框架/UI开发_ArkTS声明式开发范式/学习UI范式状态管理/状态管理V1-V2迁移指导/状态管理V1向V2迁移场景/组件复用迁移/arkts-v1-v2-migration-reusable.md`（`@Reusable → @ReusableV2` 对照表）。
> 可抄片段：`templates/global-reuse-pool.ets`。

**禁止清单**（V1 装饰器与 V1 全局存储）：`@State`、`@Prop`、`@Link`、`@Observed`、`@ObjectLink`、`@Provide`、`@Consume`、`@Watch`、`LocalStorage`、`AppStorage`、`PersistentStorage`。

> [!warning] 现存 `pages\Index.ets` 是 V1 模板占位
> 实文件 `entry\src\main\ets\pages\Index.ets:16-19` 用的是 `@Entry @Component struct Index { @State message: string = ... }` —— 这是模板原样，**不是范例**。第一个真页面落地时把它替换掉，不要照着它写新页面。
>
> 官方从 API version 19 起放宽了 V1/V2 混用约束（`…/状态管理V1和V2混用指导_API_version_19及之后/arkts-v1-v2-mixusage`），但那**不改变**本项目的规矩：本项目一律 V2，迁移细节以官方「状态管理V1-V2迁移指导」一节为准。

## 2. AI 能力：必须动态引入（`service/ai/` 收口）

| 能力 | Kit | 模拟器 | 依据 |
| :-- | :-- | :-- | :-- |
| 实体抽取 / 时间地点 | Natural Language Kit | **不支持**（原文「该能力当前不支持模拟器。」） | 台账 §2.2；调查 03 §3.1 |
| 图片文字识别 | Core Vision Kit | **不支持**（原文「本Kit暂不支持模拟器。」） | 台账 §3；调查 03 §3.1 |
| 语音转文字 | Core Speech Kit | 支持（自 6.0.0(20) 起） | 台账 §4；调查 03 §3.1 |

**为什么必须动态引入**：模拟器上**静态 import 不支持的 Kit 会让应用直接闪退**，报错模板（台账 §11「闪退规避」，原文）：

```text
LastFatalMessage:[default] [LoadJSPandaFile:00] resolveBufferCallback get hsp buffer failed，
hsp path:/data/storage/el1/bundle/com.huawei.hmos.{KitName}.kit
```

官方给出的**唯一明文规避手段**是动态引入 Kit（原文「如遇到因Kit能力不支持导致的应用闪退问题，可以尝试使用动态引入Kit的方式规避此异常问题。」，依据：调查 03 §4.2）。落到代码上：

| 规则 | 内容 | 依据 |
| :-- | :-- | :-- |
| 谁做动态引入 | **只有 `service/ai/` 这一层**做 `import()`；`service/ai/index.ets` 文件头注释原文：「对它们的引用一律走动态引入（`import()`），不要在这里做顶层 import」 | 实文件；开发指南 §9.4 |
| 谁不做 | 页面、ViewModel、`model/`、`repository/`、其它 service 子域**都不出现** `@kit.NaturalLanguageKit` / `@kit.CoreVisionKit` / `@kit.CoreSpeechKit` 的顶层 import | 开发指南 §2.3 |
| 降级 | 动态引入失败或能力不支持时走**降级分支**（假数据 / 预置文本 / 明确提示「此设备不支持」），**不许把异常抛到页面** | 调查 03 §4.2、§4.4 |
| 对外形态 | 页面只碰 `service/ai/index.ets` 桶导出的接口，不碰 `TextExtractService` / `OcrService` / `SpeechService` 实现文件 | 开发指南 §9.1 |
| 硬参数 | 抽取文本 ≤ **1000 字符**（长消息先切片）；语音仅 `zh-CN` + `online: 1` + `pcm`/16000Hz/单声道/16bit，`writeAudio` 分片长度**仅 640 或 1280** | 台账 §2.2、§4 |

## 3. Service 结果契约：成功 / 失败 + 错误码，永不抛到页面

| 规则（原文要点） | 依据 |
| :-- | :-- |
| 「所有 AI 调用统一返回『**成功 / 失败 + 错误码**』，**不允许把异常抛到页面层**」 | 开发指南 §9.4 |
| 「`publish` 的失败要**可解释**：`1700002`（数量超限）要翻译成『提醒数量已达上限，请在任务列表里完成或删除一些任务』；权限类错误码要翻译成**可执行的下一步**，不能只弹『操作失败』」 | 开发指南 §9.5 |
| 通知授权被拒（`1600004`）时，提示语必须是**可执行的下一步**，点击调 `openNotificationSettingsWithResult(context)` | 台账 §8.1 |

落地要求：

- service 层返回**结构化结果**（成功 + 数据 / 失败 + 错误码 + 可读文案），页面只做展示与转发。
- 错误码**不许只 log 不处理**，也不许统一收敛成一句「操作失败」。
- 页面**不许** `try/catch` 包住 service 调用来兜住异常——那等于把契约破坏了还看不出来。

`model/index.ets` 文件头注释原文：「**本层只放类型与常量，不放行为**；字段名改动必须同步 §9.2 那张表。」

| 规则 | 内容 | 依据 |
| :-- | :-- | :-- |
| 字段表 | 任务字段以开发指南 §9.2 的 `Task` 表为准（`id` / `title` / `detail` / `source` / `raw_text` / `raw_json` / `due_at` / `due_text` / `repeat` / `location` / `priority` / `confidence` / `missing_fields` / `status` / `remind_at` / `reminder_id` / `created_at` / `updated_at`） | 开发指南 §9.2 |
| `source` 取值 | 只允许 `paste` / `share` / `bot` / `voice` / `manual` | 开发指南 §9.2、§6.4 |
| `status` 取值 | `0` 待确认 / `1` 已确认 / `2` 进行中 / `3` 已完成 / `4` 已过期 / `5` 已删除 | 开发指南 §9.2、§9.3 |
| 状态机 | 「**已过期（4）只有系统能写**，用户不能手动把任务标成已过期」 | 开发指南 §9.3 |

## 5. 提醒抽象：只有三个动作，内部两条路径

| 动作 | 签名（开发指南 §9.5 骨架） | 说明 |
| :-- | :-- | :-- |
| 发布 | `publish(task: Task): Promise<number>` | 返回本地 reminder 键并写进 `task.reminder_id` |
| 撤销 | `cancel(taskId: number): Promise<void>` | 已完成 / 已删除 / 编辑时间后**都要调** |
| 查询 | `listValid(): Promise<Task[]>` | 供设置页显示「当前生效提醒 N / 30 条」 |

| 规则（原文） | 依据 |
| :-- | :-- |
| 「内部走哪条路径**由它自己决定**，页面与 ViewModel 里**不许出现** `if (用了日历)` 这种分支」 | 开发指南 §8.1 |
| 内部两条路径收口在同一接口：路径 A `reminderAgentManager.publishReminder`／路径 B `calendarManager.createCalendar → addEvent` | 开发指南 §9.5 |
| **发布要幂等**：重复 `publish` 必须收敛成一条（路径 A 靠确定性 `notificationId`；路径 B 靠先按 `taskId` 查有无日程，有则改、无则建） | 开发指南 §9.5 |
| **撤销要成对**：任务状态变已完成/已删除、或截止时间被编辑时必须 `cancel` | 开发指南 §9.5 |
| 切路径时**必须把已有任务的 `reminder_id` 全部作废**（两套系统是两套编号空间） | 开发指南 §9.5 |
| 条数上限 30：只为**最近 30 条未完成任务**发布提醒，超出的在首页显示「提醒已合并」，设置页写明原因 | 开发指南 §8.1 |
| 日历路径：`Event.reminderTime` **单位分钟**（值 5 = 开始前 5 分钟，不设则不提醒）；`EventType` 一律 `NORMAL`；平台 `repeat` → `recurrenceRule` 的映射做成**纯函数 + 单元测试** | 开发指南 §9.5；台账 §6.1 |
| 日历路径必须写进设置页的两句话：提醒出现在**系统日历**而不是知了的时间线；用户在系统日历里删掉日程，知了侧状态不会自动同步 | 台账 §6 |

## 6. 数据字段纪律

开发指南 §9.2 的**三条字段纪律**（原文）：

1. **`raw_text` 和 `raw_json` 必须存。** 前者是「原文对照」的唯一依据，后者是第 3 周调解析规则的唯一依据。删掉任何一个，后面都会回来重做。
2. **缺失字段进 `missing_fields`，不编造值。** 这是「缺失不猜测」的工程实现形式。
3. **`repeat` 存平台原样字符串**（如 `W3` / `M2` / `workingDay`），不要在写入时就翻译成周期对象——翻译规则会在真机验证后调整。

补充约束：

| 规则 | 依据 |
| :-- | :-- |
| 写入原文的路径**不依赖 UI 线程** | 开发指南 W1-T05 验收标准 |
| 云上只存 `BotTask` 十个字段；`raw_text` / `raw_json` / 发送者 / 群号 / 消息 id **一律不出手机** | 开发指南 §6.3、§6.4、§8.4 |
| 云端同步**默认关闭**，开启时说明「哪些字段会离开手机、存在哪、保留多久」 | 开发指南 §6.5 |
| 云函数把结构化字段写库后**直接返回，原文只作为内存入参**；bot 进程与云函数**都不打印消息正文**（只打 `client_task_id`、字段数量、耗时） | 开发指南 §6.3、§6.5 |

## 8. 生命周期与性能

| 规则 | 内容 | 依据 |
| :-- | :-- | :-- |
| `aboutToAppear` **只做同步、无 IO 的初始化** | 赋值、绑定引用、设置初始状态 | 推论自下列三条硬约束 |
| ❌ 不在 `aboutToAppear` 里读写数据库 / 首选项 | 「写入原文的路径**不依赖 UI 线程**」 | 开发指南 W1-T05 验收标准 |
| ❌ 不在 `aboutToAppear` 里调 AI（抽取 / OCR / ASR） | 这些调用是异步且耗时；必须动态引入 + 返回结果契约 | 开发指南 §9.4；台账 §2.2 |
| ❌ 不在冷启动弹通知授权窗 | 官方调用模式是**先 `isNotificationEnabled()` 判断，只有未授权才调 `requestEnableNotification()`**；且「**冷启动不许弹窗**，要等用户在引导页点『开启提醒』」；用户拒绝过之后该接口再也弹不出窗 | 台账 §8.1；开发指南 §2.1 |
| ❌ 不在 `aboutToAppear` 里做长文本切片 | 抽取上限 1000 字符，长消息必须先切片；切片是可并行的纯计算 | 台账 §2.2 |
| ✅ 重活交给 TaskPool / Worker | TaskPool 注意事项（官方原文）：任务函数需 `@Concurrent` 标注且**仅支持在 .ets 文件中使用**；跨并发实例传带方法的实例对象需 `@Sendable`（否则考虑 Worker）；**任务函数 CPU 执行时长不能超过 3 分钟**（异步 I/O 等待不计入）；入参需满足序列化支持的类型；**不支持用 V1 的 `@State`/`@Prop`/`@Link` 装饰的复杂类型** | `开发指南/ArkTS_方舟编程语言/ArkTS并发/多线程并发/TaskPool简介/taskpool-introduction` |
| 分享场景的落盘时机 | **拿到 want 就落盘**（UIAbility 形态看 `onNewWant`，扩展形态看 `onSessionCreate`），不要依赖 `onDestroy`；若必须写，官方推荐 `async onDestroy(): Promise<void>` | 台账 §7.1、§7.4；开发指南 §2.1 |
| 预览器不是性能结论的来源 | 预览器**不支持** Attach / 跨 Ability / C++ / Hot Reload / **多进程与 worker、taskpool 调试** | 台账 §11 |

| 配置 | 值 | 含义 |
