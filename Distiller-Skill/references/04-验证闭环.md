# 04 · 验证闭环

> 这份文件给出**从改完一个文件到「这条任务算做完了」的完整顺序**，命令逐字可抄。
> 依据：`Distiller-DOC\开发指南.md`（下称「开发指南」）§10.1 / §10.2 / §10.4、`Distiller-DOC\99-附录-取证台账.md`（下称「台账」）§1.1 / §11、`Distiller\docs\_调查\01-分享接收取证.md` §6。

## 1. 有序闭环（照顺序走，不要跳）

### 第 0 步 · 静态检查（每改完一个文件）

| 项 | 内容 |
| :-- | :-- |
| 手段 | `mcp__deveco__check`（ArkTS 语法检查） |
| 路径 | **只接受相对工程根的路径**，例如 `entry/src/main/ets/pages/A_Home.ets` |
| 传绝对路径会怎样 | 报 `Error: Absolute path is not allowed` |
| **假通过** | 返回「**没有有效的 .ets 文件**」/「**No diagnostics collected**」**不算通过** → 改用 `devecocli build` 兜底 |
| 依据 | 开发指南 §10.1「两条工具的实际脾气」 |

### 第 1–4 步 · 编译

```text
# 1) 常规构建（默认 product=default、build-mode=debug）
devecocli build

# 2) 只构建 entry 模块
devecocli build --modules entry

# 3) release 包
devecocli build --build-mode release

# 4) 清理（构建结果可疑、或换 product 之前）
devecocli build clean
```

> [!note] 一个真实基线：这套命令不是纸面推演
> `devecocli create --app-name Distiller --project-path "E:\Program_File\HMOS_proj\Distiller" --bundle-name com.xjtu.distiller --api-level 22` 已真实建出工程，`devecocli build --modules entry` 实测通过（数字见 §4）。
> **每次提交前**要做的正是「`check` 无新增报错 + `devecocli build` 通过」这两件（开发指南 §10.2）。

### 第 5 步 · 核对产物路径

```text
entry/build/default/outputs/default/entry-default-unsigned.hap
```

| 项 | 内容 |
| :-- | :-- |
| 大小（实测） | **121404 字节** |
| 文件名里的 `unsigned` | 就是「**装不进真机**」的提示；看到它就不要浪费时间去 `devecocli run` |
| release 产物 | **未实测**：本文件只记录已实测的 debug 路径，release 的路径与体积以命令输出为准，不要照抄上面这一行 |

### 第 6–7 步 · 运行（有设备时）

```text
# 6) 先看设备；多设备时必须显式 --device
devecocli device list
devecocli run --module entry --device <sn>
```

| 项 | 内容 |
| :-- | :-- |
| 先自己探 | `devecocli device list` —— **输出由你机器的实际情况决定，本文不替你写死**。打印 `No active devices.` 就是这台机器上没连真机 |
| `No active devices` 的含义 | **正常状态，不是「团队没有设备」**。团队全班底只有**一台** 6.0.2(22) 真机（验证机），它连在哪台机器上、当时插没插，每次都不一样 |
| 要跑真机怎么办 | 先把验证机用 USB 连到**你这台**机器（确认 `hdc` 认到设备），再 `devecocli device list` 确认；然后再走 `devecocli run`。设备只有一台 → 多人要用就排队 |
| `--device` | 多设备时**必须显式给 sn**；单设备也建议写上，避免误装到模拟器 |
| 还有别的开关 | `devecocli run` 支持 `--module <m>` / `--device <sn>` / `--product <p>` / `--ability <a>` / `--uninstall` / `--skip-build` |
| 未签名包 | 装不上。要跑真机，先解决签名（W4-T03，或按官方在 DevEco Studio 里配自动签名） |

### 第 8–10 步 · 看日志（排查崩溃与「到点有没有真的响」）

```text
# 8) 只看错误级别
devecocli log --level E

# 9) 只看崩溃
devecocli log --crash

# 10) 挂着跟随看（提醒到点、分享链路这类「系统触发」的场景用这条）
devecocli log --level I --bundle-name com.xjtu.distiller --follow
```

| 项 | 内容 |
| :-- | :-- |
| 别的过滤开关 | `devecocli log` 支持 `--device <sn>` / `--level D\|I\|W\|E\|F` / `--bundle-name <b>` / `--keyword <k>` / `--from` / `--to` / `--tail <n>` |
| 日志量 | 输出很大：**先落盘再用 grep 取关键行**，只把结论带回上下文 |

## 2. 什么算做完

| 条件 | 说明 |
| :-- | :-- |
| ✅ `mcp__deveco__check` 干净 | 无新增报错；返回「没有有效的 .ets 文件」/「No diagnostics collected」**不算**（见第 0 步） |
| ✅ `devecocli build` 通过 | 产物路径能对上（第 5 步） |
| ✅ 提交信息带任务号 | 格式 `[W1-T03] 六页静态原型`；**没有任务号的提交不接受** |
| ❌ 不算做完 | 编译不过、或靠注释包一层让它编过；「不许为了『看起来有进展』而提交编译不过的代码」（开发指南 §10.2） |
| ❌ 不算做完 | 只跑了静态检查、没编译；或只在预览器里看过一眼（预览器限制见台账 §11） |
| ⚠️ 需要设备的功能 | 编译通过 + 没设备 = **只能声明「编译通过，未做运行验证」**（见 §5） |

## 3. 两个「按正常方式调不出来」的场景

### 3.1 分享接收的唤起

| 项 | 内容 |
| :-- | :-- |
| 为什么抓不到 | 拉起它的是**系统分享面板**，不是 DevEco 的运行按钮 → 属于「外部事件冷启动」；`devecocli run` 与普通 Debug 都抓不到断点 |
| 前提 | 设备上被 attach 的应用代码**和本地代码一致**，且**已提前构建生成必要的 sourceMap 文件**；**attach 仅支持 debug 签名的应用**（手机上没有例外） |
| 操作 | DevEco Studio → **Attach Debugger to Process** → 勾选 **Show all process** → 选中知了进程 → **Debug type 选 ArkTS** → 等到底部出现 **`Waiting for debugger`** 进度条 → **这时才切到 QQ 去分享** |
| 辅助日志 | `devecocli log --level E --bundle-name <包名> --follow`；崩溃用 `devecocli log --crash` |
| 依据 | 开发指南 §10.4；台账 §7；调查 01 §6.3 / §6.4 |

流程按调查 01 §6.4 的版本走一遍（可直接抄）：

1. `devecocli build` 构建 debug 包 → `devecocli run` 安装到真机；
2. DevEco Studio → **Attach Debugger to Process** → 勾 **Show all process** → 选中知了进程 → Debug type 选 **ArkTS** → OK，看到 **`Waiting for debugger`**；
3. 在 `onSessionCreate` / `onNewWant` / `uriToPixelMap` 首行下断点；
4. 切到 QQ / 微信，长按消息或截图 → 分享 → 选择知了；
5. 断点命中后逐帧看 `want` 与 `record`。

> [!note] 两个已知的坑（实测前先看，省半小时）
> - bundleName 与当前工程不一致时，会提示 `The selected process does not match the bundlename of the current project!`，**勾 Show all process 即可绕过**，不阻塞调试。
> - 官方 FAQ 里同一条路还有另一种入口写法：**Run → Attach to Process by Name** → 类型选 **ArkTS** → Attach → 等到 `Waiting for debugger`（来源：调查 01 §6.2，迁移自 FormExtensionAbility 的官方 FAQ，**不是 Share Kit 专属文档**）。

### 3.2 代理提醒到点后的行为

| 项 | 内容 |
| :-- | :-- |
| 为什么抓不到 | 触发者是**系统**，且往往在**应用已被杀之后** |
| 怎么做 | 用 `devecocli log --level I --bundle-name com.xjtu.distiller --follow` **挂着看日志**；崩溃用 `devecocli log --crash` |
| 排期含义 | 「**这一条决定了 W1-T07 的验证必须留够时间**」（开发指南 §10.4 原文） |
| 额外注意 | `requestEnableNotification` 的弹窗**只能弹一次**——验证前想清楚要看什么，别把通知授权浪费在没试跑的验证上 |

## 5. 没有设备时怎么说

**底线一句话：不合格的结论不许包装成合格。**

| 场景 | 允许怎么说 | 不许怎么说 |
| :-- | :-- | :-- |
| 编译通过、没有设备/没验 | 「编译通过，**未做运行验证**」 | 「已验证」「跑通了」 |
| 能力只在模拟器上跑不起来（OCR / 实体抽取） | 「模拟器不支持，**未验证**」 | 拿静态截图凑「解析可用」 |
| 账号/申请没下来导致没验 | 「**未验证**」，并写明卡在哪 | 写成「通过」 |
| 三项可行性验证 | 每项写成 **「通过 / 不通过 / 未验证」** | 「大概可以」「基本没问题」 |
| 假数据闭环跑通 | 「界面闭环已通，**解析未接**」（两句分开写） | 「解析已完成」 |
| 云端中继 | 「通 / 不通 / **未验证**」 | 拿本机 localhost 调试通过当成「公网可达」 |

依据：开发指南 §8.2「不要做的事」、`第一周开发指南.md` §5「一条不能碰的底线」、开发指南 §4（W1-T10 风险栏）。

> [!warning] 为什么这条写得这么重
> 「不要用模拟器跑不起来的截图去凑『解析可用』的结论。这一条比任何技术风险都危险，因为它会把『项目没做出来』包装成『项目做出来了』。」——开发指南 §8.2。
> 而且它会在第 4 周答辩时才被拆穿（第一周开发指南 §5）。
