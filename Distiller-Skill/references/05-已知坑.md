## P1 · 静态 import 模拟器没有的 Kit → 应用**直接闪退**

| 项 | 内容 |
| :-- | :-- |
| 证据 | 台账 §11「闪退规避」：模拟器上静态 import 不支持的 Kit 会导致 **Kit HSP 加载失败**，报错模板 `LastFatalMessage:[default] [LoadJSPandaFile:00] resolveBufferCallback get hsp buffer failed，hsp path:/data/storage/el1/bundle/com.huawei.hmos.{KitName}.kit`；官方原文「如遇到因Kit能力不支持导致的应用闪退问题，可以尝试使用**动态引入Kit**的方式规避此异常问题。」 |
| 谁会踩 | 实体抽取（Natural Language Kit）、图片文字识别（Core Vision Kit）——两者都**不支持模拟器** |
| 表现 | 不是「调用报错」，是**应用起不来**：进页面即闪退，hilog 里是上面那行 HSP 加载失败 |
| 处置 | ① AI 调用点全部收口在 `service/ai/`，**在那一层做 `import()` 动态引入**（开发指南 §2.3、§9.4）；② `service/ai/index.ets` 文件头注释已写明「不要在这里做顶层 import」；③ 动态引入失败走降级分支，**不许把异常抛到页面** |
| 一处待澄清 | 报错模板里的路径在源文件中有两种写法：`el1/bundle`（开发指南 §2.3、台账 §11）与 `el1_bundle`（问题列举 #6）。**哪一个是逐字原文未取证**，抓日志时按实际输出为准 |

## P2 · `rrule` 已被 `repeat` 取代，落了 `rrule` 会**静默失效**

| 项 | 内容 |
| :-- | :-- |
| 证据 | 台账 §2.3 引官方 FAQ 原文：「**从5.0.1.130版本开始，rrule字段以后不会输出了，请使用repeat字段替代**」；同节 `jsonObject` 字段表里 `rrule` 的说明是「不一定准确，具体以 repeat 为准（**参考数据，不建议使用**）」 |
| 表现 | **不报错**。字段就是空的/停留在旧值，周期判断在新系统上静默不生效——最难查的一类缺陷 |
| 处置 | ① 数据模型**只存 `repeat`**（开发指南 §2.3 坑 2）；② 同时保留平台原始 `jsonObject` 原文（`raw_json`）以便回溯与调参（开发指南 §9.2 字段纪律 1）；③ `repeat` 取值按台账 §2.3 的规范表（`Y` / `Y3` / `Y3.6` / `M` / `M2` / `W` / `W3` / `W3-W5` / `workingDay`），`workingDay` 的**完整取值未取证**；④ 日历路径的 `repeat → recurrenceRule` 映射**做成纯函数 + 单元测试**（开发指南 §9.5） |

## P3 · `notificationId` 相同的提醒会**互相覆盖**

| 项 | 内容 |
| :-- | :-- |
| 证据 | 台账 §5.1 `ReminderRequest.notificationId` 字段说明：「**相同 id 的后一条提醒会覆盖前一条**」；开发指南 §2.3 坑 3 直接列为「踩过一次就别再踩」 |

## P4 · `onDestroy()` 里的异步工作**可能根本不执行**

| 项 | 内容 |
| :-- | :-- |
| 证据 | SDK 原文（`openharmony/ets/api/@ohos.app.ability.UIExtensionAbility.d.ts:115`）：「在执行完onDestroy生命周期回调后，应用可能会退出，从而可能导致onDestroy中的异步函数未能正确执行，比如异步写入数据库。**推荐使用Promise异步回调**，避免因应用退出导致onDestroy中的异步函数（比如异步写入数据库）未能正确执行。」（转引自调查 01 §5.4；开发指南 §2.1、台账 §7.4） |
| 表现 | 分享进来的原文偶尔没落盘；用户以为分享成功了，回到应用里什么都没有。**复现概率随系统负载变化**，最难稳定复现 |
| 处置 | ① **拿到 want 就落盘**——UIAbility 形态看 `onNewWant`，扩展形态在 `onSessionCreate` 阶段完成（开发指南 §2.1、§9.2）；② 若确实要写在销毁里，按官方推荐写成 `async onDestroy(): Promise<void>` 并 `await`；③ 失败路径不留空白页（扩展形态 `session.terminateSelf()`） |

> [!note] 同族但不算「坑」的两条硬约束（写代码时一起记住）
> - 代理提醒**单应用有效提醒 ≤ 30 条**，超了报 `1700002`；点 CLOSE 才算过期，**周期性提醒永远算有效**（台账 §5.2）。→ 只为最近 30 条未完成任务发布，超出显示「提醒已合并」。
> - **通知授权是所有提醒路径的前置条件**；用户拒绝后（`1600004`）`requestEnableNotification` **再也弹不出窗**，重试只能靠 `openNotificationSettingsWithResult(context)`（台账 §8.1、开发指南 §2.1）。

## P5 · `@Builder` 不要用组件属性名（`toolbar` 这类）—— 会编译报错

`toolbar` 是 `CustomComponent` 基类的**保留成员**：`toolbar(value: CustomBuilder): CommonAttribute`。
在自己的组件里再声明 `@Builder toolbar()`，签名对不上，直接报类型错误：

```text
Property 'toolbar' in type 'X' is not assignable to the same property in base type 'CustomComponent'.
  Type '() => void' is not assignable to type '(value: CustomBuilder) => CommonAttribute'.   (2416)
Argument of type 'this' is not assignable to parameter of type 'BaseCustomComponent'.          (2345)
```

**这是 2026-10-12 用 `mcp__deveco__check` 在 `templates/global-reuse-pool.ets` 上实报出来的，不是推测**；
已在模板里改名 `topToolbar` 并复检为 **0 error**。

**规避**：`@Builder` 命名避开组件属性名 —— 用 `topToolbar` / `buildHeader` / `headerArea` 这类。
同类高危名：`title`、`width`、`height`、`padding`、`margin`、`opacity`、`id`、`key`、`clip`、`scale`、`rotate`。

## T1 · **若**你的 shell 是 Windows PowerShell 5.1 —— 无 BOM 的 UTF-8 `.ps1` 会被当 ANSI 解析

| 项 | 内容 |
| :-- | :-- |
| 触发条件 | **这条坑不是某一台机器特有的，也没有「三人共用一台机器」的意思。** 判定方法：`$PSVersionTable.PSVersion.ToString()` —— 主版本是 **5** 就适用；是 **7+** 则本条**通常不适用**（PS 7 默认按 UTF-8 读脚本，不再当 ANSI）。⚠️ **「7+ 不适用」这一半未实测**：生成副本时手上只有 PS 5.1、没有 `pwsh`，所以没验过。拿不准就照样跑一次 BOM 修复（见「处置」），无害。另：`Get-Command pwsh -ErrorAction SilentlyContinue` **有输出** = 你装了 PowerShell 7，**输出为空** = 只有 `powershell.exe` |
| 证据 | 问题列举 #26 实测（在一台只有 PS 5.1 的机器上）：「无 `pwsh`，只有 `powershell.exe` 5.1，脚本要写 UTF-8 **with BOM** 否则中文路径解析失败」；`Distiller-Skill\tools\ensure-bom.ps1` 文件头原文：「Windows PowerShell 5.1（本机唯一 shell）会把无 BOM 的 .ps1 文件解码成 ANSI/GBK，从而**弄乱所有非 ASCII 文本并产生假的解析错误**」——括号里的「本机唯一 shell」是那台机器的现状，**不是这条坑的成立条件；成立条件是 PS 5.1 这个版本** |
| 表现 | **两种症状一起出现**：① 脚本里的中文变成乱码（`鍒涘缓` 这类）；② 报**莫名其妙的** `Unexpected token`、字符串未终止、`Missing ')'` 之类的解析错误——报错行往往看着完全正常。**判定法：脚本报 `Unexpected token` 且中文变乱码，就是这个原因**。**在生成这个技能包的过程中就踩过这一次**：写出来的 `.ps1` 是 UTF-8 无 BOM |
| 处置 | 写完 `.ps1` 立刻跑一次 BOM 修复（脚本本身是 ASCII-only，任何编码下都能跑）：`powershell -NoProfile -ExecutionPolicy Bypass -File tools\ensure-bom.ps1 -Path tools\*.ps1`。这个脚本是**幂等**的：读的时候按 UTF-8 读、写的时候一律加 BOM，本来就带 BOM 的文件输出仍是**一个** BOM（脚本会打印 `[already]` 而不是 `[ADDED  ]`）。**所以 PS 7+ / 已带 BOM 的机器上跑它也无害** |
| 边界 | 这条只针对**脚本**：Markdown / `.ets` **正文**要 UTF-8 **无 BOM**（避免 BOM 混进内容），`.ps1` 才要带 BOM。**与 shell 版本无关，三台机器一致** |

## T5 · 中文路径与编码：正文无 BOM、脚本带 BOM

| 对象 | 编码要求 |
| :-- | :-- |
| Markdown / `.ets` / 配置**内容** | UTF-8 **无 BOM**（BOM 会混进正文，`sync-docs.ps1` 也按无 BOM 写回） |
| `.ps1` **脚本文件** | UTF-8 **带 BOM**（否则见 T1） |
| 行尾 | 仓库内一律 **LF**（`.gitattributes`：`* text=auto eol=lf`）。不锁行尾的话，编辑器一存就是「整个文件都改了」的**假 diff** |

## T8 · `mcp__deveco__check` 的工程根是**工程目录**，送检文件必须在它里面

实测：工程根是 `...\HMOS_proj\Distiller`（**不是**它的父目录 `...\HMOS_proj`）。绝对路径被拒，`../` 也被拒。
**后果**：放在本 skill 包里的 `templates/*.ets` 默认**送不进去** —— 它不在任何 HarmonyOS 工程内。

**送检办法（2026-10-12 实测可行）**：临时拷进 entry 模块，检查完删掉。

```powershell
$stage = "<Distiller>\entry\src\main\ets\_tpl_check"
New-Item -ItemType Directory -Force -Path $stage | Out-Null
Copy-Item "<本skill>\templates\*.ets" -Destination $stage -Force
# 对 entry/src/main/ets/_tpl_check/<file>.ets 送检；一次别超过 2~3 个，否则 LSP 20s 超时
Remove-Item $stage -Recurse -Force
```

**必须放模块内**：放在工程根的裸目录里，LSP 会在 20 s 内不返回任何诊断
（`received no diagnostics within 20000ms from LSP`）—— 那**不算通过**。
收尾记得确认 `git status` 干净。
