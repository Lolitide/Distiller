# 09 · 文档新鲜度与升级

> **一句话**：这个 skill 里的官方文档副本是**快照**，不是活链接。快照跟着 **devecocli 的 npm 包**走；
> 想刷新，只能升级 devecocli，然后重跑爬取脚本。**没有 `devecocli docs update` 这个子命令。**

> [!warning] 2026-10-12 实测推翻的一条前提：**升级 CLI 不会刷新那个 md 目录树**
> 1.2.0 把 `docs.zip` 解压成 `~\.local\share\deveco-cli\docs` 下的 md 目录树；
> **1.3.4 改为直接从包内 `docs.zip` 里读**（只把 `index.zip` 解到 `<数据目录>\index\data`）。
> 所以升级到 1.3.4 后，那个 md 目录树**一个字节都不会变**——它成了旧版遗留物。
> 实测：升级到 1.3.4 并跑过 `devecocli docs catalog` 之后，该目录的 `.version` 仍是 `1.2.0`、md 数仍是 14125、mtime 未变。
>
> **正确姿势**：把 `docs.zip` 解到独立目录再爬（不碰旧目录，还留着做比对）：
>
> ```powershell
> cd E:\Program_File\Skill\Distiller-Skill
> powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -ExtractDocsZip -Apply
> # 记下它打印的目标目录，然后：
> powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -DocsRoot "<上一步的目标目录>" -Check
> powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -DocsRoot "<上一步的目标目录>" -Only official -Apply -Prune
> ```
>
> 实测差异（1.2.0 遗留目录 → 1.3.4 的 docs.zip）：**md 14,125 → 14,686**，
> 逐文件**变更/新增 4,024、消失 86**；而且新库多了 `26_0_0_Beta2` / `26_0_0_Release` 两档版本说明。
> 所以**"升级了但目录没变"不等于没有新内容** —— 一定要走 `docs.zip` 这条路。

## 1. 机制（为什么「刷新文档」等于「升级 CLI」）

| 事实 | 证据 |
| :-- | :-- |
| 文档**随 npm 包发布** | 1.2.0 包里含 `docs.zip` = 51,557,398 B，占包体 52,157,405 B 的 **98.85%**；`package.json` 里有维护者脚本 `"download-docs": "tsx scripts/download-docs.ts"` —— 快照是**发布时**从华为站点抓下来打进包的（**这些体积数字是 1.2.0 那个包的量，换版本就会变**；机制本身不变） |
| `docs` 只有三个子命令 | `devecocli docs --help` → `search` / `read` / `catalog`。**没有 update** |
| store 位置与版本门控 | `docsDir = join(os.homedir(), ".local", "share", "deveco-cli", "docs")`；`versionFile = docsDir/.version`；`getCurrentVersion()` **硬编码返回包版本** |
| 换版本 = **整库 `rm -rf` 重解** | `extractDocsIfNeeded()`：`.version` ≠ 当前版本 → `cleanOldDocs()`（`fs.rm(docsDir, {recursive:true, force:true})`）→ 从 `docs.zip` 全量重解 |
| 升级命令做什么 | `update` 子命令 = `npm install -g @deveco/deveco-cli@latest` |
| 1.3.x 是分包 | `@deveco/deveco-cli@1.3.4` 只有 2 个文件 / 2,270 B，真实体在 `@deveco/deveco-cli-common@1.3.4`（57,036,672 B / 38 files / `node >= 22`，带 `postinstall`） |

### 三条必须记住的负面结论

1. **升级是全局的。** 会波及你其它 HarmonyOS 工程与 `hmos-*` 技能里按旧快照取证的 documentId 引用。
2. **不要「本地并存两个版本」。** store 路径硬编码走 `os.homedir()`，两个版本会**互相 `rm -rf` 抢同一个 store**。要么整体升，要么整体不升。
3. **永远不要手改 `~\.local\share\deveco-cli\docs`。** 换版本必被整库抹掉。要留证据就留进本 skill 的 `references\`。

## 2. 升级 runbook（由**你**在终端执行，agent 不代跑）

### 第 0 步（推荐，5 分钟）· 先留旧快照指纹

```powershell
cd E:\Program_File\Skill\Distiller-Skill
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -FingerprintOnly -Apply
```
产出 `references\official\_provenance-<版本>.json`（逐文件 sha256）。**这是唯一一次能抓到旧快照的机会** —— 升级会把它抹掉，之后就没有比对基线了。

### 第 1 步 · 升级

```powershell
npm i -g @deveco/deveco-cli@1.3.4
```
（`devecocli update` 等价于 `npm i -g @deveco/deveco-cli@latest`；显式写版本号更可控。）

### 第 2 步 · 四条断言（任一不过就停下，别继续爬）

```powershell
devecocli --version                                          # 期望 1.3.4
Get-Content "$HOME\.local\share\deveco-cli\docs\.version"     # 期望 1.3.4
Get-Content "$HOME\.local\share\deveco-cli\docs\.index\build-meta.json"
#   docsZipSha256 必须 != 7f4183fb41f8c2224ec9941d666ee0a6e178741c4cc511d4bba53d535273b463
Get-ChildItem "$HOME\.local\share\deveco-cli\docs\版本说明" -Directory
#   期望多出 26_0_0 Beta2 或更新的版本目录（生成副本时旧快照里只有 26_0_0 / Beta1，
#   而那台机器的 SDK 与模拟器都是 Beta2 —— 你自己机器上的版本组合用 01-项目基线.md §1.1 现探，不要照抄）
```

**若 `.version` 与 `docsZipSha256` 都没变 → 库根本没换**，后面所有「更新」都是错觉。转第 4 节的排查分支。

### 第 3 步 · 重跑爬取并比对

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -Check      # 只读比对
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -Apply      # 重新爬
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -ExtractSamples -Apply
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -Revalidate -Apply
```
- `-Check` → `references\10-漂移报告.md`：三张表（逐文件 sha256 变更 / 路径消失 / 清单解析不到）。
- `-Revalidate` → `10-漂移报告.md` 的另一半：`03-能力速查.md` 与 `06-未取证清单.md` 的条目在新库里还能不能命中。
- **拿到报告后要人工确认**再改 `03` / `06`。命中页数 > 0 只说明「官方有相关内容」，不等于原先的未取证项已被回答。

### 回滚

```powershell
npm i -g @deveco/deveco-cli@1.2.0
```
`.version` 不匹配 → store 自动重解回 1.2.0，**不需要手工恢复**。

## 3. 快照口径表（**生成这份副本的机器**的文档库指纹）

> [!warning] 先看清这张表是谁的
> 它记的是**生成这份副本的那台机器**上、**当时那一次** `build-references.ps1 -Apply` 抓到的指纹 ——
> **不是团队共享口径，你自己的机器一定不同**（换过 `devecocli` 版本、甚至只是重装一次，`.version` 与 `docsZipSha256` 就会变）。
> 它的用途是**溯源**：「这份 `references/official/` 副本来自哪个快照」。要问「**我机器上**的库是什么版本」，得去读**你自己**的 store：
> `$HOME\.local\share\deveco-cli\docs\.version` 与 `…\docs\.index\build-meta.json`（`$HOME` 展开成你的家目录）。
> 两边对不上，说明你看的副本和你机器上的库**不是同一个快照** —— 这正是 `-Check` / `-Revalidate` 要发现的事。

本节的两处数值由 `tools\build-references.ps1 -Apply` 写入 `07-官方文档索引.md` 表头，以下是**生成这份副本时**的实际值：

| 项 | 值 |
| :-- | :-- |
| 文档库根 | `$HOME\.local\share\deveco-cli\docs`（`$HOME` = **你自己**的家目录；这里**故意不写生成副本那台机器的绝对路径**，账户名与盘符对你没有意义） |
| `.version`（= 包版本） | `1.2.0` |
| `docsZipSha256` | `7f4183fb41f8c2224ec9941d666ee0a6e178741c4cc511d4bba53d535273b463` |
| `.index\build-meta.json` `indexVersion` | `1.9.1` |
| `builtAt` | 2026-09-22 19:05:30 |
| `segmentCount` | 23537 |
| 库内 md | 14125 篇 / 135.1 MB |
| `docs.zip` 文件时间 | 2026-07-17 |

> **判断「这份副本有多新」就看这张表**，不要看本文件或 `07` 的生成时间。
> 注意表里的 `.version` 是**库**的版本（= 生成它的那个 CLI 版本），**不一定等于你机器上 `devecocli --version` 报的版本** ——
> 两者不一致时以「你机器上的 `.version`」为准判断库的新旧，以 `devecocli --version` 为准判断 CLI 的新旧。

## 4. 排查分支：升级后库没换

1.3.4 引入了 `postinstall: node scripts/postinstall.mjs`，**store 落点可能不再是** `~\.local\share\deveco-cli\docs`。按顺序查：

```powershell
Get-ChildItem -Recurse -Filter docs.zip $HOME -ErrorAction SilentlyContinue
Get-ChildItem "$HOME\.local\share\deveco-cli" -Force -Recurse -Depth 2
# 若装的是 1.3.x 这类分包版本，去全局 npm 根下看真实的包目录：
$g = npm root -g            # 实测输出形如 <你的家目录>\AppData\Roaming\npm\node_modules
Get-ChildItem "$g\@deveco" -Force
Get-ChildItem "$g\@deveco" -Recurse -Depth 3 -Filter postinstall.mjs -ErrorAction SilentlyContinue |
  Select-Object -ExpandProperty FullName
```
**在找到真实 store 之前不要爬取** —— 否则会把旧库当成新库，`07` 的指纹表头与实际内容不符。

## 5. 联网来源（唯一一条）

`references\sources\flutter-ohos\` 来自 gitcode，**不受 devecocli 版本影响**，需要时单独重跑：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File tools\build-references.ps1 -Only sources -Apply
```

已知约束：gitcode 匿名 contents API 约 **100 次快速调用后返回 HTTP 429**，脚本已内置 180 ms 间隔与退避重试；
`git/trees/<sha>?recursive=1` **不可用**（只返根树），所以走逐层枚举。
