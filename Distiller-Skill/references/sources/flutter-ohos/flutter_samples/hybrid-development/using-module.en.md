# How to Use a Module in Hybrid Development

This topic describes how to reference `flutter_module` in an OpenHarmony project.

## Prerequisites

- [Flutter OH Development Environment Setup Guide](../getting-started/flutter-oh-env-setup.en.md) has been completed.
- An OpenHarmony native project has been created using DevEco Studio.

## Preparing the flutter_module Project

### Step 1: Create flutter_module

```bash
# Create a Flutter module project in the directory sibling to the host project
flutter create -t module flutter_module
```

### Step 2: Build the Artifacts

```bash
cd flutter_module
# Generate the .ohos project structure and HAR artifacts
flutter build har --debug
cd -
```

> [!NOTE]
>
> The HAR dependency approach consumes the generated HAR artifacts (located in `flutter_module/build/ohos/har/debug/`; for release builds, in `release/`); the source dependency approach consumes only the generated `.ohos` project structure.

### Step 3: Copy the Entry Files to the Host

Copy the `EntryAbility` and default home page generated by `flutter_module` into the host project as the entry for loading Flutter pages later:

```bash
cp flutter_module/.ohos/entry/src/main/ets/entryability/EntryAbility.ets MyApplication/entry/src/main/ets/entryability/EntryAbility.ets
cp flutter_module/.ohos/entry/src/main/ets/pages/Index.ets MyApplication/entry/src/main/ets/pages/Index.ets
```

## Integration Methods

An OpenHarmony project can reference `flutter_module` in either of two ways. Choose one based on your scenario:

| Method | Applicable Scenario | Immediate Effect After Source Code Changes |
|------|---------|------------------|
| HAR artifact dependency | Stable releases; module and host maintained separately | No. The HAR must be rebuilt and replaced |
| Source dependency (recommended) | Development and joint debugging; frequent changes to the module or plugins | Yes. Re-running the host makes them take effect immediately |

### Method 1: Reference the HAR Artifacts

#### Step 1: Copy the HAR Files

Copy the HAR files from the build artifacts to the `har/` directory at the root of the host project:

```bash
cp -r flutter_module/build/ohos/har/debug/* MyApplication/har/
```

> [!WARNING]
>
> Referencing HARs separately from each module instead of storing them together in the `har/` directory causes duplicate packaging and increases the package size. Always place them in the `har/` directory and reference them through `overrides`.

#### Step 2: Configure oh-package.json5

Reference the HARs in `overrides` of `MyApplication/oh-package.json5` (debug is used as an example; for release, replace the `_debug` file name suffix with `_release`):

```json5
{
  "overrides": {
    "@ohos/flutter_ohos": "file:./har/flutter_embedding_debug.har",
    "flutter_native_arm64_v8a": "file:./har/arm64_v8a_debug.har",
    "@ohos/flutter_module": "file:./har/flutter_module.har"
  }
}
```

Then declare them in `dependencies` of `entry/oh-package.json5` (no version specified; they are resolved uniformly through `overrides`):

```json5
{
  "dependencies": {
    "@ohos/flutter_ohos": "",
    "flutter_native_arm64_v8a": "",
    "@ohos/flutter_module": ""
  }
}
```

#### Step 3: Configure the Signature and Run

Configure the signature of `MyApplication` in DevEco Studio and run it. For signing and installation steps, see [OpenHarmony Device Running Guide](../getting-started/openharmony-device-guide.en.md).

### Method 2: Source Dependency (Recommended)

The host compiles the source code of `flutter_module` and the `ohos/` source code of each plugin directly through the hvigor plugin `injectNativeModules`. Source code changes take effect immediately, without repeatedly building and copying HARs. This aligns with the `:flutter` submodule include mechanism of Add-to-App on Android / iOS.

#### Step 1: Register the hvigor Plugin in the Host

In the host's `hvigorconfig.ts` (create it if it does not exist), call `injectNativeModules`; register `flutterHvigorPlugin` in `hvigorfile.ts`, with the import path pointing to `.ohos/include_flutter` of `flutter_module`:

```ts
// hvigorconfig.ts
import { injectNativeModules, getFlutterProjectPath } from './path/flutter_module/.ohos/include_flutter';

injectNativeModules(__dirname, getFlutterProjectPath(), 1)
```

```ts
// hvigorfile.ts
import { appTasks } from '@ohos/hvigor-ohos-plugin';
import { flutterHvigorPlugin, getFlutterProjectPath } from './path/flutter_module/.ohos/include_flutter';

export default {
  system: appTasks,
  plugins:[flutterHvigorPlugin(getFlutterProjectPath(), 1)]
}
```

#### Step 2: Clean Up the Old Configuration

- `MyApplication/build-profile.json5`: Remove the `flutter_module` module declaration (it is dynamically injected by the plugin).
- `MyApplication/oh-package.json5`: Remove Flutter-related dependencies from `dependencies` and `overrides` (skip this if they do not exist).

#### Step 3: Declare the entry Dependencies

Add the following to `dependencies` of `entry/oh-package.json5` (empty strings, specifying no version or path):

```json5
{
  "dependencies": {
    "@ohos/flutter_ohos": "",
    "@ohos/flutter_module": ""
  }
}
```

> [!NOTE]
>
> Plugin source code is injected by `injectNativeModules` at build time and does not need to be declared in `dependencies`; add a plugin dependency only when this module directly calls that plugin's API, for example `"plugin_x": ""`.

> [!WARNING]
>
> The two dependencies declared in this step are prerequisites for the entry to import `@ohos/flutter_module` / `@ohos/flutter_ohos`; if either is missing, compilation fails with the error "Cannot find '@ohos/flutter_module'". These two entries are not remote repository packages but local source nodes injected at build time through `includeNode` by the hvigor plugin `injectNativeModules`. Therefore, **do not run `ohpm install` separately to refresh dependencies**: ohpm bypasses hvigor, cannot see the injected local nodes, and looks them up in remote repositories, which returns 404. Always use DevEco Studio's **Sync Now** or `hvigorw assembleHap` to trigger dependency resolution.

#### Step 4: Configure the Signature and Run

Configure the signature in DevEco Studio and run. For the rebuild process after source code changes, see [Build and Verification](../app-development/hvigor-plugin-build.en.md#build-and-verify).

<details>
<summary>Early manual source copy approach (legacy, not recommended)</summary>

In earlier versions, source dependency could be achieved by manually copying the `flutter_module` source directory, registering the module in `modules` of `build-profile.json5`, and referencing it through the `./flutter_module` path in `oh-package.json5`. This approach involves tedious configuration and requires repeated copying after source code changes; use the hvigor plugin approach described above instead.

</details>

## Verification

1. Run `Sync Now` in DevEco Studio, or run `ohpm install` in the root directory of the host project (**for the source dependency approach, do not run `ohpm install` separately**; use `Sync Now` or `hvigorw` instead. For the reason, see Method 2, Step 3).
2. Configure the signature and run; or execute the following in the host project directory:

   ```bash
   hvigorw assembleHap --no-daemon -p product=default -p buildMode=debug
   ```

3. If the app starts and enters the Flutter page normally, the integration is successful.

## FAQ

### Problem: No oh_modules Cache Directory Is Generated Under entry After Integration

Run `ohpm install` in the project root directory, not in the `entry` directory.

### Problem: Compilation Error "Cannot find '@ohos/flutter_module'"

With the source dependency approach, `@ohos/flutter_module` is injected by the hvigor plugin `injectNativeModules` at build time through `includeNode` as a local source node; the package does not exist in remote repositories. This error is usually caused by one of the following:

- `"@ohos/flutter_module": ""` is not declared in `dependencies` of `entry/oh-package.json5` (see Method 2, Step 3), so the package is not linked into `entry/oh_modules`. Add it and build again.
- `ohpm install` was run separately to refresh dependencies: ohpm bypasses hvigor, cannot see the injected local nodes, and looks them up in remote repositories, which returns 404. Use DevEco Studio's **Sync Now** or `hvigorw assembleHap` to trigger dependency resolution instead.

> [!NOTE]
>
> With the HAR dependency approach, `@ohos/flutter_module` comes from the HAR artifacts in the `har/` directory, and `ohpm install` resolves it properly; this entry applies only to the source dependency approach.

### Problem: Changes to flutter_module Code Do Not Take Effect

- **Source dependency approach**: After Dart changes, run `flutter pub get` in the `flutter_module` directory to refresh the `.ohos` injected artifacts, and then run the host project again.
- **HAR dependency approach**: Run `flutter build har --debug` (or `--release`) again in the `flutter_module` directory, copy the newly generated HARs into the `har/` directory to replace the old files, and run **Sync Now** in DevEco Studio to refresh dependencies.

### Problem: Can the HAR Dependency and Source Dependency Approaches Be Mixed

Mixing them is not recommended. With the source dependency approach, the module and plugin source code are injected by the plugin; manually referencing HARs in `oh-package.json5` at the same time causes duplicate symbols or version conflicts. Choose one of the two approaches.
