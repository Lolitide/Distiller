# Developing an FFI Plugin

You may refer to [Developing an FFI plugin](https://flutter.cn/docs/packages-and-plugins/developing-packages#plugin-ffi).

This document describes how to develop an FFI plugin on the OpenHarmony platform, covering the end-to-end flow: placing precompiled so dynamic libraries, packaging and verifying the har, and publishing to git so the plugin can be consumed by a host project via a git dependency.

## Prerequisites

Before you start, make sure your local environment is ready:

1. **Flutter ohos toolchain**: Run `flutter --version`; you should see a version number like `3.x.x-ohos-x.x.x` (with the `-ohos-` suffix), and the `HarmonyOS toolchain` line in `flutter doctor` should be `[✓]`.
2. **DevEco Studio + OHOS SDK**: Install the OpenHarmony/HarmonyOS SDK through DevEco Studio. The environment variable `DEVECO_SDK_HOME` points to the SDK root directory. hvigorw, ohpm, Node, etc. are installed together with DevEco and require no separate configuration.
3. **Project path must be pure ASCII**: The hvigor build system requires the project path to contain only letters, digits, hyphens (`-`), underscores (`_`), dots (`.`), English parentheses (`()`), spaces, or `@`. **A path containing non-ASCII characters such as Chinese fails the build directly** (see the FAQ). This is the most common environment-type blocker — Chinese users should take particular note.
4. **LLVM/libclang (optional, only when you need to regenerate the Dart bindings)**: `package:ffigen` depends on the libclang dynamic library. If you modify `src/*.h` and need to rerun ffigen, install LLVM and set `LIBCLANG_PATH`, or configure `llvm-path` in `ffigen.yaml` (see Step 4). It is not needed if you only use the pregenerated bindings shipped with the template.

> [!TIP]
> The har packaging in Step 6 does **not** require app signing; however, the `flutter build hap` verification step in [Step 7.3](#step-7-3) **does** require a debug signature to be configured first (see [Step 7.3](#step-7-3)).

## Usage Steps

### Step 1: Create the package

```sh
flutter create --template=plugin_ffi hello --platforms=android,ios,ohos
```

After creation, the plugin root directory structure:

```text
hello/
├── lib/                          # Dart interface implementation (includes the template-pregenerated hello_bindings_generated.dart)
├── src/                          # Cross-platform C/C++ native source (includes CMakeLists.txt)
├── ohos/                         # ohos platform project (har module)
│   └── src/main/                 # Module code (cpp/, module.json5)
├── android/                      # Android platform project
├── ios/                          # iOS platform project
├── example/                      # Example app (its example/ohos is a complete hvigor host project, used to build/verify the plugin har)
├── ffigen.yaml                   # ffigen configuration
└── pubspec.yaml
```

### Step 2: Specify platforms in pubspec.yaml

The `flutter create --template=plugin_ffi` **template has already generated** the `plugin.platforms` configuration; **you usually do not need to edit it by hand** — only edit it when adding or removing platforms:

```yaml
  plugin:
    platforms:
      android:
        ffiPlugin: true
      ohos:
        ffiPlugin: true
      ios:
        ffiPlugin: true
```

`ffiPlugin: true` means the toolchain is responsible for building and packaging the native code (required by `dart:ffi`).

### Step 3: Place the precompiled so files

If the plugin contains precompiled so dynamic libraries (instead of compiling C/C++ sources under `src/` on the fly), place them in the plugin's `ohos/libs/<abi>` directory. Supported ABI directories include:

- `arm64-v8a` (real devices)
- `x86_64` (emulators)

Example directory structure:

```text
ohos/
├── build-profile.json5
├── oh-package.json5
├── hvigorfile.ts
├── src/main/
└── libs/
    ├── arm64-v8a/
    │   └── libhello.so
    └── x86_64/
        └── libhello.so
```

<a id="step-3-1"></a>**Step 3.1: Remove externalNativeOptions**

The `ohos/build-profile.json5` generated by `flutter create --template=plugin_ffi` configures `externalNativeOptions` by default, which compiles the C sources from `../src/CMakeLists.txt` on the fly into so files. **When using precompiled so files, remove it**, to avoid the build system failing because it cannot find the CMake sources, or the on-the-fly build output overwriting the precompiled so.

Before (template default):

```json5
{
  "apiType": "stageMode",
  "buildOption": {
    "externalNativeOptions": {
      "path": "../src/CMakeLists.txt",
      "arguments": "",
      "cppFlags": "",
    }
  },
  "targets": [
    { "name": "default" }
  ]
}
```

After (using precompiled so):

```json5
{
  "apiType": "stageMode",
  "buildOption": {
  },
  "targets": [
    { "name": "default" }
  ]
}
```

> [!TIP]
> If you want the so to be compiled from C/C++ sources on the fly (instead of precompiled), just keep `externalNativeOptions`; there is no need for a `libs/` directory. The OHOS SDK already ships cmake/ninja (build tasks `BuildNativeWithCmake` / `BuildNativeWithNinja`), so **there is no need to install cmake separately on the host machine**.

#### How so files get packaged into the har

When packaging a har module, OpenHarmony's hvigor build system automatically packs the `.so` files under `libs/<abi>/` at the module root into the har artifact (at the `libs/<abi>/` path inside the har); no extra configuration in `build-profile.json5` is required.

> [!IMPORTANT]
> The so files should be placed under `ohos/libs/<abi>/` (that is, the `libs/` directory at the ohos module root). Files placed elsewhere (such as `ohos/src/main/libs/<abi>/`) are also packed into the har, but their path inside the har is `src/main/libs/<abi>/`, **which is not in OpenHarmony's runtime so search path `libs/<abi>/`**, causing `dlopen failed` at runtime. Always use `ohos/libs/<abi>/`.

> [!TIP]
> Output difference between the precompiled path and the source-compilation path: with source compilation (keeping `externalNativeOptions`), hvigor **automatically** packs the C++ runtime `libc++_shared.so` into the har as well; the precompiled path only packs the files you manually put into `ohos/libs/`. If your precompiled so depends on the C++ runtime (`libc++_shared.so`), put it into `ohos/libs/<abi>/` too; otherwise loading fails at runtime due to missing symbols.

### Step 4: Bind the local native code

To use the local native code, you need to bind it in Dart.

To avoid writing the bindings by hand, they are generated by package:ffigen from the header file (src/hello.h). `flutter create --template=plugin_ffi` **has already pregenerated** `lib/hello_bindings_generated.dart`, ready to use out of the box. **Only after you modify `src/hello.h`** do you need to run the following command to regenerate the bindings:

```sh
dart run ffigen --config ffigen.yaml
```

> [!IMPORTANT]
> ffigen depends on **LLVM's libclang dynamic library**. If the run reports `Couldn't find dynamic library in default locations`, install LLVM first (on Windows, install a [llvm-project release](https://github.com/llvm/llvm-project/releases) or the version bundled with Visual Studio/DevEco), then let ffigen find it in either of these ways:
>
> - Set the environment variable `LIBCLANG_PATH` to the directory containing `libclang` (on Windows, the directory containing `libclang.dll`);
> - Or add `llvm-path: ['<LLVM installation path>']` to `ffigen.yaml`.

### Step 5: Call the local native code

Local native functions that finish quickly can be called directly in any isolate. For example, see sum in `lib/hello.dart`.

Local native functions that run for a longer time should be called on a [helper isolate](https://dart.cn/guides/language/concurrency#background-workers) to avoid dropped frames in the Flutter application. For example, see sumAsync in `lib/hello.dart`.

### Step 6: Package the har and verify the so

**Step 6.1: Package the har**

**Option A: DevEco Studio (GUI)**

Use DevEco Studio to open the plugin's `example/ohos` directory, locate the plugin's ohos module, and click `Build > Make Module 'xxx'` to package it.

**Option B: Command line (CI/CD friendly)**

Run the hvigorw `assembleHar` task in the `example/ohos` directory to package the plugin's har alone (**no app signing required**):

```sh
# Run in the example/ohos directory
hvigorw assembleHar --no-daemon -p product=default -p buildMode=debug
```

After a successful build, the har artifact is located at:

```text
ohos/build/default/outputs/default/<plugin_name>.har
```

**Step 6.2: Verify the har contains the so**

A har is essentially the **tar.gz** format (a gzip-compressed tar archive). You can use the following command to check whether the har contains so files (`tar` ships with Linux/macOS, and Windows 10+ also ships `tar.exe`):

```sh
# Works on all platforms
tar -tzf <plugin_name>.har | grep "\.so"
```

The expected output should contain entries such as `package/libs/arm64-v8a/libhello.so`. If it is empty, the so was not packed into the har; go back and check the directory location and `build-profile.json5` configuration from Step 3.

> [!IMPORTANT]
> The har produced by the current hvigor toolchain is **tar.gz** (not zip). Do not use `unzip` or .NET's `[System.IO.Compression.ZipFile]::OpenRead`; they fail because they cannot recognize the archive.

### Step 7: Publish to git and consume via a git dependency

<a id="step-7-1"></a>**Step 7.1: Pre-commit checks (.gitignore)**

> [!NOTE]
> This is **the most common cause** of "works with a local path dependency, but the har has no so in it after importing via git".

Before committing, make sure:

1. **The so files are tracked by git**. The template's `ohos/.gitignore` does not ignore `*.so`, but if `*.so` or `libs/` is mistakenly added to the repository root `.gitignore`, the so files will not be committed; when others import the plugin via git, `ohos/libs/` is empty and naturally nothing can be packed into the har. How to check:

   ```sh
   git ls-files | grep "\.so"
   # You should see entries such as ohos/libs/arm64-v8a/libhello.so
   ```

   If it is empty, force-add the file with `git add -f ohos/libs/arm64-v8a/libhello.so`, and fix the `.gitignore`:

   ```text
   # Wrong (ignores all so files, so the precompiled so cannot be committed)
   *.so
   ```

   To ignore only the Flutter engine so, specify it precisely, for example:

   ```text
   # Ignore only engine/artifact so, without affecting the plugin's precompiled so
   **/libs/arm64-v8a/libflutter.so
   **/libs/arm64-v8a/libapp.so
   **/libs/arm64-v8a/libvmservice_snapshot.so
   ```

2. **Do not commit har build artifacts**. The template's `ohos/.gitignore` already includes `/build` (har artifacts land under `build/` and are ignored). It is recommended to also add a `**.har` line as a fallback to avoid accidental commits:

   ```text
   **.har
   /build
   ```

**Step 7.2: Consume the plugin from the host project via a git dependency**

Add the FFI plugin as a git dependency in the host project's `pubspec.yaml`:

```yaml
dependencies:
  hello:
    git:
      url: https://gitcode.com/<org>/hello_ohos.git
      path: hello            # If the plugin is in a repository subdirectory, specify path; omit if it is at the root
      ref: v1.0.0            # Specify a branch/tag/commit
```

After you run `flutter pub get`, pub clones the plugin source into the PUB cache. The flutter_ohos tool incorporates the plugin's ohos module into the host project build as a hvigor node (source-based, not a prebuilt har); at build time, the so files are taken from the plugin source's `ohos/libs/<abi>/` and packed into the final hap.

> [!TIP]
> Therefore, **whether the so exists in the git repository's `ohos/libs/<abi>/` directly determines whether a git dependency can pack in the so**. With a local path dependency, the so is taken directly from the local disk (not via git), so it works even if the so was never committed — this is exactly the root cause of the inconsistent behavior between the two import methods.

<a id="step-7-3"></a>**Step 7.3: Verify**

Building a hap requires a debug signature; a har does not. If signing is not yet configured, open the host `ohos` project in DevEco Studio first, go to `File > Project Structure > Signing Configs` and check `Automatically generate signature` (this writes `signingConfigs` into `build-profile.json5`), or fill in your existing signing materials manually.

```sh
flutter pub get
flutter build hap --debug
# or flutter run -d <device-id>
```

The built hap should contain the plugin so; run it on a device to verify that the ffi calls work. To confirm the hap contains the so, run `Build > Build Hap(s)` in DevEco Studio and check `entry/build/default/outputs/default/entry-default-signed.hap` (also a tar.gz archive; inspect it with the method from Step 6.2).

## FAQ

### Build error: Invalid project path / path contains Chinese characters

**Symptom**: `flutter build hap` or `hvigorw` reports `Invalid project path. Current path does not match ...` and lists the allowed character set; the Chinese characters in the path appear garbled.

**Cause**: hvigor requires the project path to contain only ASCII characters (letters, digits, `-`, `_`, `.`, English parentheses, spaces, `@`). Chinese folder names (such as "New folder") are rejected.

**Solution**: Move the project to a pure ASCII path (such as `C:\dev\hello`) and build again.

### Works with a local path dependency, but the har has no so after switching to a git dependency

**Symptom**: With the plugin imported via a local `path` dependency, the so is correctly packed into the har/hap; after switching to a `git` dependency, the build output no longer contains the so.

**Causes and troubleshooting** (ordered by probability, highest first):

1. **The so is not committed to git (most common)**: Use `git ls-files | grep "\.so"` to confirm the so is tracked; check whether the repository root and `ohos/.gitignore` ignore `*.so` or `libs/`. See [Step 7.1](#step-7-1) for details.
2. **Wrong so directory location**: The so must be under `ohos/libs/<abi>/` (the `libs/` at the ohos module root). Files placed under `ohos/src/main/libs/` and similar locations are packed into the har, but are not in the runtime search path `libs/<abi>/`, so `dlopen` fails at runtime. See [Step 3](#step-3-place-the-precompiled-so-files) for details.
3. **externalNativeOptions not removed**: If you use a precompiled so but `ohos/build-profile.json5` still keeps `externalNativeOptions` pointing to nonexistent CMake sources, the build either errors out or skips packaging the prebuilt libs. Remove it as described in [Step 3.1](#step-3-1).
4. **ABI mismatch**: The so must be placed in the ABI directory matching the target device. Real devices use `arm64-v8a`; emulators use `x86_64`.

### The so path inside the har does not match the runtime load path

OpenHarmony loads so files from `libs/<abi>/` inside the hap at runtime. If the so is located at `libs/<abi>/` in the har but you still get `dlopen failed` at runtime, check the so's dependencies (use `readelf -d libhello.so` to see whether the other so files it depends on are also present, and whether `libc++_shared.so` needs to be bundled with the package) and whether the so's compiled architecture (arm64) matches the device.

### ffigen error: Couldn't find dynamic library

**Symptom**: Running `dart run ffigen --config ffigen.yaml` reports `Couldn't find dynamic library in default locations`.

**Cause**: ffigen depends on LLVM's libclang, which is not installed on the machine or cannot be found by ffigen.

**Solution**: Install LLVM and set the `LIBCLANG_PATH` environment variable, or configure `llvm-path` in `ffigen.yaml`. See [Step 4](#step-4-bind-the-local-native-code) for details. If you have not modified `src/*.h`, you can use the template-pregenerated `lib/hello_bindings_generated.dart` directly without rerunning ffigen.
